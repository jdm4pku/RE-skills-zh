## 目的
创建验收标准，定义需求被视为满足的具体、可测试条件。使用此技能来弥合"这个需求是什么意思？"和"我们如何证明它有效？"之间的差距。

这不是测试用例编写——验收标准定义*验证什么*。测试用例定义*如何验证*。验收标准存在于需求中；测试用例存在于测试计划中。

## 核心概念

### 验收标准 vs. 验收测试

| 方面 | 验收标准 | 验收测试 |
|--------|-------------------|-----------------|
| 内容 | 满足条件 | 验证条件的过程 |
| 编写者 | BA / 需求工程师 | QA / 测试工程师 |
| 时间 | 需求规格说明期间 | 测试计划期间 |
| 格式 | Given/When/Then、检查清单 | 包含预期结果的分步测试过程 |
| 存放位置 | SRS、用户故事 | 测试计划、测试管理工具 |

### 验收标准的三种格式

**1. Given/When/Then（Gherkin）**
最适合具有明确前置条件和触发器的行为驱动场景：
```
Given [前置条件],
When [动作],
Then [预期结果].
```

**2. 检查清单**
最适合简单的通过/失败条件：
```
- [ ] [必须为真的条件]
- [ ] [另一个必须为真的条件]
```

**3. 基于规则**
最适合具有多个示例的业务规则：
```
Rule: [业务规则声明]
Example: [输入] -> [预期输出]
Example: [不同输入] -> [不同预期输出]
```

### SMART 验收标准
每个验收标准应满足：
- **Specific（具体的）** -- 描述单一、具体的条件
- **Measurable（可度量的）** -- 具有通过/失败的判定
- **Achievable（可实现的）** -- 技术上可行
- **Relevant（相关的）** -- 可追溯到需求或用户需要
- **Testable（可测试的）** -- 测试人员无需解读即可验证

### 反模式
- **显而易见型** -- "系统应正确运行。" 每个需求都应该正确运行。
- **主观臆断型** -- "界面应美观。" 以谁的审美标准？
- **实现细节型** -- "系统应使用存储在硬件安全模块中的 256 位 AES 加密密钥。" 那是设计，不是需求。
- **无限集合型** -- "系统应处理所有可能的输入。" 无法测试。

## 应用

### 步骤 1：从需求出发

拿到你的需求（用户故事、shall 声明或用例步骤），然后问：
- "我们如何知道这个需求已被满足？"
- "当它正常工作时，用户期望看到什么？"
- "失败看起来是什么样子？"

### 步骤 2：选择正确的格式

| 使用此格式 | 适用场景 |
|----------------|------|
| Given/When/Then | 行为取决于前置条件且有明确的触发/响应 |
| 检查清单 | 没有复杂前置条件的简单通过/失败条件 |
| 基于规则 | 具有多个场景或边界条件的业务规则 |

### 步骤 3：编写标准

**Given/When/Then 示例：**
```markdown
**需求：** CT.ALERT.EXPIRY.1 -- 当化学品距到期日还有 30 天时，
系统应向负责的实验室技术员发送电子邮件警报。

**验收标准：**

AC-1: Given 一种化学品的到期日距今天正好 30 天，
      and 一名实验室技术员被分配到其存储位置，
      When 每日警报作业运行时，
      Then 向分配的技术员发送一封包含化学品名称、CAS 编号、
      存储位置和到期日期的电子邮件。

AC-2: Given 一种化学品的到期日距今天正好 30 天，
      and 该存储位置没有分配技术员，
      When 每日警报作业运行时，
      Then 改为向实验室管理员发送电子邮件。

AC-3: Given 一种化学品状态为"已处置"，
      and 到期日距今天 30 天，
      When 每日警报作业运行时，
      Then 不为该化学品发送任何警报。
```

**检查清单示例：**
```markdown
**需求：** CT.CATALOG.SEARCH.1 -- 按名称、CAS 编号、存储位置
或到期日期范围搜索化学品。

**验收标准：**
- [ ] 按部分化学品名称搜索返回所有匹配记录
- [ ] 按精确 CAS 编号搜索返回特定记录
- [ ] 按存储位置搜索返回该位置的所有化学品
- [ ] 按日期范围搜索返回在该范围内到期的化学品
- [ ] 组合多个条件时缩小结果范围（AND 逻辑）
- [ ] 空搜索结果显示"未找到化学品"消息
- [ ] 在 50,000 条记录下搜索结果在 2 秒内显示
```

**基于规则示例：**
```markdown
**需求：** BR-002 -- 批量折扣计算

**验收标准：**

Rule: 折扣按每个 SKU 的订单数量计算，而非总订单量。
  Example: 50 件 SKU-A -> 0% 折扣（低于 100 件门槛）
  Example: 150 件 SKU-A -> 所有 150 件享受 5% 折扣
  Example: 50 件 SKU-A + 100 件 SKU-B -> A 为 0%，B 为 5%
  
Rule: 折扣适用于税前单价。
  Example: SKU-A 单价 $10，200 件 -> $10 * 0.95 * 200 = $1,900
```

### 步骤 4：验证标准质量

对每个验收标准，验证：
- [ ] 测试人员无需向 BA 询问澄清即可判定通过/失败
- [ ] 该标准测试一个具体条件（而非多个组合条件）
- [ ] 已覆盖边界条件（29 天怎么办？31 天呢？正好 30 天呢？）
- [ ] 已包含负面用例（什么不应该发生）
- [ ] 该标准可追溯到父需求

### 步骤 5：与利益相关方评审

与以下人员逐条讨论验收标准：
- **开发人员** -- "这足够清楚可以实现吗？"
- **测试人员** -- "你能根据这些编写测试用例吗？"
- **用户** -- "这与你期望系统做的事情一致吗？"

## 常见陷阱

### 陷阱 1：没有负面测试用例
**症状：** 所有验收标准都描述系统*应该*做什么。没有描述系统*不应该*做什么。

**后果：** 错误路径、边界情况和安全问题未被测试。

**修复：** 对每个正面标准，问"什么不应该发生？"每个需求至少添加一个负面标准。

---

### 陷阱 2：标准过于模糊，无法测试
**症状：** "系统响应迅速"或"数据正确显示"。

**后果：** 测试人员无法判定通过/失败。"迅速"对谁而言？"正确"按什么标准？

**修复：** 量化："2 秒内响应"和"按指定顺序显示所有 6 个字段"。

---

### 陷阱 3：标准测试的是实现而非行为
**症状：** "系统使用 PostgreSQL 存储记录"或"API 返回 200 状态码"。

**后果：** 标准与实现耦合。如果数据库更改，即使行为相同，标准也会失效。

**修复：** 测试行为："保存后记录可检索"和"系统确认提交成功"。
