## 目的
识别、分类和记录约束或治理系统行为的业务规则。业务规则独立于任何软件系统而存在——它们是组织策略、法规、数学公式和领域约束。使用此技能将持久的业务逻辑与临时的实现细节分离，确保规则得到维护、追溯，并在多个功能和用例中一致地应用。

这不是需求规格说明——而是一个参考目录。业务规则为功能需求、用例和验收标准提供输入，但它们存储在自己的管理集合中。

## 关键概念

### 什么是业务规则？
业务规则是定义或约束业务某个方面的声明。无论是否构建软件，它都存在。示例：
- "超过 $10,000 的订单需要VP审批"（策略）
- "德克萨斯州的销售税为 8.25%"（事实）
- "连续3次逾期付款的客户被归类为高风险"（推断）
- "运费 = 基础费率 + (重量 * 每磅费率) + 附加费"（计算）

### 业务规则分类体系

| 类型 | 定义 | 示例 |
|------|------|------|
| **事实（Fact）** | 在领域中始终为真的陈述 | "一个采购订单必须恰好引用一个供应商" |
| **约束（Constraint）** | 对系统或用户能做什么的限制 | "员工不能审批自己的报销单" |
| **动作使能（Action Enabler）** | 触发或允许某个动作的条件 | "当库存低于再订购点时，生成采购申请" |
| **推断（Inference）** | 从现有事实推导出新事实的规则 | "年订单总额超过 $50K 的客户有资格获得金牌等级" |
| **计算（Computation）** | 数学公式或算法 | "折扣 = base_price * tier_discount_rate * volume_multiplier" |

### 业务规则与需求的区别
- **业务规则：** "超过 $10,000 的订单需要VP审批"（策略声明）
- **功能需求：** "系统应将超过 $10,000 的订单路由到VP审批队列，并且在记录VP审批之前不得处理这些订单"（实现该规则的系统行为）

业务规则是 *为什么（why）*。需求是 *系统对此做什么（what the system does about it）*。

### 业务规则的来源
业务规则来自：
- 公司政策和流程
- 政府法规和行业标准
- 合同义务
- 领域知识（业务如何运作）
- 管理层决策

### 反模式
- **将规则嵌入代码** -- 规则分散在源代码文件中，没有集中目录。当规则变更时，开发人员需要在代码中逐一查找所有实例。
- **将规则混入需求** -- 业务规则混在SRS文本中。当规则变更时，你需要更新多个需求，而不是修改一条规则。
- **未文档化的规则** -- "大家都知道"超过 $10K 的订单需要VP审批。直到有新人加入。

## 应用

使用 `template.md` 获取填写结构。

### 步骤 1：识别业务规则

在需求获取过程中，注意倾听以下表述：
- "我们总是..." / "我们从不..."
- "政策规定是..."
- "根据法律，我们必须..."
- "X 的计算公式是..."
- "如果发生 X，就必须 Y..."
- "只有具备角色 X 的人才能做 Y"

可挖掘的来源：
- 公司政策手册
- 法规文件
- 现有系统文档
- 领域专家访谈
- 当前业务流程描述

### 步骤 2：对每条规则进行分类

对于每条已识别的规则，确定其类型（事实、约束、动作使能、推断或计算）并分配唯一ID：

```
BR-001 [约束]: 员工不能审批自己的报销单。
BR-002 [计算]: 销售税 = 小计 * 辖区税率。
BR-003 [动作使能]: 当库存数量低于再订购点时，
       系统应生成采购申请。
BR-004 [推断]: 如果客户滚动12个月的采购总额
       超过 $100,000，则被归类为"高级客户"。
BR-005 [事实]: 每个产品恰好属于一个产品类别。
```

### 步骤 3：记录每条规则

对于每条业务规则，记录以下信息：

- **规则ID** -- 唯一标识符（BR-001, BR-002 等）
- **规则名称** -- 简短的描述性名称
- **类型** -- 事实 / 约束 / 动作使能 / 推断 / 计算
- **声明** -- 用精确的自然语言描述的规则
- **来源** -- 该规则的出处（政策文件、法规、主题专家）
- **理由** -- 该规则存在的原因
- **相关需求** -- 实现该规则的功能需求
- **相关用例** -- 引用该规则的用例
- **易变性** -- 该规则变更的频率（稳定 / 每年 / 频繁）
- **生效日期** -- 该规则何时生效（对法规规则尤为重要）

### 步骤 4：验证规则

对于每条规则，验证：
- [ ] 规则陈述精确（无歧义）
- [ ] 来源具有权威性
- [ ] 该规则不与其他规则冲突
- [ ] 利益相关者认同规则的正确性
- [ ] 易变性评估是现实的

### 步骤 5：将规则追溯到需求

创建追溯交叉引用：
- 每条业务规则应至少正向追溯到一个功能需求
- 每个实现业务规则的功能需求应反向追溯到该规则
- 当业务规则变更时，追溯关系能准确告诉你哪些需求需要更新

## 示例

参见 `examples/sample.md` 获取完整的业务规则目录。

简要示例摘录：

```markdown
### BR-007: 逾期付款分类
- **类型：** 推断
- **声明：** 如果客户有3张或更多连续发票逾期超过30天未付，
  则被归类为"付款风险客户"。
- **来源：** 财务政策手册，第4.3节（2024-01更新）
- **理由：** 在处理新订单之前触发信用审查
- **相关需求：** FR-42, FR-43
- **易变性：** 每年（每个财年审查一次）

### BR-012: 管控物质记录
- **类型：** 约束
- **声明：** 每次发放 Schedule II-V 管控物质时，
  必须在发放后24小时内记录到DEA登记簿中。
- **来源：** DEA 21 CFR 1304（联邦法规）
- **理由：** 联邦法律合规；违规可能导致执照被吊销
- **相关需求：** FR-88, FR-89, FR-90
- **易变性：** 稳定（法规性质，很少变更）
```

## 常见陷阱

### 陷阱 1：规则埋藏在需求中
**症状：** 一个功能需求写道："系统不应允许员工审批自己的报销单，因为公司政策禁止自我审批。"

**后果：** 规则（"禁止自我审批"）与实现纠缠在一起。如果政策变更，你需要在SRS中逐一查找。

**修复：** 分离处理：BR-001 陈述规则；FR-55 陈述系统对此的处理方式；FR-55 引用 BR-001。

---

### 陷阱 2：规则声明不明确
**症状：** "大额订单需要经理审批。"

**后果：** 什么是"大额"？$1,000？$10,000？哪个经理？开发人员只能猜测。

**修复：** 要精确："超过 $10,000 的订单需要部门VP或更高级别人员的审批，在订单提交给供应商之前必须在系统中记录审批。"

---

### 陷阱 3：规则冲突
**症状：** BR-003 规定"超过 $100 的订单免运费"，而 BR-015 规定"危险材料始终收取 $25 运费附加费"。

**后果：** 当有人订购 $150 的危险材料时会怎样？在上线之前没人知道。

**修复：** 对规则进行两两审查以发现冲突。记录优先级："对于危险材料，BR-015 优先于 BR-003。"

---

### 陷阱 4：不追踪易变性
**症状：** 所有规则都被视为永久性的。

**后果：** 法规规则每年变更，但没有人进行审查。系统不再合规。

**修复：** 为每条规则标记易变性（稳定 / 每年 / 频繁），并相应地安排审查计划。
