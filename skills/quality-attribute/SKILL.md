## 目的
引导需求工程师识别、优先排序和规格化质量属性（非功能需求），设定可度量的目标。使用 Planguage 标记法进行精确规格说明，并使用权衡矩阵解决竞争属性之间的冲突。

这不是一份可以直接复制到 SRS 中的通用非功能需求清单。这是一个发现*你的*系统中*哪些*质量属性重要，并将它们精确到足以测试的流程。

## 关键概念

### 质量属性分类

**外部质量属性**（用户可见）：
| 属性 | 定义 |
|-----------|-----------|
| 可用性（Availability） | 系统可运行和可访问的时间百分比 |
| 可安装性（Installability） | 在目标环境中安装系统的难易程度 |
| 完整性（Integrity） | 防止未授权的数据访问或损坏 |
| 互操作性（Interoperability） | 与其他系统交换数据的能力 |
| 性能（Performance） | 负载下的响应时间、吞吐量和资源利用率 |
| 可靠性（Reliability） | 在指定时间段内不发生故障的能力 |
| 鲁棒性（Robustness） | 优雅地处理无效输入、错误和意外情况的能力 |
| 安全性（Safety） | 避免对人员或环境造成伤害的状态的能力 |
| 信息安全性（Security） | 抵抗未授权访问、数据泄露和恶意攻击的能力 |
| 易用性（Usability） | 学习难易度、使用效率、可记忆性、错误频率、满意度 |

**内部质量属性**（开发者/维护者可见）：
| 属性 | 定义 |
|-----------|-----------|
| 效率（Efficiency） | 最小化系统资源（CPU、内存、存储、带宽）的使用 |
| 可修改性（Modifiability） | 修改系统以满足新需求的难易程度 |
| 可移植性（Portability） | 迁移到新环境的难易程度 |
| 可复用性（Reusability） | 组件可在其他系统中使用 |
| 可扩展性（Scalability） | 处理用户、数据或事务增长的能力 |
| 可验证性（Verifiability） | 测试和验证系统的难易程度 |

### Planguage 标记法
Tom Gilb 的 Planguage 提供精确的规格说明：

| 标签 | 含义 | 示例 |
|-----|---------|---------|
| **Tag（标签）** | 质量属性的名称 | 响应时间 |
| **Ambition（愿景）** | 定性目标描述 | 足够快，用户不会感知到延迟 |
| **Scale（标度）** | 度量单位 | 从用户操作到系统响应的秒数 |
| **Meter（度量方法）** | 如何度量 | 模拟负载下的自动化测试工具 |
| **Goal（目标）** | 现实可行的目标 | 第 95 百分位响应时间 <= 2 秒 |
| **Stretch（拉伸目标）** | 理想目标（超越目标） | 第 95 百分位响应时间 <= 1 秒 |
| **Wish（期望）** | 期望值（不承诺） | 第 95 百分位响应时间 <= 0.5 秒 |
| **Fail（失败阈值）** | 不可接受的阈值 | 第 95 百分位响应时间 > 5 秒 |
| **Past（基线）** | 当前基线 | 第 95 百分位响应时间 = 4.2 秒 |

### 质量属性权衡矩阵
当属性冲突时，明确权衡关系：

|              | 性能 | 安全性 | 易用性 | 可用性 |
|--------------|-------------|----------|-----------|-------------|
| 性能  | --          | 性能 > 安全性？ | 性能 > 易用性？ | 性能 > 可用性？ |
| 安全性     |             | --       | 安全性 > 易用性？ | 安全性 > 可用性？ |
| 易用性    |             |          | --        | 易用性 > 可用性？ |
| 可用性 |             |          |           | --          |

对于每一对属性，利益相关者决定冲突时哪个属性胜出。记录决策及其理由。

### 五步质量属性流程

1. **从广泛分类开始** -- 展示完整列表；不要孤立地定义属性
2. **缩减列表** -- 识别哪些属性对这个系统真正重要
3. **优先排序** -- 按重要性对剩余属性进行排序
4. **获取期望** -- 对于每个优先属性，了解利益相关者的期望
5. **编写 SMART 需求** -- 使用 Planguage 编写可度量的需求

### 反模式
- **"能力"堆砌** -- 不经分析就将 20 个通用质量属性复制粘贴到 SRS 中
- **一厢情愿** -- 对不需要（或负担不起）的系统要求"99.999% 可用性"
- **不可度量的非功能需求** -- "系统应当用户友好"（这意味着什么？如何测试？）

## 应用

使用 `template.md` 作为填写结构。

### 步骤 1：展示分类

向利益相关者展示外部和内部质量属性的完整列表。提问：
- "这些属性中哪些对本系统重要？"
- "如果搞错了，哪些属性可能带来风险？"
- "竞争对手在哪些属性上做得比我们好？"

### 步骤 2：缩减列表

从完整分类中选择 4-8 个真正重要的属性。并非每个系统都需要所有属性：
- 医疗设备需要安全性（Safety）和可靠性（Reliability）
- 电商网站需要性能（Performance）和可用性（Availability）
- 内部工具需要易用性（Usability）和可修改性（Modifiability）

### 步骤 3：优先排序

对选定的属性进行排序。使用两两比较法：
"如果性能和安全性冲突，哪个胜出？"

记录在权衡矩阵中。

### 步骤 4：获取期望

对于每个优先属性，访谈利益相关者：
- "'足够快'对你来说意味着什么？给我一个数字。"
- "每月可接受多少停机时间？"
- "如果系统宕机 1 小时会对业务产生什么影响？1 天呢？"
- "该属性当前的基线是多少？"

### 步骤 5：使用 Planguage 规格化

对于每个属性，编写 Planguage 规格说明：

```markdown
### QA-001: 搜索响应时间

- **Tag:** 响应时间（搜索操作）
- **Ambition:** 搜索结果显示足够快，实验室技术人员
  不会打断思路
- **Scale:** 从提交搜索查询到完整结果显示的秒数
- **Meter:** 50 个并发用户、50,000 条化学品记录的自动化
  负载测试，在第 95 百分位处测量
- **Past:** 4.2 秒（当前基于电子表格的查找）
- **Fail:** > 5 秒（技术人员将恢复手动查找）
- **Goal:** <= 2 秒
- **Stretch:** <= 1 秒
- **Wish:** <= 0.5 秒（即时感）
- **Source:** 实验室技术人员用户类（Maria Santos），可用性研讨会
- **Priority:** 高
- **Traces to:** BO-1（减少报告时间）
```

### 步骤 6：验证

- [ ] 每个质量属性都有可度量的标度和度量方法
- [ ] 定义了目标（Goal）和失败（Fail）阈值（最重要的边界）
- [ ] 权衡决策已记录并获得利益相关者签字确认
- [ ] 规格说明在预算和技术约束下是现实可行的
- [ ] 每条规格说明都可追溯到业务目标

```markdown
### 质量属性权衡矩阵（ChemTrack）

|              | 性能 | 安全性 | 易用性 | 可用性 |
|--------------|-------------|----------|-----------|-------------|
| 性能  | --          | 安全性胜出 | 性能胜出 | 可用性胜出  |
| 安全性     | 安全性胜出    | --       | 安全性胜出  | 安全性胜出    |
| 易用性    | 性能胜出   | 安全性胜出 | --        | 可用性胜出  |
| 可用性 | 可用性胜出  | 安全性胜出 | 可用性胜出| --          |

**优先级顺序：** 安全性 > 可用性 > 性能 > 易用性
**理由：** 化学品安全数据必须安全（法规要求）。系统在实验室
开放时间必须可用（安全影响）。速度对日常使用很重要。
易用性重要但次于以上三个属性。
```

## 常见陷阱

### 陷阱 1："系统应当快速"
**症状：** 没有标度、度量方法或目标的模糊质量属性。

**后果：** 没人知道需求何时满足。性能测试没有通过/失败标准。

**修复方法：** 使用 Planguage：定义标度（秒）、度量方法（如何度量）和目标（目标数值）。

---

### 陷阱 2：不切实际的目标
**症状：** "99.999% 可用性"（五个九 = 每年 5.26 分钟停机时间）。

**后果：** 五个九的可用性成本比三个九高出几个数量级。预算不支持。

**修复方法：** 始终将目标与成本分析配对。问："每小时停机的业务成本是多少？"然后反推以证明投资的合理性。

---

### 陷阱 3：缺少权衡讨论
**症状：** 所有质量属性都标记为"高优先级"。

**后果：** 当它们不可避免地发生冲突时（安全性增加登录摩擦，降低易用性），没有决策框架。

**修复方法：** 使用矩阵强制进行两两权衡决策。每一对属性都必须有记录在案的胜出者。

---

### 陷阱 4：质量属性作为事后补充
**症状：** 质量属性在所有功能需求编写完成后，才作为事后补充添加到 SRS 中。

**后果：** 仅由功能需求驱动的架构决策可能与质量属性目标不兼容，导致昂贵的返工。

**修复方法：** 在愿景和范围阶段就识别质量属性。它们影响架构，应在详细设计之前确定。
