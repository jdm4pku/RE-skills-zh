## 目的
系统化地从现有来源（过去的项目、需求模式目录、产品线核心资产和组织标准）中识别、评估和应用可复用需求。使用本技能可以避免为通用功能重复发明需求，并提高相关系统之间的一致性。

这不是复制一份旧的 SRS 然后更改项目名称。这是关于战略性的、经过评估的复用，需要明确决定哪些原样复用、哪些需要改编、哪些需要重新编写。

## 关键概念

### 需求复用的三个维度

每个复用决策涉及三个独立的维度：

| 维度 | 选项 | 描述 |
|-----------|---------|-------------|
| **范围（Extent）** | 部分 / 全部 | 复用选定的需求或整个规格说明 |
| **修改（Modification）** | 原样 / 改编 | 完全按原文使用或针对新上下文进行修改 |
| **机制（Mechanism）** | 复制 / 引用 | 复制到新项目中或指向共享来源 |

**组合示例：**
- 全部 / 原样 / 引用 -- 产品线核心需求在所有产品间共享
- 部分 / 改编 / 复制 -- 从过去项目中选取需求，针对新上下文进行修改
- 部分 / 原样 / 复制 -- 将标准安全需求复制到每个项目的 SRS 中

### 需求模式（Withall）

需求模式是针对常见需求类型的可复用模板。每个模式包括：
- **模式名称** -- 所覆盖的内容（例如"审计跟踪（Audit Trail）"）
- **基本细节** -- 带参数的核心需求声明
- **扩展细节** -- 针对更复杂需要的可选扩展
- **注意事项** -- 需要做出的上下文特定决策

常见需求模式：

| 模式 | 适用场景 | 示例参数 |
|---------|-------------|-------------------|
| **审计跟踪（Audit Trail）** | 系统必须记录谁在何时做了什么 | 保留期限、详细程度 |
| **授权（Authorization）** | 访问必须基于角色控制 | 角色层级、权限粒度 |
| **归档（Archive）** | 数据必须保留然后移除 | 归档期限、检索要求 |
| **通知（Notification）** | 用户必须收到事件提醒 | 渠道（邮件/短信）、时间、升级机制 |
| **过期（Expiry）** | 项目具有时间限制的有效性 | 预警期限、过期操作 |
| **计算（Calculation）** | 系统执行领域特定的计算 | 公式、精度、舍入规则 |

### 复用场景

**产品线复用：** 组织构建多个相关产品（例如面向大学的 ChemTrack、面向制药企业的 ChemTrack、面向政府的 ChemTrack）。核心需求共享；产品特定需求在其之上叠加。

**重建复用：** 替换遗留系统。现有系统的行为是需求的主要来源。复用"做什么"（what），同时重新设计"怎么做"（how）。

**类似项目复用：** 构建一个与过去项目相似的新系统（例如三年前构建过一个库存管理系统，现在要构建新的）。有选择性地复用适用的需求。

### 为什么有效
- **减少需求获取工作量** -- 认证、审计跟踪和通知等通用需求不需要每次都从头获取
- **提高一致性** -- 复用的需求携带了过去项目的经验教训和修正
- **加快评审** -- 评审人员已经熟悉复用的需求
- **模式词汇** -- 需求模式为团队提供了描述通用功能的共同语言

### 反模式
- **NIH 综合征（Not Invented Here，非此处发明）** -- 因为"我们的项目不同"而拒绝可复用需求。每个项目在某些方面是独特的，但认证、审计日志和错误处理在各个领域惊人地相似。
- **NAH 综合征（Not Applicable Here，不适用于此）** -- 盲目假设过去的需求适用而不评估适配性。对大学实验室正确的需求对制药设施未必正确。
- **复制-粘贴-遗忘** -- 复制过去 SRS 的章节而不审查每条需求的适用性。过时或不适用的需求会污染新的规格说明。
- **无目录维护** -- 构建一次复用目录后再也不用后续项目的修正和改进来更新它。

## 应用

使用 `template.md` 作为填写结构。

### 步骤 1：识别复用来源

调查可用的可复用需求来源：

1. **过去项目的 SRS 文档** -- 组织构建过的类似系统
2. **需求模式目录** -- Withall 的模式、组织模式库
3. **产品线核心资产** -- 如果组织有产品线架构
4. **法规标准** -- 跨项目适用的合规要求
5. **组织标准** -- 公司范围内的安全性、可访问性等要求

对每个来源，记录：
- 来源名称和位置
- 与当前项目的领域相似度（高 / 中 / 低）
- 来源的质量（是否经过评审？测试？维护？）

### 步骤 2：筛选复用候选

对每个来源，识别可能适用于当前项目的需求：

**高置信度复用候选**（大多数系统通用）：
- 认证（Authentication）和授权（Authorization）
- 审计跟踪和日志
- 错误处理和恢复
- 数据备份和归档
- 通知和告警
- 报表生成框架

**中置信度候选**（取决于领域相似度）：
- 领域特定的业务规则
- 工作流和审批流程
- 数据验证规则
- 集成接口

**低置信度候选**（需要仔细评估）：
- 领域特定的计算
- UI 特定的需求
- 性能目标（依赖上下文）

### 步骤 3：评估每个候选

对每个复用候选，在三个维度上做出决策：

1. **适用性：** 该需求是否适用于新系统？
   - 是，直接适用
   - 是，需要修改
   - 否，不适用（丢弃）

2. **所需修改：** 如果适用，需要什么改变？
   - 无（原样复用）
   - 参数更改（例如保留期限：5 年 -> 7 年）
   - 结构性更改（例如添加额外条件）
   - 大幅重写（可能不值得"复用"）

3. **机制：** 如何复用？
   - 引用（指向共享目录）-- 最适合组织标准
   - 复制（复制到项目 SRS 中）-- 最适合改编后的需求

### 步骤 4：改编和集成

对每条复用的需求：
- 在当前项目的编号方案中分配新的需求 ID
- 在可追溯性矩阵中标记为复用（链接到来源）
- 更新任何项目特定的参数
- 审查与新 SRS 中其他需求的一致性
- 标记从来源继承的、需要验证的假设

### 步骤 5：构建复用目录

项目结束后，为组织复用目录做出贡献：
- 添加具有复用潜力的新编写需求
- 用本项目中发现的修正来更新现有目录条目
- 按领域、模式类型和质量等级标记需求

## 示例

参见 `examples/sample.md` 获取完整的复用评估示例。

简要示例摘录：

```markdown
### 复用候选：审计跟踪（来自 LabManager v2 SRS）

- **来源：** LabManager v2，FR-090 到 FR-095
- **适用性：** 直接适用 -- ChemTrack 需要相同的
  审计跟踪功能
- **修改：** 仅参数更改 -- 保留期限从
  3 年改为 7 年（化学品记录的法规要求）
- **机制：** 复制（不同的保留参数）
- **复用为：**
  - CT.AUDIT.1（来自 FR-090）："系统应记录化学品记录上的所有
    创建、更新和删除操作，包括时间戳、用户 ID
    和修改前/后的值。" -- 原样
  - CT.AUDIT.2（来自 FR-091）："系统应自创建之日起
    保留审计记录 7 年。" -- 已改编（原为 3 年）
```

## 常见陷阱

### 陷阱 1：不经评估就复用
**症状：** 从过去项目中复制整个 SRS 章节，只对项目名称进行查找替换。

**后果：** 不适用于新上下文的需求、过时的业务规则和不适用的约束充斥 SRS。评审人员浏览"复用"的章节时会因为假设它们是正确的而一带而过。

**修正：** 针对三个维度（范围、修改、机制）逐条评估每个复用的需求。

---

### 陷阱 2：没有到来源的可追溯性
**症状：** 复用的需求没有链接到其来源。

**后果：** 当在复用的需求中发现缺陷时，无法知道哪些其他项目复用了同一条有缺陷的需求。

**修正：** 维护复用可追溯性链接：每条复用的需求指向其在目录或来源项目中的来源。

---

### 陷阱 3：忽视上下文差异
**症状：** 将小型部门系统的需求复用到企业系统中，而不考虑规模因素。

**后果：** 适用于 20 个用户的性能需求、并发处理和授权模型在 2,000 个用户时会失败。

**修正：** 在复用之前明确评估上下文差异（规模、监管环境、用户群体、集成环境）。

---

### 陷阱 4：不投资建设目录
**症状：** 组织反复构建类似系统，但每个团队都从零开始编写需求。

**后果：** 每个项目重复发明相同的需求，带有相同的遗漏和相同的错误。

**修正：** 投资建设共享复用目录。从小处着手 -- 将最常需要的 10 组需求编入目录（认证、审计、通知等）。
