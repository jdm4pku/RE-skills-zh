# SRS 文档示例

## 示例：ChemTrack SRS 摘录

```markdown
# 软件需求规格说明书：ChemTrack

**版本：** 1.2
**日期：** 2025-04-01
**作者：** Sarah Chen，高级业务分析师
**状态：** 已基线化

---

## 1. 引言

### 1.1 目的
本 SRS 记录了 ChemTrack 的功能需求和非功能需求，ChemTrack 是一个面向
大学实验室的化学品库存管理系统。目标受众为开发团队、QA 团队
和项目干系人。

### 1.2 文档约定
- 需求标识遵循以下模式：CT.[FEATURE].[FUNCTION].[Number]
- 优先级：高（发布必须包含）、中（重要但可推迟）、
  低（锦上添花）
- "应（Shall）"表示强制性需求

### 1.3 项目范围
ChemTrack 管理大学实验室的化学品库存，包括
编目、过期跟踪和法规合规性报告。
完整范围定义参见愿景与范围文档 v1.0。

---

## 3. 系统特性

### 3.1 化学品目录

#### 3.1.1 描述
化学品目录允许实验室技术人员搜索、查看、添加和
编辑化学品记录。该特性直接支持 BO-1（减少
报告时间）和 BO-2（消除过期化学品）。优先级：高。

#### 3.1.2 功能需求

**CT.CATALOG.SEARCH.1：** 系统应允许用户通过以下任意
组合搜索化学品：化学品名称（部分匹配）、
CAS 编号（精确匹配）、存放位置和过期日期范围。
- 理由：技术人员日常操作需要灵活的查找功能
- 来源：实验室技术人员用户类别（Maria Santos）
- 优先级：高
- 业务规则：无

**CT.CATALOG.SEARCH.2：** 当搜索返回结果时，系统应
按化学品名称字母顺序排序显示，显示名称、
CAS 编号、数量、存放位置和距过期天数。
- 理由：一致的显示有助于快速识别
- 来源：2025-02 可用性研讨会反馈
- 优先级：高

**CT.CATALOG.SEARCH.3：** 对于包含最多 50,000 条化学品记录的
目录，系统应在 2 秒内返回搜索结果。
- 理由：技术人员每天搜索 20-30 次；搜索缓慢
  会干扰工作流程
- 来源：性能需求研讨会
- 优先级：高

**CT.CATALOG.ADD.1：** 当用户提交新的化学品条目时，
系统应验证 CAS 编号格式（NNN-NN-N 模式的数字和连字符），
然后才接受该记录。
- 理由：无效的 CAS 编号会导致法规报告错误
- 来源：EHS 合规官员（Tom Rivera）
- 优先级：高
- 业务规则：BR-008

**CT.CATALOG.ADD.2：** 如果用户输入的 CAS 编号在库存中
已存在，系统应显示现有记录并提示"是否更新现有数量？
（是/否）"，而不是创建重复条目。
- 理由：重复记录会导致库存计数错误
- 来源：实验室技术人员用户类别
- 优先级：高

### 3.2 过期提醒

#### 3.2.1 描述
当化学品接近过期日期时的自动通知。
支持 BO-2（消除过期化学品）和 BO-4（减少安全
事故）。优先级：高。

#### 3.2.2 功能需求

**CT.ALERT.EXPIRY.1：** 当化学品距过期还有 30 天时，
系统应向负责的实验室技术人员发送电子邮件提醒。
- 优先级：高
- 业务规则：BR-011

**CT.ALERT.EXPIRY.2：** 当化学品距过期还有 7 天时，
系统应发送第二封电子邮件提醒，主题行标记为"紧急"。
- 优先级：高

**CT.ALERT.EXPIRY.3：** 当化学品超过过期日期期间，
系统应在该化学品记录上显示红色"已过期"横幅，
并阻止将其分配给任何新实验。
- 优先级：高
- 业务规则：BR-012

---

## 6. 质量属性

### 6.1 性能
**CT.PERF.1：** 在正常负载（最多 50 个并发用户）下，
系统应在 3 秒内显示任何单个页面。

**CT.PERF.2：** 对于最多 50,000 条记录的库存，
系统应在 30 秒内生成季度 EPA 合规报告。

### 6.2 可用性
**CT.AVAIL.1：** 系统应在计划运行时间（周一至周五，
7:00-22:00）的 99.5% 时间内可用，不包括提前至少
48 小时通知的计划维护窗口。

### 6.3 安全性
**CT.SEC.1：** 系统应通过大学的
Active Directory 单点登录验证用户身份。

**CT.SEC.2：** 系统应记录所有库存修改（添加、
编辑、删除），包含用户 ID、时间戳和修改前后的值，
并按法规要求保留这些日志 7 年。
```

**为什么这样做是好的：**
- 每条需求都有唯一的、持久的标识
- 需求一致使用"应（shall）"
- 每条需求都是单一的、可测试的语句
- 包含理由和来源以支持追溯
- 业务规则通过 ID 引用，而非重新陈述
- 质量属性有量化的目标
- 使用了 EARS 模式（事件驱动型："当...时"；状态驱动型："在...期间"）
