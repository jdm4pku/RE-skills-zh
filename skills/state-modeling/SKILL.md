## 目的
使用状态转换图（STD, State-Transition Diagram）和状态表来建模领域对象的生命周期。当对象在响应事件时经历不同状态，且必须防止无效转换时使用此技能。状态建模能系统性地暴露遗漏的需求。

这不是流程图——它建模的是*单个对象在其生命周期中的状态*，而不是用户执行的步骤。

## 关键概念

### 状态转换图元素

| 元素 | 表示方式 | 含义 |
|------|---------|------|
| 状态（State） | 圆角矩形 | 对象可以处于的一种条件 |
| 转换（Transition） | 状态之间的箭头 | 从一种状态到另一种状态的移动 |
| 事件/触发器（Event/Trigger） | 箭头上的标签 | 引发转换的原因 |
| 守卫条件（Guard） | 箭头上的 [条件] | 转换发生所必须满足的条件 |
| 动作（Action） | 箭头上的 /动作 | 转换过程中执行的操作 |
| 初始状态（Initial State） | 实心圆 | 对象的起始位置 |
| 终止状态（Final State） | 靶心圆 | 对象的终结位置 |

### 状态表（状态转换图的补充）
状态表是一个系统性覆盖每个状态-事件组合的矩阵：

| 状态 \ 事件 | 事件 A | 事件 B | 事件 C |
|------------|--------|--------|--------|
| 状态 1 | -> 状态 2 / 动作 | --（不可能） | -> 状态 3 / 动作 |
| 状态 2 | 错误 | -> 状态 3 / 动作 | -> 状态 1 / 动作 |
| 状态 3 | -> 状态 1 / 动作 | 错误 | --（无变化） |

**单元格取值：**
- `-> 状态 X / 动作` -- 带动作的有效转换
- `--（不可能）` -- 此事件在此状态下不可能发生（设计如此）
- `错误` -- 此事件不应发生；系统必须作为错误处理
- `--（无变化）` -- 事件发生但对象保持当前状态

**状态表的威力：** 每个空单元格都是一个潜在的遗漏需求。填满每一个单元格。

### 何时使用状态建模
状态建模在以下情况下有价值：
- 对象有 3 个或更多不同的状态
- 状态之间的转换受业务规则控制
- 无效转换必须被阻止（而不仅仅是忽略）
- 生命周期涉及多个参与者触发转换
- 法规合规性要求跟踪状态历史

### 反模式
- **缺失状态** -- 未建模终止状态（已删除、已过期、已归档）
- **缺失转换** -- 只建模正常路径；忽略错误和回滚转换
- **混淆状态与状态值** -- UI 中的"状态"字段与状态模型不同。模型应捕获所有可能的值、转换和规则。

## 应用

### 步骤 1：识别对象

选择一个生命周期涉及多种状态的领域对象：
- 订单、工单、账户、化学品、处方、请求、文档等。

### 步骤 2：列出所有状态

列举对象可能处于的每种状态。包括：
- 初始状态（对象如何进入系统）
- 正常状态（预期的生命周期）
- 异常状态（错误、暂停、搁置）
- 终止状态（已完成、已删除、已过期、已归档）

### 步骤 3：列出所有事件

列举可能影响对象状态的每个事件：
- 用户操作（提交、批准、拒绝、取消）
- 系统事件（定时器到期、阈值达到）
- 外部事件（收到付款、API 响应）

### 步骤 4：构建状态表

创建以状态为行、事件为列的矩阵。对于每个单元格：
1. 此事件是否可能在此状态下发生？
2. 如果是，对象将转换到什么状态？
3. 转换过程中执行什么动作？
4. 适用什么守卫条件？

**填满每一个单元格。** 空单元格是等待发生的缺陷。

### 步骤 5：绘制状态转换图

将状态表转换为可视化图表：
- 将状态绘制为圆角矩形
- 将转换绘制为带标签的箭头：`事件 [守卫条件] / 动作`
- 标记初始状态和终止状态
- 验证图表与状态表一致

### 步骤 6：导出需求

对于每个转换：
```
当 [事件] 发生且 [对象] 处于 [状态] 时，
系统应 [动作] 并将 [对象] 状态设置为 [新状态]。
```

对于每个错误单元格：
```
如果 [事件] 在 [对象] 处于 [状态] 时发生，
系统应拒绝该操作并显示"[错误消息]"。
```

### 步骤 7：验证

- [ ] 每个状态至少有一个入向转换和一个出向转换（初始状态和终止状态除外）
- [ ] 每个事件在每个状态下都有处理方式（状态表中无空单元格）
- [ ] 终止状态没有出向转换
- [ ] 所有守卫条件都有精确定义
- [ ] 已规定状态历史跟踪需求（如果审计需要）

简要示例：

```markdown
## 化学品记录状态

状态：活跃、即将过期、已过期、已处置

| 状态 \ 事件 | 30 天预警触发 | 过期日期已过 | 技术员处置 | 技术员续期 |
|------------|-------------|------------|-----------|-----------|
| 活跃 | -> 即将过期 / 发送预警 | -> 已过期 / 禁止使用 | -> 已处置 / 记录处置 | 错误（未临近过期） |
| 即将过期 | --（已预警） | -> 已过期 / 禁止使用 | -> 已处置 / 记录处置 | -> 活跃 / 更新日期 |
| 已过期 | --（已过期） | --（已经过期） | -> 已处置 / 记录处置 | 错误（必须先处置） |
| 已处置 | 错误 | 错误 | 错误（已处置） | 错误 |
```

## 常见陷阱

### 陷阱 1：状态表中的空单元格
**症状：** 分析过程中多个状态-事件组合被留空。

**后果：** 当这些组合在生产环境中发生时，系统行为不可预测。

**修正：** 填满每一个单元格。如果该组合不应发生，标记为"错误"并规定错误处理方式。

---

### 陷阱 2：没有终止状态
**症状：** 状态模型显示了活跃状态，但从未定义对象生命周期如何结束。

**后果：** 对象在系统中永远累积，无法清理或归档。

**修正：** 添加终止状态（已删除、已归档、已过期、已完成），并定义什么触发它们以及需要什么清理操作。

---

### 陷阱 3：建模流程而非对象状态
**症状：** 图表显示的是用户步骤（登录、搜索、选择、提交）而非对象状态。

**后果：** 这是活动图，不是状态模型。它无法捕获对象生命周期需求。

**修正：** 关注*对象*变成什么，而非*用户*做什么。"订单：待处理 -> 已批准 -> 已发货"（对象状态），而非"提交 -> 审核 -> 发货"（用户操作）。
