## 目的
建立和维护需求管理基础设施——基线化（Baselining）、版本控制、属性跟踪和状态监控。这是在整个项目生命周期中保持需求有序的运营支柱。

这不是关于开发需求的技能，而是关于在需求开发完成后对其进行管理——跟踪状态、控制变更、度量进度，以及维护需求工作的投入成果。

## 核心概念

### 需求管理活动

| 活动 | 作用 | 时机 |
|----------|-------------|------|
| **基线化（Baselining）** | 将已评审的一组需求冻结为约定的起点 | 验证之后 |
| **版本控制（Version Control）** | 跟踪单条需求随时间的变更 | 持续进行 |
| **属性跟踪（Attribute Tracking）** | 维护每条需求的元数据（状态、优先级、来源等） | 持续进行 |
| **状态监控（Status Monitoring）** | 跟踪需求在生命周期各状态中的流转 | 每个迭代/里程碑 |
| **变更控制（Change Control）** | 评估并批准/拒绝提出的变更 | 当变更出现时 |
| **可追溯性（Traceability）** | 维护需求与其他制品之间的链接 | 持续进行 |

### 需求属性
每条需求应携带以下属性：

| 属性 | 用途 | 示例 |
|-----------|---------|---------|
| **唯一标识（Unique ID）** | 持久标识 | CT.ALERT.EXPIRY.1 |
| **版本（Version）** | 跟踪修订 | 1.2 |
| **状态（Status）** | 当前生命周期状态 | Approved |
| **优先级（Priority）** | 重要性排序 | High |
| **来源（Source）** | 谁提出的 | Maria Santos，实验室技术员 |
| **理由（Rationale）** | 为什么存在 | 防止过期化学品引发安全事故 |
| **业务目标（Business Objective）** | 支持哪个业务目标 | BO-2 |
| **复杂度（Complexity）** | 估计难度 | Medium |
| **稳定性（Stability）** | 变更可能性 | Stable |
| **目标版本（Release）** | 目标发布版本 | Release 1.0 |
| **创建日期（Date Created）** | 首次记录时间 | 2025-03-25 |
| **修改日期（Date Modified）** | 最后修改日期 | 2025-04-14 |

### 需求状态生命周期

```
Proposed -> In Progress -> Drafted -> Approved -> Implemented -> Verified
（已提出）  （进行中）    （已起草）  （已批准）   （已实现）     （已验证）
                                         |
                                         +-> Deferred（已延期）
                                         |
                                         +-> Deleted（已删除）
                                         |
                                         +-> Rejected（已拒绝）
```

| 状态 | 含义 | 谁来变更 |
|--------|---------|---------------|
| **Proposed（已提出）** | 已识别但未分析 | BA 或利益相关方 |
| **In Progress（进行中）** | 正在细化/编写 | BA |
| **Drafted（已起草）** | 已编写但未评审 | BA |
| **Approved（已批准）** | 已评审，纳入基线 | CCB 或产品负责人 |
| **Implemented（已实现）** | 已编码并完成单元测试 | 开发人员 |
| **Verified（已验证）** | 通过验收测试 | QA |
| **Deferred（已延期）** | 已批准但推迟到未来版本 | CCB |
| **Deleted（已删除）** | 从基线中移除并记录原因 | CCB |
| **Rejected（已拒绝）** | 经评估后被否决 | CCB |

### 需求燃尽图（Requirements Burndown Chart）
跟踪各状态中需求数量随时间的变化：

```
Sprint 1:  [=====Proposed=====][Drafted][Approved]
Sprint 2:  [===Proposed===][==Drafted==][===Approved===]
Sprint 3:  [=P=][=D=][=====Approved=====][==Implemented==]
Sprint 4:  [P][D][===Approved===][=====Implemented=====][==Verified==]
Sprint 5:  [D][Approved][===Implemented===][========Verified========]
```

该图表显示需求是否以可持续的速度被消化，以及是否存在瓶颈（例如，许多需求已实现但很少被验证 = 测试瓶颈）。

### 反模式
- **无基线** -- 需求从未被正式确认。变更不可见。
- **状态未更新** -- 需求已实现但状态仍显示"已批准"。没人知道真实进度。
- **ID 复用** -- 已删除需求的 ID 被重新分配给新需求。可追溯性被破坏。
- **属性过载** -- 每条需求 30 个属性。没人维护它们。应从 8-10 个核心属性开始。

## 应用

### 阶段 1：基础设施建立（2-4 小时，一次性）

**1.1 选择需求管理工具**

按项目规模选择：

| 项目规模 | 工具 | 备注 |
|-------------|------|-------|
| 小型（< 50 条需求） | 电子表格（Excel/Sheets） | 简单、易用、有局限 |
| 中型（50-500 条需求） | 专用 RM 工具或带自定义字段的问题跟踪器 | Jira、Azure DevOps、DOORS |
| 大型（500+ 条需求） | 完整 RM 工具 | IBM DOORS、Jama、Helix RM |

**1.2 定义属性模式**
选择要跟踪的属性（从核心属性开始，后续按需添加）：

**核心（必须跟踪）：**
- 唯一标识（Unique ID）、状态（Status）、优先级（Priority）、来源（Source）、版本（Version）

**推荐（中型及以上项目添加）：**
- 业务目标（Business Objective）、复杂度（Complexity）、目标版本（Release）、创建日期（Date Created）、修改日期（Date Modified）

**可选（按需添加）：**
- 稳定性（Stability）、理由（Rationale）、分配的开发人员（Assigned Developer）、测试用例 ID（Test Case IDs）

**1.3 定义标识命名规范**
选择需求 ID 方案：
- 顺序编号：FR-001、FR-002、FR-003（简单项目）
- 层次化文本：PRODUCT.FEATURE.FUNCTION.N（大型项目）
- 规则：ID 一旦分配后永不重用

**1.4 定义状态工作流**
将状态映射到转换和角色：
- 谁可以将状态从 Proposed 变更为 In Progress？（BA）
- 谁可以将状态从 Drafted 变更为 Approved？（CCB）
- 谁可以将状态从 Implemented 变更为 Verified？（QA）

**1.5 建立变更控制阈值**
定义哪些变更需要正式的变更控制，哪些 BA 可自行决定：
- 澄清说明（无行为变更）：BA 可直接更新
- 修改（行为变更）：需要变更请求 + CCB 评审
- 范围新增：需要变更请求 + CCB + 影响分析

---

### 阶段 2：基线化（1-2 小时）

在需求通过验证后（参见 `skills/requirements-validation-process/SKILL.md`）：

1. **为所有已批准的需求分配版本 1.0**
2. **记录基线日期**和参与的利益相关方
3. **锁定基线** -- 从此刻起所有变更均需通过变更控制
4. **归档基线** -- 保留基线化 SRS 的只读副本

---

### 阶段 3：持续管理（连续进行）

**3.1 状态更新**
- 在每个迭代（Sprint）/迭代中：
  - 根据开发进度更新需求状态
  - 跟踪每个状态中有多少需求
  - 更新燃尽图

**3.2 变更控制**
- 通过 `skills/change-control-advisor/SKILL.md` 处理变更请求
- 当变更被批准后更新需求版本
- 更新可追溯性链接

**3.3 可追溯性维护**
- 当新增需求时，将其追溯到业务目标
- 当需求被实现时，链接到测试用例
- 每月运行可追溯性分析（孤立项检测）

**3.4 进度报告**
创建每周或每迭代的状态报告：
```
需求状态报告：Sprint 4
需求总数：37
- Proposed（已提出）：0
- Drafted（已起草）：1（2.7%）
- Approved（已批准）：5（13.5%）
- Implemented（已实现）：18（48.6%）
- Verified（已验证）：12（32.4%）
- Deferred（已延期）：1（2.7%）

本迭代变更请求：
- CR-005：已批准（警报时间变更）
- CR-006：评审中（新增导出功能）

问题：
- 测试速度需要提升（18 条已实现 vs 12 条已验证）
```

**3.5 项目结束评审**
项目完成时：
- 所有需求的最终状态
- 记录已延期的需求以供未来参考
- 需求流程改进的经验教训
- 度量指标：总变更数、每个阶段发现的缺陷数、周期时间

## 常见陷阱

### 陷阱 1：先工具后流程
**症状：** 组织在定义流程之前购买了昂贵的 RM 工具。

**后果：** 工具配置随意，属性不一致，没人能正确使用。

**解决方案：** 先定义流程（状态、属性、工作流、角色），然后配置工具来支持它。一个有良好流程的电子表格胜过一个没有流程的高级工具。

---

### 陷阱 2：属性从不更新
**症状：** 需求状态数月保持"已起草"状态，因为没人更新状态字段。

**后果：** 没人知道需求的真实状态。燃尽图毫无意义。

**解决方案：** 将状态更新纳入迭代工作流。开发人员在代码提交时更新为"已实现"。QA 在测试通过时更新为"已验证"。尽可能自动化。

---

### 陷阱 3：没有版本历史
**症状：** 需求被修改了，但没有记录之前版本的内容。

**后果：** 当利益相关方问"为什么改了这个？"时，没人知道。

**解决方案：** 对每次需求变更进行版本化。记录：旧文本、新文本、变更原因、谁批准的、何时批准的。
