# 需求管理流程示例

## 示例：ChemTrack 需求管理设置

```markdown
# 需求管理计划：ChemTrack

**日期：** 2025-04-01
**RM 负责人：** Sarah Chen，BA
**工具：** Google Sheets（小型项目，37 条需求）

---

## 属性模式

| 属性 | 类型 | 必填 | 示例 |
|-----------|------|----------|---------|
| ID | 文本 | 是 | CT.ALERT.EXPIRY.1 |
| Version（版本） | 数字 | 是 | 1.2 |
| Title（标题） | 文本 | 是 | 发送 30 天到期警报 |
| Statement（描述） | 文本 | 是 | 系统应发送... |
| Status（状态） | 枚举 | 是 | Approved |
| Priority（优先级） | 枚举 | 是 | High |
| Source（来源） | 文本 | 是 | Maria Santos，实验室技术员 |
| Business Objective（业务目标） | 文本 | 是 | BO-2 |
| Release（目标版本） | 文本 | 是 | Release 1.0 |
| Business Rules（业务规则） | 文本 | 否 | BR-011 |
| Date Created（创建日期） | 日期 | 是 | 2025-03-25 |
| Date Modified（修改日期） | 日期 | 是 | 2025-04-14 |

## 标识命名规范
模式：CT.[FEATURE].[FUNCTION].[Number]
- CT = ChemTrack（产品）
- FEATURE = 主要功能区域（CATALOG、ALERT、REPORT、DISP 等）
- FUNCTION = 功能区域内的功能（SEARCH、ADD、EXPIRY、GEN 等）
- Number = 功能内的序号

规则：ID 永不重用。已删除的需求保留其 ID，状态标记为"Deleted"。

## 状态工作流

| 从 | 到 | 谁 | 触发条件 |
|------|-----|-----|---------|
| Proposed | In Progress | BA | BA 开始细化 |
| In Progress | Drafted | BA | 需求编写完成 |
| Drafted | Approved | CCB（发起人 + BA + 开发负责人） | 通过审查 |
| Approved | Implemented | 开发人员 | 代码提交 + 单元测试完成 |
| Implemented | Verified | QA 负责人 | 验收测试通过 |
| Approved | Deferred | CCB | 移至未来版本 |
| 任何状态 | Deleted | CCB | 需求移除并记录原因 |
| 任何状态 | Rejected | CCB | 变更请求被拒绝 |

## 变更控制阈值

| 变更类型 | 所需审批 | 流程 |
|-------------|------------------|---------|
| 澄清说明（无行为变更） | 仅 BA | 直接更新，递增次版本号 |
| 修改（行为变更） | CCB 评审 | 变更请求 + 影响分析 |
| 范围新增（新需求） | CCB + 影响分析 | 完整变更请求流程 |
| 紧急修复（阻塞开发） | BA + 开发负责人 | 快速通道，48 小时内 CCB 追认 |

## 基线历史

| 版本 | 日期 | 变更内容 | 批准人 |
|---------|------|---------|-------------|
| 1.0 | 2025-04-14 | 初始基线（35 条需求） | 发起人、BA、开发负责人、EHS |
| 1.1 | 2025-04-18 | 原型验证新增 2 条需求，审查修改 3 条 | CCB |
| 1.2 | 2025-05-16 | CR-005 警报时间变更 | CCB |
```

**为什么这样做有效：**
- 简单的工具（电子表格）配合清晰的流程，胜过没有流程的高级工具
- 属性模式大小合适（12 个属性，而非 30 个）
- 状态工作流有明确的转换和角色分配
- 变更控制阈值避免了对小变更的过度管控
- 燃尽图展示了真实进度并暴露了测试瓶颈
- 基线历史提供了审计追踪
