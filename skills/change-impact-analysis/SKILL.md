## 目的
指导需求工程师对提议的需求变更进行结构化的影响分析。这是变更控制的分析核心——没有它，变更决策只能凭直觉，范围蔓延将不受控制。

这不是官僚式的填表练习。这是一种系统性评估，确保每个变更决策都建立在对变更真实成本、影响范围和引入风险的充分理解之上。

## 关键概念

### 三步影响分析

Wiegers 定义了分析任何提议变更的三步流程：

1. **影响分析（Implications Analysis）** ——该变更的直接和间接后果是什么？
2. **受影响的工作产品（Affected Work Products）** ——哪些文档、设计、代码模块和测试用例需要修改？
3. **工作量估算（Effort Estimation）** ——需要多少工作量，对进度和成本有什么影响？

### 变更请求属性（18 个字段）

一个完整的变更请求记录包含：

| # | 属性 | 描述 |
|---|------|------|
| 1 | 变更请求 ID | 唯一标识符（CR-001） |
| 2 | 提交日期 | 请求提交的时间 |
| 3 | 请求者 | 提交请求的人 |
| 4 | 变更类型 | 增强、缺陷修正、约束变更、接口变更 |
| 5 | 描述 | 请求的变更内容 |
| 6 | 理由 | 为什么需要此变更 |
| 7 | 优先级 | 变更的紧迫程度（关键/高/中/低） |
| 8 | 受影响的需求 | 哪些需求被直接变更 |
| 9 | 受影响的其他工作产品 | 设计、代码、测试、用户文档、培训材料 |
| 10 | 影响 | 副作用、连锁效应、新风险 |
| 11 | 估算工作量 | 实施所需的人时或故事点 |
| 12 | 估算进度影响 | 增加到时间线的天数或冲刺数 |
| 13 | 估算成本影响 | 美元成本或预算百分比 |
| 14 | 引入的风险 | 新的技术或业务风险 |
| 15 | 依赖关系 | 此变更依赖的其他变更或功能 |
| 16 | 已考虑的替代方案 | 满足潜在需要的其他方式 |
| 17 | 状态 | 已提交、审核中、已批准、已拒绝、已推迟、已实施 |
| 18 | 决议及理由 | 最终决定和推理 |

### 影响清单

对每个提议的变更，系统性地评估：

- [ ] 此变更是否与任何现有需求冲突？
- [ ] 此变更是否影响任何质量属性（性能、安全性、可用性）？
- [ ] 此变更是否需要更改系统架构？
- [ ] 此变更是否影响与外部系统的接口？
- [ ] 此变更是否改变了已记录的业务规则？
- [ ] 此变更是否引入新的法规或合规义务？
- [ ] 此变更是否影响用户文档或培训材料？
- [ ] 此变更是否使现有测试用例失效？
- [ ] 此变更是否影响已实施和部署的需求？
- [ ] 此变更是否创建了对另一个未完成功能的依赖？

### 为什么这种方法有效
- **防止隐性成本** ——许多变更看起来很小，但具有巨大的连锁效应。三步流程在承诺变更之前将这些问题暴露出来。
- **支持知情决策** ——变更控制委员会看到的是完整的影响，而不仅仅是请求者乐观的描述。
- **创建可追溯性** ——18 个属性为审计和回顾提供了完整的记录。
- **支持比较** ——当多个变更竞争有限的产能时，影响分析提供了比较的基础。

### 反模式
- **橡皮图章式 CCB** ——变更控制委员会在不审查影响分析的情况下批准一切。变更积累的速度超过了处理能力。
- **过度分析** ——花 8 小时分析一个 2 小时的变更。应根据变更的规模和风险调整分析深度。
- **缺少可追溯性** ——在没有可追溯性矩阵的情况下进行影响分析。受影响的工作产品是猜测的，而不是追溯得出的。

## 应用

使用 `template.md` 获取完整的变更影响分析表单。

### 步骤 1：接收并记录变更请求

当变更请求到来时：
1. 分配唯一的 CR 标识符
2. 记录请求者、日期和描述
3. 分类变更类型（增强、缺陷、约束、接口）
4. 根据请求者的输入分配初始优先级（后续将进行验证）

对于 ChemTrack：一位实验室主任请求为化学品容器添加条码扫描功能（CR-007）。

### 步骤 2：执行影响分析

对提议的变更逐项检查影响清单：

```
变更：为化学品容器添加条码扫描（CR-007）

- 与现有需求冲突？否
- 影响质量属性？是——性能（扫描延迟）、
  可用性（新的硬件交互模式）
- 需要架构变更？是——新的硬件接口层、
  相机/扫描仪 API 集成
- 影响外部接口？是——条码扫描仪硬件 API
- 改变业务规则？否
- 新的法规义务？可能——条码格式必须符合
  GHS 标签标准
- 影响用户文档？是——新的扫描工作流
- 使现有测试用例失效？否，不影响现有测试
- 影响已部署的需求？否
- 创建新的依赖？是——依赖条码硬件采购
```

### 步骤 3：识别受影响的工作产品

使用需求可追溯性矩阵（`skills/requirements-traceability/SKILL.md`）从受影响的需求追溯到所有下游工件：

| 工作产品 | 受影响的具体项 | 变更性质 |
|---------|--------------|---------|
| SRS | FR-01（化学品录入）、NFR-03（性能） | 为手动录入添加扫描替代方案 |
| 架构 | 组件图、接口规格说明 | 添加扫描仪接口模块 |
| UI 设计 | 化学品录入界面原型 | 添加扫描按钮和反馈 UI |
| 数据库 | 无 | 无模式变更 |
| 测试计划 | 集成测试套件 | 添加条码扫描测试用例 |
| 用户手册 | 化学品录入流程章节 | 添加扫描工作流 |
| 培训 | 实验室技术员培训模块 | 添加扫描培训内容 |

### 步骤 4：估算工作量、进度和成本

将实施分解为任务：

```
CR-007 任务分解：
- 需求更新：              4 小时
- 架构更新：              8 小时
- UI 设计更新：           6 小时
- 扫描仪 API 集成：     24 小时
- 单元测试：              8 小时
- 集成测试：             12 小时
- 用户文档：              4 小时
- 培训更新：              4 小时
---------------------------------
总估算工作量：           70 小时（约 2 个开发者周）

进度影响：如果现在开始 +1 个冲刺；如果推迟到 Release 2 则 +0
成本影响：$8,400 开发费用 + $2,500 硬件费用（5 个实验室的扫描仪）
```

### 步骤 5：评估风险和替代方案

记录引入的新风险：
- 扫描仪硬件可能与所有实验室环境不兼容
- GHS 条码格式合规性增加了法规验证工作量

记录已考虑的替代方案：
- 带自动完成的手动键盘录入（当前方案）——无成本，但速度较慢
- 手机摄像头扫描——硬件成本较低但存在安全顾虑
- 推迟到 Release 2——无即时进度影响但延迟收益实现

### 步骤 6：提交给变更控制委员会

打包完整的分析并向 CCB 提交建议：
- **批准：** 收益足以抵消成本和进度影响
- **推迟：** 有价值但不紧急；安排到后续版本
- **拒绝：** 成本超过收益，或替代方案更优

对于 CR-007，建议可能是："推迟到 Release 2。手动变通方案对 Release 1 来说已经够用。硬件采购交付周期使 Release 1 中包含此功能存在风险。"

```markdown
## 变更请求 CR-007：条码扫描

**优先级：** 中
**估算工作量：** 70 小时
**进度影响：** 如果在 Release 1 中实施则 +1 个冲刺

```

## 常见陷阱

### 陷阱 1：分析瘫痪
**症状：** 每个变更请求，无论多小，都进行完整的 18 个字段分析，需要 3 天周转时间。

**后果：** 变更流程成为瓶颈。利益相关者绕过它或停止提交变更。

**修复：** 根据变更规模调整分析深度。小型变更（拼写修正、外观调整）进行轻量级审查。大型变更（新功能、架构变更）进行完整分析。在变更控制策略中定义阈值。

---

### 陷阱 2：遗漏下游影响
**症状：** 影响分析覆盖了需求和代码，但遗漏了文档、培训、测试用例或部署流程。

**后果：** 变更在代码中"完成"了，但测试套件、用户手册和培训材料不同步。

**修复：** 系统性地使用受影响工作产品清单。包括非代码工件：用户文档、培训、部署脚本、配置、帮助文本。

---

### 陷阱 3：过于乐观的工作量估算
**症状：** 工作量估算仅覆盖"快乐路径"实施——没有测试、文档或集成的时间。

**后果：** 变更实际花费的时间是估算的 2-3 倍。进度延迟或质量下降。

**修复：** 使用任务分解方法。将测试、文档和集成工作量与实施工作量分开估算。

---

### 陷阱 4：没有替代方案分析
**症状：** 影响分析仅评估所提议的变更本身，不考虑替代方法。

**后果：** CCB 批准了一个昂贵的实施方案，而一个更简单的替代方案可以满足同样的底层需求。

**修复：** 始终记录至少一个替代方案，即使是"什么都不做"。这迫使人们思考所提议的方法是否是满足需求的最佳方式。

---

### 陷阱 5：缺乏业务理由的变更请求
**症状：** 变更请求描述了应该变更什么，但没有描述为什么。

**后果：** CCB 无法评估变更是否值得，因为缺少业务论证。

**修复：** 在每个变更请求上要求填写理由字段。"为什么需要此变更？"以及"如果不做此变更会怎样？"
