## 目的
指导需求工程师选择和采纳需求开发与管理工具。使用此技能基于实际工作流需求和项目背景做出工具决策，而不是依赖供应商演示和功能清单。

这不是一份产品对比图表。工具的变化速度超过任何指南所能跟踪的。这是一个决策框架，帮助你根据实际需求评估任何工具。

## 关键概念

### RD 工具与 RM 工具

| 类别 | 目的 | 示例 | 关键能力 |
|----------|---------|---------|-----------------|
| **需求开发（RD）** | 创建和规格化需求 | 文字处理器、建模工具、原型工具、绘图工具 | 文档编写、可视化建模、UI 原型 |
| **需求管理（RM）** | 跟踪、追溯和控制需求 | 专用 RM 工具、ALM 平台 | 唯一标识、属性、可追溯性、基线、变更历史、状态跟踪 |

大多数团队两者都需要，但痛点不同。如果你的问题是"我们写不出好的需求"，RM 工具帮不了你。如果你的问题是"我们无法跟踪变更和追溯需求"，文字处理器帮不了你。

### 工具成熟度等级

| 等级 | 描述 | 典型工具 |
|-------|-------------|---------------|
| **等级 0：临时方式** | 没有一致的工具使用 | 电子邮件、走廊对话 |
| **等级 1：办公工具** | 需求存放在文档和电子表格中 | Word、Excel、Google Docs/Sheets |
| **等级 2：结构化跟踪** | 需求存放在带有 ID 和属性的结构化工具中 | Jira、Azure DevOps、带有结构化的 Notion |
| **等级 3：专用 RM** | 专门构建的 RM 工具，具备可追溯性、基线、变更控制 | DOORS、Jama、Helix RM、Modern Requirements |
| **等级 4：集成 ALM** | RM 工具与设计、测试和项目管理工具集成 | Polarion、codeBeamer、Azure DevOps 全套 |

一次跨越超过一个等级的风险很高。从等级 1 直接跳到等级 3 会跳过等级 2 所提供的组织学习过程。

### 为什么有效
- **基于上下文的选择**将工具与你的实际问题匹配，而不是与供应商的功能列表匹配
- **成熟度评估**防止过度采购（处于等级 1 的团队不需要等级 4 的工具）
- **聚焦痛点**确保工具解决真正的工作流问题
- **采纳规划**防止常见的失败模式——"买了工具，没人用"

### 反模式
- **功能清单评估** -- 基于最长的功能列表来选择工具。大多数团队使用的 RM 工具功能不到 30%。
- **供应商驱动选择** -- 让演示最好或销售团队最强的供应商胜出。演示是为了留下印象而优化的，不是为了真实工作流。
- **工具作为流程修复** -- 买工具来修复流程问题。如果你的团队现在不做可追溯性，工具不会让他们开始做。先修复流程。
- **大爆炸式迁移** -- 同时将所有项目迁移到新工具。如果出了问题，一切都会受到影响。

## 应用

### 交互式工具选择流程

**问题 1：你当前的项目/团队规模是多少？**

1. **小型** -- 1-3 人负责需求，< 200 条需求
2. **中型** -- 3-8 人，200-1000 条需求，有一些跨团队协调
3. **大型** -- 8+ 人，1000+ 条需求，多个团队，法规合规要求
4. **产品线** -- 多个相关产品共享核心需求

---

**问题 2：你当前的工具成熟度等级是？**

1. **等级 0：临时方式** -- 需求在邮件、会议记录和人们的脑子里
2. **等级 1：办公工具** -- Word 文档和 Excel 电子表格
3. **等级 2：结构化跟踪** -- Jira、Azure DevOps 或类似工具，需求作为条目
4. **等级 3+：专用 RM** -- 已经使用专用 RM 工具（寻求改进或替换）

---

**问题 3：你最主要的 2-3 个痛点是什么？**

1. **找不到需求** -- 需求分散在各种文档中，没有单一的事实来源
2. **无法跟踪变更** -- 没有变更历史，没有基线，不清楚什么时候改了什么
3. **没有可追溯性** -- 无法将需求追溯到测试、设计或业务目标
4. **协作问题** -- 多人编辑同一文档，版本冲突
5. **报告缺口** -- 无法生成状态报告、覆盖率报告或合规矩阵
6. **规模问题** -- 当前方法在需求数量增长时失效
7. **集成问题** -- 需求工具无法连接开发、测试或 CI/CD 工具

---

**问题 4：需求工程工具必须与哪些工具集成？**

1. **无需集成** -- 独立使用即可
2. **问题跟踪器** -- Jira、Azure DevOps、GitHub Issues
3. **测试管理** -- TestRail、Zephyr、qTest
4. **开发工具** -- Git、CI/CD 管道
5. **文档管理** -- SharePoint、Confluence
6. **以上多项** -- 请具体说明

---

### 推荐逻辑

**小型团队 + 等级 0-1 + 可查找性/变更跟踪痛点：**
- **推荐：** 迁移到等级 2。使用你已有的结构化工具（Jira、Azure DevOps、Notion），设置一个需求专用项目/空间。
- **为什么不选等级 3：** 专用 RM 工具的开销不合理。先学习结构化需求管理。
- **行动：** 定义一个需求条目类型，包含标准属性（ID、状态、优先级、来源）。使用 `skills/requirements-traceability/SKILL.md` 建立基本的可追溯性。

**中型团队 + 等级 1-2 + 可追溯性/报告痛点：**
- **推荐：** 评估等级 3 工具。团队已经超出电子表格的承载能力，需要可追溯性、基线和报告功能。
- **候选评估工具：** Jama Connect、Helix RM、Modern Requirements（适用于 Azure DevOps 用户）、DOORS Next（适用于大型企业）。
- **行动：** 执行下面的 7 步评估流程。

**大型团队 + 任何等级 + 合规/规模痛点：**
- **推荐：** 需要专用的等级 3 或等级 4 工具。合规文档和跨团队可追溯性需要专门构建的能力。
- **关键标准：** 法规报告、审计追踪、基线比较、基于角色的访问控制、面向外部审计员的导入/导出。
- **行动：** 执行 7 步评估流程，合规需求权重较高。

**产品线 + 任何痛点：**
- **推荐：** 等级 3-4 工具，具备明确的产品线支持（变体管理、共享核心需求与产品特定层）。
- **关键标准：** 需求重用和引用（参见 `skills/requirements-reuse/SKILL.md`）、变体配置、分支或产品特定视图。
- **行动：** 将变体管理作为必选评估标准。

**任何规模 + 等级 3+ + 采纳问题：**
- **推荐：** 不要更换工具。先解决采纳问题。
- **行动：** 参见下面的"工具采纳与文化变革"部分。

---

### 7 步工具评估流程

**步骤 1：定义工具的需求（1 天）**

为你的需求工具编写需求。包括：
- 必须具备的能力（与你的痛点关联）
- 最好具备的能力
- 集成需求
- 预算约束
- 部署模式（云 / 本地 / 混合）
- 用户数量和许可模式偏好

**步骤 2：创建候选名单（1-2 天）**

研究并确定 3-5 个候选工具。来源：
- 分析师报告（Gartner、Forrester）
- 类似组织的同行推荐
- 在线社区评价（实际用户，不是营销内容）

**步骤 3：根据必备项评估（1-2 天）**

淘汰不符合必备需求的工具。这应该将名单缩减到 2-3 个入围者。

**步骤 4：使用真实数据进行实际试用（3-5 天）**

对每个入围者：
- 导入一部分真实需求（50-100 条）
- 执行你的实际工作流：创建、评审、追溯、基线化、变更
- 让多个团队成员独立使用该工具
- 记录摩擦点和令人印象深刻的能力

**步骤 5：评估集成（1-2 天）**

测试与现有工具的实际集成：
- Jira 集成是否真的能与你的 Jira 配置一起工作？
- 能否按合规审计员需要的格式导出？
- API 是否足以满足你需要的自定义集成？

**步骤 6：总拥有成本（1 天）**

为每个入围者计算：
- 许可证费用（每用户、每年）
- 实施/迁移费用
- 培训费用
- 持续管理费用
- 集成开发费用

**步骤 7：决策和试点计划（1 天）**

选择工具。规划试点：
- 一个项目，一个团队，2-3 个月
- 在开始之前定义成功标准
- 只有在试点成功后才规划推广

### 工具采纳与文化变革

如果工具已经购买但采纳率低，问题通常不在工具本身：

**诊断采纳失败：**
- 团队是否接受了充分的培训？（不是供应商演示——而是基于团队自身工作流的实操培训）
- 工具是否适合团队的实际工作流，还是团队必须改变工作流来适应工具？
- 是否有倡导者（一位受尊重的同事，而不是管理层）为工具代言？
- 不使用工具是否有后果？（如果电子表格仍然被接受，人们就会继续使用电子表格）

**修复采纳问题：**
1. 找出未采纳者的前 3 个抱怨
2. 逐一解决（配置调整、培训或工作流调整）
3. 找到或培养内部倡导者
4. 要求在特定交付物中使用该工具（不再接受电子表格替代方案）
5. 提供持续支持（不仅仅是初始培训）

## 常见陷阱

### 陷阱 1：先工具后流程
**症状：** 组织在定义需求工程流程之前就购买了 RM 工具。

**后果：** 工具强制执行一个与团队工作方式不匹配的工作流。团队抵制或绕过工具。

**修复：** 先定义你的需求工程流程（即使是非正式的）。然后选择支持该流程的工具。参见 `skills/re-process-improvement/SKILL.md`。

---

### 陷阱 2：过度采购
**症状：** 一个 5 人团队购买了为 500 人项目设计的企业级 RM 工具。

**后果：** 过多的开销、复杂的管理、永远用不到的功能，以及难以证明合理性的价格。

**修复：** 将工具成熟度与团队成熟度匹配。处于等级 1 的小型团队应该先迁移到等级 2。

---

### 陷阱 3：忽视迁移成本
**症状：** 基于功能和许可证费用选择工具。未预算现有需求的迁移。

**后果：** 由于没人有时间将现有的 800 条需求从电子表格中迁出，导致六个月的双系统并行运行。

**修复：** 将迁移工作量、并行运行期和培训时间纳入总拥有成本。

---

### 陷阱 4：演示驱动选择
**症状：** 供应商演示最令人印象深刻的工具赢得了评估。

**后果：** 演示展示的场景你永远不会用到。工具在你的实际工作流中表现不佳。

**修复：** 始终执行步骤 4（使用真实数据进行实际试用）。你的数据、你的工作流、你的团队成员——而不是供应商精心策划的演示。
