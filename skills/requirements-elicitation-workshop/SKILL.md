## 目的
引导需求工程师规划和执行结构化的需求获取会议。将多种技术编排成会议计划，包含具体的议程、参与者角色和预期产出。

这不是单一技术的说明，而是对技术进行排序、管理参与者并将产出综合整理为需求的工作流。

## 核心概念

### 获取会议类型

| 类型 | 参与者 | 时长 | 最适用于 |
|------|--------|------|----------|
| **发现研讨会（Discovery Workshop）** | 5-10位利益相关者 | 2-4小时 | 新项目的初始需求 |
| **深度访谈（Deep-Dive Interview）** | 1-2位领域专家 | 1-2小时 | 特定领域的详细需求 |
| **观察会议（Observation Session）** | 1位观察者 + 用户 | 2-4小时 | 未文档化的工作流程、隐性知识 |
| **评审与验证（Review & Validation）** | 3-7位混合利益相关者 | 1-2小时 | 确认已草拟的需求 |

### 获取准备检查清单
在任何获取会议之前：
- [ ] 目标已定义（需要了解什么）
- [ ] 参与者已确定并确认（来自 `skills/stakeholder-analysis/SKILL.md`）
- [ ] 技术已选择（来自 `skills/elicitation-technique-selector/SKILL.md`）
- [ ] 材料已准备（议程、现有工件、问题）
- [ ] 后勤已安排（房间、工具、录音许可）
- [ ] 已审阅先前知识（现有文档、之前的会议记录）

### 获取工作流
```
准备 -> 执行 -> 记录 -> 综合整理 -> 验证
```

## 应用

### 阶段1：准备（会议前1-2小时）

**1.1 定义目标**
写一句话："在本次会议结束时，我们将得到[具体产出]。"

示例：
- "……识别出所有用户类别及其主要目标"
- "……记录当前化学品跟踪工作流程及痛点"
- "……为排名前5的用户故事指定验收标准"

**1.2 选择参与者**
根据利益相关者分析：
- 至少包含每个受影响用户类别的一位代表
- 如涉及业务规则，需包含一位领域专家
- 研讨会限制在5-10人（人数过多会降低效率）
- 始终包含一位产品负责人

**1.3 准备议程**

**发现研讨会**（3小时）：
```
00:00 - 00:15  欢迎、目标说明、基本规则
00:15 - 00:45  背景介绍（现状、问题、目标）
00:45 - 01:30  获取活动1（例如：流程走查）
01:30 - 01:45  休息
01:45 - 02:30  获取活动2（例如：需求头脑风暴）
02:30 - 02:50  优先级排序（快速MoSCoW或投点法）
02:50 - 03:00  总结、后续步骤、行动项
```

**深度访谈**（1小时）：
```
00:00 - 00:05  目标说明与建立融洽关系
00:05 - 00:15  背景问题（角色、工作流程、工具）
00:15 - 00:40  核心问题（特定主题深入探讨）
00:40 - 00:50  场景与边界情况
00:50 - 00:55  "还有什么我应该知道的吗？"（开放式）
00:55 - 01:00  后续步骤与致谢
```

**1.4 准备问题**

三类问题，按顺序：
1. **无背景问题** -- 关于问题本身，而非解决方案
   - "您试图解决什么问题？"
   - "谁会受到这个问题的影响？"
   - "成功的结果是什么样的？"

2. **特定背景问题** -- 关于当前情况
   - "请带我走一遍您今天是如何做X的。"
   - "这个流程中最耗时的部分是什么？"
   - "当Y出错时会发生什么？"

3. **面向解决方案的问题** -- 关于期望的未来状态
   - "如果您可以改变这个流程中的一件事，会是什么？"
   - "什么会让您确信新系统是有效的？"
   - "是否有我们必须遵守的约束条件？"

---

### 阶段2：执行会议

**2.1 引导规则**
- 多听少说（80/20法则）
- 通过追问"为什么？"和"当……时会发生什么？"来深入挖掘
- 不要与利益相关者的回答争论（先记录，后验证）
- 记录一切——即使看起来不重要的内容
- 观察肢体语言（困惑、不同意、兴奋）
- 管理主导型参与者（引导："这很有帮助。让我们听听其他人的意见。"）

**2.2 记录技术**
- 白板/电子白板用于可视化建模
- 便利贴用于头脑风暴（每张贴一个想法）
- 笔记本用于详细记录（直接引用非常宝贵）
- 录音（如获许可）供后续回顾
- 指定专门的记录员，与引导者分开

**2.3 获取活动**

**流程走查（30-45分钟）：**
1. 请用户逐步走查其工作流程
2. 对每个步骤追问：谁？什么？何时？何地？为什么？如何？
3. 识别痛点、变通方法和决策点
4. 边走查边绘制流程（泳道图或流程图）

**需求头脑风暴（30-45分钟）：**
1. 提出问题："系统需要为您做什么？"
2. 不加评判地收集所有想法（5-10分钟自由发散）
3. 将相似想法分组
4. 讨论并澄清每个分组
5. 识别遗漏："那X呢？异常处理呢？"

**场景走查（20-30分钟）：**
1. 呈现一个真实场景："假设您收到一批化学品……"
2. 追问："您首先做什么？然后呢？如果X出了问题怎么办？"
3. 这能发现抽象问题无法触及的需求

---

### 阶段3：记录（会议后30-60分钟）

在会议结束后24小时内：

1. **整合原始记录**为结构化格式
2. **草拟初始需求**（用户故事、shall语句或用例）
3. **标记待解决问题** -- 需要跟进的事项
4. **识别冲突** -- 利益相关者之间存在分歧的地方
5. **列出假设** -- 已假定但未确认的事项

---

### 阶段4：综合整理（1-2小时）

1. **将获取产出映射到需求格式：**
   - 流程走查 -> 用例或活动图
   - 头脑风暴的需要 -> 用户故事
   - 提及的业务规则 -> 业务规则目录条目
   - 提及的数据 -> 数据字典条目
   - 质量关注点 -> 质量属性规格说明

2. **与现有工件交叉参照：**
   - 新需求是否与愿景和范围一致？
   - 相对于业务目标，覆盖范围是否存在缺口？
   - 是否与之前已记录的需求存在冲突？

3. **准备输出包：**
   - 需求草案（使用相应的技能模板）
   - 待解决问题清单
   - 冲突解决事项
   - 后续会议计划（如需要）

---

### 阶段5：验证（下次会议或异步进行）

1. 将需求草案发送给会议参与者进行评审
2. 询问："这是否准确地记录了您告诉我们的内容？"
3. 解决利益相关者之间的观点冲突
4. 为待解决问题安排后续会议

## 常见陷阱

### 陷阱1：没有准备
**症状：** 引导者没有计划、议程或准备问题就参加会议。

**后果：** 会议漫无目的。参与者失去信心。重要主题被遗漏。

**修正：** 为每次获取会议投入1-2小时进行准备。议程、问题和参与者名单应在会议开始前就绪。

---

### 陷阱2：引导性提问
**症状：** "你不觉得我们应该用下拉菜单来做这个字段吗？"（引导向特定解决方案）

**后果：** 您得到的是对自己假设的确认，而不是发现真正的需求。

**修正：** 提出开放式问题："您希望如何在这里选择一个值？"让利益相关者定义需求；您后续再设计解决方案。

---

### 陷阱3：没有后续文档
**症状：** 会议很好，有很多洞见，但事后没有人写下任何东西。

**后果：** 洞见丢失。两周后，没人记得细节。

**修正：** 在24小时内完成文档记录。在48小时内将需求草案发送给参与者进行确认。

---

### 陷阱4：利益相关者主导
**症状：** 一个人占了会议80%的发言时间。其他人保持沉默。

**后果：** 需求反映的是一个人的视角，而非团队的。沉默的利益相关者的需求被遗漏。

**修正：** 使用轮流发言技术："让我们挨个说。每人分享一个需求。"直接对主导发言者说："谢谢，这非常有帮助。我也想听听其他人的意见。"
