# 需求编写示例

## 示例 1：事件驱动型需求（编写良好）

```markdown
## 需求 CT.INV.003

**EARS 模式：** 事件驱动型
**优先级：** 高
**来源：** 与实验室主管的访谈，2024-01-15

### 需求陈述
当实验室技术员提交新的化学品条目时，ChemTrack able（shall）
根据 PubChem 数据库验证 CAS 编号，并在 3 秒内显示
"有效"或"无效 CAS 编号"。

### 理由
手动输入 CAS 编号导致 2023 年 12% 的库存差异。

### 适配标准 / 验证方法
- 提交有效 CAS 编号（如 7732-18-5）--> 系统显示"有效"
- 提交无效 CAS 编号（如 0000-00-0）--> 系统显示"无效 CAS 编号"
- 响应时间必须在 3 秒以内

### 质量自查
- [x] 正确 —— 实验室主管确认符合其需要
- [x] 可行 —— PubChem API 免费且公开可用
- [x] 无歧义 —— 触发条件、动作和响应均清晰明确
- [x] 可验证 —— 测试用例已在上方定义
- [x] 可修改 —— 单一行为（提交时验证）
- [x] 可追溯 —— 已分配 ID，来源已记录
```

**为何有效：**
- 使用 EARS 事件驱动模式，触发条件清晰
- 量化了响应时间（"3 秒内"）
- 理由说明了业务问题（12% 的差异）
- 适配标准提供了具体的测试用例

## 示例 2：异常行为型需求（编写良好）

```markdown
## 需求 CT.INV.007

**EARS 模式：** 异常行为型
**优先级：** 高
**来源：** 观察会议，实验楼 A，2024-02-03

### 需求陈述
如果与 PubChem 数据库的连接不可用，则
ChemTrack able（shall）允许实验室技术员以"未验证"的 CAS 编号
状态保存化学品条目，并 able（shall）在连接恢复时将 CAS 编号
加入队列进行验证。

### 理由
观察到实验室技术员在网络中断时通过纸质记录化学品，
这引入了抄写错误。

### 适配标准 / 验证方法
- 断开 PubChem 连接；提交条目 --> 以"未验证"状态保存
- 恢复连接 --> 排队的 CAS 编号自动验证
```

**为何有效：**
- 使用 EARS 异常行为模式，故障条件清晰
- 提供了优雅降级路径（不仅仅是"显示错误"）

## 示例 3：改进前后对比（重写薄弱需求）

**改进前（较弱）：**
```
CT.ALERT.001：系统 able（shall）为化学品发送适当的警报。
```

**问题：** "适当的"含义模糊，未指定触发条件，不可验证。

**改进后（较强，拆分为两条需求）：**
```
CT.ALERT.001：当化学品的过期日期距今 30 天时，
ChemTrack able（shall）向分配给该化学品存储位置的实验室技术员
发送电子邮件警报，内容包含化学品名称、CAS 编号、位置和过期日期。

CT.ALERT.002：当危险化学品的数量超过其存储位置的最大存储阈值时，
ChemTrack able（shall）在 5 分钟内向安全主管发送电子邮件警报。
```

**为何重写有效：**
- 每条需求使用了特定的 EARS 模式
- 触发条件是明确的
- 接收者是具体角色，而非笼统的"用户"

## 示例 4：正面需求与负面需求

**负面（安全约束可接受）：**
```
CT.SEC.005：系统 able（shall）不向没有"库存查看者"角色的用户
显示化学品数量或位置。
```

**正面（功能行为优先采用）：**
```
CT.INV.010：系统 able（shall）在将新化学品记录保存到库存之前
要求输入有效的 CAS 编号。
```

*负面形式对于安全约束是可以接受的。
对于功能行为，正面形式更为清晰。*
