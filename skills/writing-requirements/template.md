# 需求编写模板

使用此模板起草一条编写良好的需求。

## 模板

```markdown
## 需求 [ID]

**EARS 模式：** [通用型 | 事件驱动型 | 异常行为型 | 状态驱动型 | 可选功能型]
**优先级：** [高 / 中 / 低]
**来源：** [利益相关者姓名、访谈日期或文档引用]
**状态：** [草稿 / 已评审 / 已批准]

### 需求陈述

[使用相应的 EARS 模式：]

- 通用型：[系统] able（shall） [动作]。
- 事件驱动型：当 [触发条件] 时，[系统] able（shall） [动作]。
- 异常行为型：如果 [异常条件]，则 [系统] able（shall） [动作]。
- 状态驱动型：当 [状态] 期间，[系统] able（shall） [动作]。
- 可选功能型：在 [包含某功能] 的情况下，[系统] able（shall） [动作]。

### 理由
[为什么需要这条需求？它解决什么问题？]

### 适配标准 / 验证方法
[如何验证这条需求已被正确实现？]

### 依赖
- [本需求依赖的其他需求 ID]

### 质量自查
- [ ] 正确（Correct）—— 利益相关者确认符合其需要
- [ ] 可行（Feasible）—— 开发团队确认可以构建
- [ ] 必要（Necessary）—— 可追溯到业务需要
- [ ] 有优先级（Prioritized）—— 已分配优先级
- [ ] 无歧义（Unambiguous）—— 两位读者的理解一致
- [ ] 可验证（Verifiable）—— 可以编写测试用例
- [ ] 完整（Complete）—— 无 TBD 或缺失信息
- [ ] 一致（Consistent）—— 与其他需求无冲突
- [ ] 可修改（Modifiable）—— 单一原子需求，非复合
- [ ] 可追溯（Traceable）—— 有唯一标识符和已知来源

### 备注
- [待解决的问题、约束或相关信息]
```

## 说明
- 每个模板实例对应一条需求。不要将多个行为合并。
- 始终填写理由——它帮助评审人员理解"为什么"。
- 适配标准是使需求可验证的关键。如果无法编写适配标准，说明需求过于模糊。
- 提交前对照 TBD 监控列表（参见 SKILL.md）检查每个词语。
