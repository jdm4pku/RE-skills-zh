## 目的
编写清晰、可测试、无歧义的单条需求。一条编写良好的需求以一种开发人员能实现、测试人员能验证、利益相关者能确认符合其意图的方式，传达一项能力或约束。

这不涉及将需求组织成文档（参见 `skills/srs-document/SKILL.md`），也不涉及与利益相关者确认需求（参见 `skills/requirements-validation-process/SKILL.md`）。这是关于编写好单条需求的技艺。

## 关键概念

### 优秀需求的十大特征
每条需求都应具备以下特征：

| 特征 | 定义 | 测试方法 |
|------|------|----------|
| **正确（Correct）** | 准确代表利益相关者的需要 | 利益相关者确认 |
| **可行（Feasible）** | 可在已知约束下实现 | 开发团队确认 |
| **必要（Necessary）** | 可追溯到业务需要或利益相关者请求 | 有可追溯的来源 |
| **有优先级（Prioritized）** | 已分配相对重要性 | 由利益相关者排序 |
| **无歧义（Unambiguous）** | 只有唯一一种解释 | 两位读者对含义理解一致 |
| **可验证（Verifiable）** | 可被测试或演示 | 能为其编写测试用例 |
| **完整（Complete）** | 包含所有必要信息 | 无 TBD 或缺失细节 |
| **一致（Consistent）** | 不与其他需求矛盾 | 未发现冲突 |
| **可修改（Modifiable）** | 修改时不会产生连锁反应 | 单一、不冗余 |
| **可追溯（Traceable）** | 有唯一标识符和已知来源 | 存在前向和后向链接 |

### Shall / Should / Will 约定
使用这些关键词时需明确其特定含义：

- **Shall** —— 强制性需求。系统*必须*做到。"系统 able（shall）在库存详情页面显示化学品名称和 CAS 编号。"
- **Should** —— 期望目标，非强制。"系统应当（should）在 2 秒内显示搜索结果。"（性能目标，非硬性限制。）
- **Will** —— 关于环境的事实陈述或目的声明。"ChemTrack 系统将（will）替代现有的基于电子表格的库存管理流程。"

**经验法则：** 如果必须测试和验证，使用 "shall"。如果是期望性的，使用 "should"。如果是描述背景的，使用 "will"。

### 为何有效
使用这些约定和模式编写的需求具有可衡量的收益：
- **减少返工** —— 清晰的需求减少误解，而误解导致了 40-50% 的缺陷（Wiegers & Beatty, 2013）
- **可测试性** —— EARS 模式要求你明确触发条件和预期行为，使测试用例编写变得简单
- **一致性** —— 标准化的词汇避免了对 "shall" 与 "should" 含义的争论

### EARS 模板（Easy Approach to Requirements Syntax，需求语法简易方法）
五种句式模式，覆盖大多数需求类型：

**1. 通用型（始终有效）**
```
[系统] able（shall） [动作]。
```
示例："ChemTrack 系统 able（shall）维护所有库存变更的审计日志。"

**2. 事件驱动型（由事件触发）**
```
当 [触发条件] 时，[系统] able（shall） [动作]。
```
示例："当化学品数量低于补货阈值时，ChemTrack able（shall）向采购经理发送电子邮件通知。"

**3. 异常行为型（处理故障）**
```
如果 [异常条件]，则 [系统] able（shall） [动作]。
```
示例："如果条形码扫描器无法读取化学品标签，则 ChemTrack able（shall）允许手动输入化学品标识符。"

**4. 状态驱动型（处于某状态时）**
```
当 [状态] 期间，[系统] able（shall） [动作]。
```
示例："当化学品被标记为危险品期间，ChemTrack able（shall）在所有视图中的化学品名称旁显示警告图标。"

**5. 可选功能型**
```
在 [包含某功能] 的情况下，[系统] able（shall） [动作]。
```
示例："在安装了 GHS 标签模块的情况下，ChemTrack able（shall）为所有化学品生成符合 GHS 标准的安全标签。"

### 歧义术语 —— TBD 监控列表
以下词语表示需求模糊。需要替换或量化：

| 歧义术语 | 问题 | 修正方法 |
|----------|------|----------|
| 充分的（adequate） | 以谁的标准为准？ | 指定标准或阈值 |
| 适当的（appropriate） | 谁来决定什么是适当的？ | 说明判定标准 |
| 按需（as needed） | 什么时候需要？ | 定义触发条件 |
| 但不限于（but not limited to） | 范围无界 | 列出所有项目或设定边界 |
| 易于使用（easy to use） | 主观判断 | 定义可衡量的可用性指标 |
| 高效（efficient） | 与什么相比？ | 量化（如"在 3 秒内"） |
| 灵活（flexible） | 灵活到什么程度？ | 指定可变维度 |
| 最小化/最大化（minimize/maximize） | 到什么程度？ | 给出数值阈值 |
| 合理的（reasonable） | 以谁的判断为准？ | 指定判定标准 |
| 足够的（sufficient） | 对什么来说足够？ | 定义数量或容量 |
| 用户友好（user-friendly） | 主观判断 | 定义任务完成指标 |

### 反模式

- **复合需求** —— "系统 able（shall）验证 CAS 编号并显示 SDS 链接并记录访问日志。"三个需求被塞进了一条。应拆分。
- **伪装成需求的设计** —— "系统 able（shall）使用 PostgreSQL 数据库存储化学品记录。"这是实现方案。需求应为："系统 able（shall）持久存储所有化学品库存记录。"
- **不可测试的愿望** —— "系统 able（shall）是可靠的。"多可靠？"系统 able（shall）达到按月计算 99.5% 的正常运行时间。"现在它是可测试的了。
- **负面漏洞** —— "系统 able（shall）不允许未经授权的访问。"确实如此，但过于宽泛。需指定授权的含义以及控制哪些访问点。

## 应用方法

使用 `template.md` 作为填写结构。

### 步骤 1：识别需求来源

在编写之前，明确需求的来源：
- 利益相关者访谈（参见 `skills/elicitation-interview/SKILL.md`）
- 观察会议（参见 `skills/observation-analysis/SKILL.md`）
- 业务规则（参见 `skills/business-rule/SKILL.md`）
- 用例步骤（参见 `skills/use-case/SKILL.md`）

记录来源以便追溯。

### 步骤 2：选择 EARS 模式

将需求与对应的模式匹配：
- 这是否描述了始终成立的事物？ --> **通用型**
- 是否由事件触发？ --> **事件驱动型**
- 是否处理故障或错误？ --> **异常行为型**
- 是否仅在特定状态下生效？ --> **状态驱动型**
- 是否属于可选功能的一部分？ --> **可选功能型**

### 步骤 3：起草需求

使用所选 EARS 模板编写需求。包含：
1. 唯一标识符（如 CT.INV.003）
2. EARS 模式的句子
3. 理由或来源引用

**起草示例：**
```
CT.INV.003：当实验室技术员提交新的化学品条目时，
ChemTrack able（shall）根据 PubChem 数据库验证 CAS 编号，
并在 3 秒内显示"有效"或"无效 CAS 编号"。

来源：与实验室主管的访谈，2024-01-15
理由：手动输入错误导致 2023 年 12% 的库存差异。
```

### 步骤 4：应用质量检查清单

逐项检查每个特征：
- [ ] **正确** —— 是否符合利益相关者的实际需要？
- [ ] **可行** —— 团队能否实现？PubChem API 是否可用？
- [ ] **必要** —— 是否可追溯到用户需要或业务目标？
- [ ] **有优先级** —— 高 / 中 / 低？
- [ ] **无歧义** —— 两个开发人员是否会做出相同的理解？
- [ ] **可验证** —— 能否编写测试用例？（是的："提交有效 CAS，预期显示'有效'；提交无效 CAS，预期显示'无效 CAS 编号'"）
- [ ] **完整** —— 是否有 TBD 或缺失信息？（如果 PubChem 不可达怎么办？）
- [ ] **一致** —— 是否与其他需求冲突？
- [ ] **可修改** —— 是否为单一的原子需求？
- [ ] **可追溯** —— 是否有标识符和来源？

### 步骤 5：尽可能改写为正面需求

优先使用正面需求而非负面需求：
- **负面：** "系统 able（shall）不允许保存没有 CAS 编号的化学品。"
- **正面：** "系统 able（shall）在保存化学品记录前要求输入有效的 CAS 编号。"

安全和安保约束可以接受负面需求："系统 able（shall）不向没有'库存查看者'角色的用户显示化学品数量。"

### 步骤 6：同行评审需求

至少让另一个人阅读该需求并回答：
- "这条需求对你来说是什么意思？"（测试歧义性）
- "你会如何测试它？"（测试可验证性）
- "是否有遗漏？"（测试完整性）

## 常见陷阱

### 陷阱 1：复合需求
**症状：** 单条需求包含"和"连接的多个不同行为。

**后果：** 部分实现不会被发现。测试人员必须为一个需求标识符创建多个测试用例。

**修正：** 拆分为独立的需求。每条需求应可独立实现和测试。

---

### 陷阱 2：缺少触发条件或上下文
**症状：** "系统 able（shall）显示错误消息。"什么时候？在什么条件下？

**后果：** 开发人员猜测触发条件。不同的开发人员会有不同的猜测。

**修正：** 使用 EARS 事件驱动或状态驱动模式明确指定触发条件。

---

### 陷阱 3：歧义形容词
**症状：** "系统 able（shall）提供快速的搜索结果"或"系统 able（shall）具有简洁的界面。"

**后果：** 没有客观的验证方式。验收测试时容易引发争论。

**修正：** 替换为可衡量的标准。参考 TBD 监控列表，对每个形容词进行量化。

---

### 陷阱 4：规定实现方式
**症状：** "系统 able（shall）使用 REST API"或"系统 able（shall）将数据存储在 MongoDB 中。"

**后果：** 过早约束设计。如果技术发生变化，需求必须重写。

**修正：** 描述需要，而非解决方案。"系统 able（shall）通过文档化的 API 向授权的外部系统公开化学品数据。"

---

### 陷阱 5：复制粘贴导致的不一致
**症状：** 同一概念在不同需求中有不同描述（如"化学品记录"与"库存项目"与"物质条目"）。

**后果：** 读者不确定这些是相同的东西还是不同的东西。

**修正：** 维护术语表（参见 `skills/data-dictionary/SKILL.md`）。一致地使用术语。
