## 目的
指导需求工程师选择合适的评审方法并规划评审流程。利用此技能在需求实施之前最大化缺陷检测率——此时修复缺陷的成本比在代码中修复低 10-100 倍。

这不是关于代码评审，而是关于需求评审——在开发人员开始构建之前，捕获歧义性、不完整性、不一致性和不可行性。

## 关键概念

### 评审正式程度谱系

| 级别 | 正式程度 | 工作量 | 缺陷检测率 | 最适用于 |
|-------|-----------|--------|-----------------|---------|
| **临时评审（Ad-hoc Review）** | 最低 | 最低 | 低（20-30%） | 小变更、低风险功能 |
| **同行桌面检查（Peer Desk Check）** | 低 | 低 | 中等（30-40%） | 单个需求、快速反馈 |
| **走查（Walkthrough）** | 中等 | 中等 | 良好（40-60%） | 需求演示、团队对齐 |
| **正式检查（Formal Inspection）** | 高 | 高 | 最佳（60-80%） | 关键系统、法规合规 |

### Fagan 检查流程

六个阶段，每个阶段都有明确的进入和退出准则：

1. **计划** -- 主持人选择检查员，分发材料，安排会议
2. **概览** -- 作者介绍需求上下文（如果检查员已熟悉则可跳过）
3. **准备** -- 每位检查员独立评审，记录潜在缺陷（大多数缺陷在此阶段发现）
4. **会议** -- 检查员汇总发现，通过讨论识别新问题，对缺陷进行分类
5. **返工** -- 作者处理所有已识别的缺陷
6. **跟踪** -- 主持人验证所有缺陷已解决，决定是否需要重新检查

### 需求缺陷分类

| 缺陷类型 | 描述 | 示例 |
|------------|-------------|---------|
| **歧义性（Ambiguity）** | 可能有多种理解 | "系统应快速响应" |
| **不完整性（Incompleteness）** | 缺少信息或场景 | 未指定错误处理 |
| **不一致性（Inconsistency）** | 与另一个需求矛盾 | FR-10 说"始终"，FR-45 说"除了当……" |
| **不可行性（Infeasibility）** | 技术上或经济上不可能 | "100% 可用时间且零成本" |
| **不可验证性（Unverifiability）** | 无法测试 | "系统应具有用户友好性" |
| **重复（Duplication）** | 同一需求在两处以不同方式表述 | FR-12 和 FR-78 说的是同一件事 |
| **镀金（Gold-plating）** | 需求未追溯到任何业务需要 | 没有人要求的功能 |
| **需求中的设计（Design in requirements）** | 指定了实现方式而非行为 | "使用 PostgreSQL 并采用 B-tree 索引" |

### 评审度量指标

| 指标 | 目标值 | 含义 |
|--------|--------|--------------|
| **准备速率** | 1-2 页/小时 | 检查员在准备阶段的评审速度 |
| **缺陷检测率** | 5-10 个缺陷/会议小时 | 检查会议的有效性 |
| **检查速率** | 2-4 页/会议小时 | 检查会议的速度 |
| **返工率** | < 原始工作量的 20% | 检查产生的返工量 |

## 应用

### 交互式选择流程

**问题 1：该系统的风险级别是什么？**

1. **安全关键** -- 故障可能对人员或环境造成伤害
2. **业务关键** -- 故障导致重大经济损失或违反法规
3. **标准** -- 故障造成不便但不会产生严重后果
4. **低风险** -- 内部工具，非关键，容易恢复

---

**问题 2：评审的对象是什么？**

1. **完整 SRS** -- 完整的需求规格说明书（50+ 页）
2. **需求集** -- 某个部分或功能的需求（5-20 页）
3. **单个需求** -- 少量需求或用户故事
4. **需求变更** -- 对现有基线的修改需求

---

**问题 3：可用于评审的资源有哪些？**

1. **完整团队** -- 业务分析师、开发人员、测试人员、领域专家均可参与评审
2. **部分团队** -- 业务分析师和 1-2 位其他人员可参与
3. **最少人员** -- 仅业务分析师和一位评审员
4. **时间受限** -- 需要快速评审（< 1 天）

---

### 推荐逻辑

**如果是安全/业务关键 + 完整 SRS + 完整团队：**
推荐：**正式 Fagan 检查**
- 在最高风险情况下实现最大缺陷检测率
- 规划 2-4 次检查会议（分块评审，而非一次性全部评审）
- 使用完整的缺陷检查清单
- 跟踪度量指标以改进流程

**如果是安全关键 + 任意评审范围 + 任意团队：**
推荐：**正式 Fagan 检查（强制）**
- 安全关键系统无论约束条件如何，都应始终使用正式检查
- 如果团队有限，以更多次数的小块形式进行检查
- 法规合规通常要求有记录的检查证据

**如果是标准 + 完整 SRS + 完整/部分团队：**
推荐：**结构化走查（Structured Walkthrough）**
- 作者逐节介绍需求
- 评审员提出问题并记录问题
- 比正式检查开销更少，仍然有效
- 将走查时间集中在风险最高的部分

**如果是标准 + 需求集 + 部分团队：**
推荐：**同行桌面检查 + 聚焦走查**
- 同行桌面检查用于单个需求质量
- 短时走查（1-2 小时）用于完整需求集
- 使用精简版缺陷检查清单

**如果是低风险 + 单个需求 + 最少人员：**
推荐：**同行桌面检查**
- 一位评审员阅读需求并提供反馈
- 聚焦于 7 个特征：完整、正确、可行、必要、已排优先级、无歧义、可验证
- 非正式、快速，仍优于不评审

**如果是需求变更：**
推荐：**聚焦评审**
- 仅评审变更的需求
- 检查对现有需求的副作用
- 验证可追溯性已更新
- 正式程度与原始评审级别一致

---

### 缺陷检查清单（任何评审中使用）

对于每个需求，检查：
- [ ] **完整** -- 所有必要信息均已提供
- [ ] **正确** -- 准确反映了利益相关者的需要
- [ ] **可行** -- 可在约束条件内实现
- [ ] **必要** -- 可追溯到业务目标（非镀金）
- [ ] **已排优先级** -- 已分配优先级
- [ ] **无歧义** -- 只有一种可能的理解
- [ ] **可验证** -- 可通过测试证明满足要求
- [ ] **一致** -- 与其他需求不冲突
- [ ] **可修改** -- 可修改而不产生连锁效应
- [ ] **可追溯** -- 唯一标识符，关联到来源和测试

## 常见陷阱

### 陷阱 1：评审变成了演示
**症状：** 作者在展示需求，而评审员被动地听。发现的缺陷很少。

**后果：** 评审变成了批准仪式，而非质量关卡。

**修复：** 要求在会议前进行独立准备。大多数缺陷应在准备阶段发现，而非在会议中。

---

### 陷阱 2：一次评审过多内容
**症状：** 试图在一次 2 小时的会议中检查 200 页的 SRS。

**后果：** 检查员疲劳。缺陷检测率在第一小时后急剧下降。

**修复：** 分块评审，每次 10-20 页。多次较短的会议比一次马拉松式会议更有效。

---

### 陷阱 3：没有缺陷检查清单
**症状：** 评审员阅读需求后说"看起来不错"，因为他们没有一个查找问题的框架。

**后果：** 系统性缺陷类型（歧义性、不完整性）被持续遗漏。

**修复：** 提供缺陷检查清单。通过示例培训评审员识别每种缺陷类型的表现形式。
