## 目的
指导需求工程师为其项目选择正确的分析和建模技术组合。不同系统需要不同的分析方法——数据密集型报表系统适合数据建模，而事件驱动的控制系统需要状态建模。使用本技能来明智地选择，而非对每个项目应用所有技术，或总是默认使用同一种技术。

本技能不是技术手册——而是选择指南。关于每种技术的详细说明，请参阅引用的技能文件。

## 关键概念

### 分析技术工具箱

| 技术 | 揭示的内容 | 最适用于 | 技能参考 |
|------|-----------|---------|---------|
| **Use Case** | 参与者-系统交互、功能流程 | 事务密集型系统、面向用户的功能 | `skills/use-case/SKILL.md` |
| **User Story** | 用户需求和验收标准 | 敏捷项目、增量交付 | `skills/user-story-re/SKILL.md` |
| **流程模型** | 工作流序列、决策点、并行性 | 多步骤业务流程、跨部门工作流 | `skills/process-modeling/SKILL.md` |
| **数据模型** | 实体关系、数据结构、基数 | 数据密集型系统、数据库、报表系统 | `skills/data-dictionary/SKILL.md` |
| **状态模型** | 对象生命周期、有效转换、事件响应 | 具有复杂对象状态的系统、嵌入式系统、工作流引擎 | `skills/state-modeling/SKILL.md` |
| **决策表** | 复杂条件逻辑、规则组合 | 具有多个交互条件的业务规则 | `skills/decision-table/SKILL.md` |
| **对话图（Dialog Map）** | 用户界面导航、屏幕流程 | UI 密集型应用、用户体验设计 | `skills/dialog-map/SKILL.md` |
| **上下文图（Context Diagram）** | 系统边界、外部接口 | 任何系统项目启动时——定义范围 | `skills/context-diagram/SKILL.md` |

### 技术选择因素

1. **需求类型重点** —— 系统主要关注用户交互、数据管理、复杂逻辑，还是事件驱动行为？
2. **系统复杂度** —— 简单的 CRUD 应用还是复杂的多领域系统？
3. **团队经验** —— 团队之前是否使用过可视化模型，还是这是全新体验？
4. **关键关注点** —— 最可能出问题的是什么：功能遗漏、数据完整性、未处理的状态，还是逻辑错误？

### "始终应用"的基线

无论系统特征如何，每个项目都受益于：
- **上下文图（Context Diagram）** —— 定义系统边界和外部接口（始终首先完成）
- **数据字典（Data Dictionary）** —— 定义系统词汇表，防止歧义

这两项不可选择性省略。其他所有技术根据适配度选择。

### 为什么有效
- **没有技术是万能的** —— Use Case 对用户交互效果好，但会遗漏数据关系。状态模型揭示生命周期缺口，但不展示用户工作流。正确的组合覆盖盲点。
- **精力是有限的** —— 你不可能为每个系统创建所有模型。选择 3-4 种高价值技术优于肤浅地做 7 种技术。
- **团队能力很重要** —— 团队无法阅读的技术就是团队无法评审的技术。将复杂度与技能水平匹配。

### 反模式
- **对所有场景使用 Use Case** —— 不管系统特征如何都默认使用 Use Case。Use Case 在揭示数据关系、复杂状态行为和条件逻辑方面较弱。
- **没有可视化模型** —— 直接从引出记录跳到编写需求，没有任何可视化分析。这通常会遗漏 15-30% 的需求。
- **总是使用所有技术** —— 为每个项目构建所有可能的模型。分析瘫痪。大多数模型不会产生相应的洞察。
- **技术与场景不匹配** —— 对简单的 CRUD 应用使用状态图，或仅对安全关键的嵌入式系统使用 User Story。

## 应用

### 交互式技术选择

**问题 1：您的主要需求类型重点是什么？**

1. **用户交互** —— 系统主要是用户执行任务（表单、工作流、事务）
2. **数据管理** —— 系统主要是存储、处理和报告复杂数据
3. **业务逻辑** —— 系统有复杂的规则、计算和条件行为
4. **事件驱动行为** —— 系统响应事件，有复杂的对象生命周期，或是实时系统
5. **均衡型** —— 系统在多个领域都有重要需求

---

**问题 2：系统的复杂度如何？**

1. **低** —— 单一用户类型，< 20 个功能，简单的 CRUD 操作
2. **中** —— 2-4 种用户类型，20-50 个功能，中等程度的业务规则
3. **高** —— 5+ 种用户类型，50+ 个功能，复杂的集成，法规要求
4. **非常高** —— 安全关键、实时、嵌入式或多系统集成

---

**问题 3：团队的建模经验如何？**

1. **无** —— 团队之前没有使用过可视化需求模型
2. **基础** —— 团队使用过简单的图表（流程图、基础 ERD），但未使用过正式的建模符号
3. **中等** —— 团队使用过 Use Case、状态图或类似的正式技术
4. **高级** —— 团队熟练使用多种建模符号（UML、BPMN、形式化方法）

---

**问题 4：您对该系统需求最大的担忧是什么？**

1. **功能遗漏** —— 我们可能遗漏功能或用户任务
2. **数据完整性** —— 数据关系和约束可能错误或不完整
3. **逻辑错误** —— 业务规则和条件行为可能有缺口
4. **未处理的状态** —— 对象生命周期和事件响应可能不完整
5. **用户体验** —— 导航和屏幕流程可能令人困惑或不完整
6. **集成** —— 系统接口和数据交换可能被遗漏

---

### 推荐逻辑

**始终推荐（所有场景）：**
- 上下文图（`skills/context-diagram/SKILL.md`）
- 数据字典（`skills/data-dictionary/SKILL.md`）

**用户交互重点（Q1=1）：**

| 复杂度 | 经验 | 推荐技术 |
|-------|------|---------|
| 低-中 | 无-基础 | User Story + 简单流程图 |
| 低-中 | 中等+ | Use Case（简要或非正式格式） |
| 高-非常高 | 中等+ | Use Case（完整格式）+ 对话图 |
| 任意 | 任意 + 关注点=功能遗漏 | Use Case —— 系统性地揭示替代流和异常流 |

**数据管理重点（Q1=2）：**

| 复杂度 | 经验 | 推荐技术 |
|-------|------|---------|
| 低-中 | 无-基础 | 数据字典 + 简单 ER 图 |
| 中-高 | 中等+ | 数据模型（完整 ERD）+ CRUD 矩阵 + 数据字典 |
| 高-非常高 | 高级 | 数据模型 + CRUD 矩阵 + 关键数据实体的状态模型 |
| 任意 | 任意 + 关注点=数据完整性 | 数据模型 + CRUD 矩阵 —— CRUD 揭示缺失的操作 |

**业务逻辑重点（Q1=3）：**

| 复杂度 | 经验 | 推荐技术 |
|-------|------|---------|
| 低-中 | 无-基础 | 决策表（简化版） |
| 中-高 | 中等+ | 决策表 + 业务规则目录（`skills/business-rule/SKILL.md`） |
| 高-非常高 | 高级 | 决策表 + 状态模型 + 规则密集型工作流的流程模型 |
| 任意 | 任意 + 关注点=逻辑错误 | 决策表 —— 通过 2^N 规则枚举强制完整性 |

**事件驱动重点（Q1=4）：**

| 复杂度 | 经验 | 推荐技术 |
|-------|------|---------|
| 低-中 | 无-基础 | 简单状态转换图（非正式符号） |
| 中-高 | 中等+ | 状态模型（完整状态表）+ 事件-响应表 |
| 高-非常高 | 高级 | 状态模型 + 决策表 + 流程模型 |
| 任意 | 任意 + 关注点=未处理的状态 | 状态模型 —— 状态表中的每个单元格要么是有效转换，要么是明确处理的"不可能发生" |

**均衡重点（Q1=5）：**

| 复杂度 | 经验 | 推荐技术 |
|-------|------|---------|
| 低-中 | 无-基础 | User Story + 数据字典 + 为最复杂的规则创建 1 个决策表 |
| 中-高 | 中等+ | Use Case + 数据模型 + 决策表 + 1-2 个关键实体的状态模型 |
| 高-非常高 | 高级 | Use Case + 数据模型 + 状态模型 + 决策表 + 跨部门工作流的流程模型 |

**针对特定关注点的补充（Q4）：**

| 关注点 | 增加此技术 | 原因 |
|--------|----------|------|
| 功能遗漏 | 系统性包含替代流/异常流的 Use Case | 强制进行"还会发生什么？"思考 |
| 数据完整性 | CRUD 矩阵 | 揭示数据被创建但从未被读取，或被读取但从未被创建的操作 |
| 逻辑错误 | 决策表 | 强制显式处理每种条件组合 |
| 未处理的状态 | 状态转换表 | 强制显式处理每种状态-事件组合 |
| 用户体验 | 对话图（Dialog Map） | 揭示 UI 中的导航路径和死胡同 |
| 集成 | 上下文图 + 接口规格说明 | 强制显式定义每个数据交换 |

## 示例

参见 `examples/sample.md` 获取完整的技术选择演练。

简要示例摘录：

```
项目：ChemTrack 化学品库存系统

Q1：均衡型（用户交互 + 数据 + 业务逻辑 + 事件）
Q2：中-高复杂度（4 种用户类型，约 40 个功能，EHS 法规）
Q3：基础建模经验（团队使用过流程图，未使用正式模型）
Q4：主要关注点：未处理的状态（化学品生命周期很复杂）

推荐组合：
1. 上下文图（始终必要）—— 定义系统边界
2. 数据字典（始终必要）—— 定义化学品记录词汇
3. User Story（用户交互重点，团队经验为基础级别）
4. 化学品记录的状态模型（主要关注点：未处理的状态）
5. 处置授权的决策表（复杂业务逻辑）

本场景不推荐的技术：
- 完整 Use Case（团队经验太基础；User Story 已经足够）
- BPMN 流程模型（团队未使用过正式符号）
- 对话图（UI 不是该系统的主要关注点）
```

## 常见陷阱

### 陷阱 1：过度建模
**症状：** 团队为一个简单的 15 功能应用创建了 7 种不同的模型类型。

**后果：** 分析阶段耗时是必要时间的 3 倍。模型被创建但从未被评审，因为数量太多。

**修复：** 将技术数量与复杂度匹配。简单系统需要 2-3 种技术。即使是复杂系统也很少需要超过 5 种。

---

### 陷阱 2：建模不足
**症状：** 团队直接从引出记录编写需求，没有进行可视化分析。

**后果：** 持续遗漏 15-30% 的需求。状态缺口、数据操作缺口和逻辑缺口直到测试或生产阶段才被发现。

**修复：** 至少创建一个上下文图，并对最复杂的领域应用一种分析技术（状态模型、决策表或 CRUD 矩阵）。

---

### 陷阱 3：技术不匹配
**症状：** 团队使用 Use Case 分析数据仓库，或使用状态图分析简单的表单应用。

**后果：** 该技术几乎没有揭示任何有价值的内容，因为它不适合系统特征。团队得出"建模没有帮助"的结论。

**修复：** 根据系统特征（本指南）选择技术，而非根据团队熟悉度或习惯。

---

### 陷阱 4：模型之间缺乏整合
**症状：** 状态图、数据模型和 Use Case 各自存在，但从未被交叉引用。

**后果：** 每个模型独立地揭示了缺口，但跨模型缺口（例如某个状态转换创建的数据不在数据模型中）被遗漏。

**修复：** 创建模型后进行交叉引用。状态模型中的每个状态都应出现在 Use Case 流程中。数据模型中的每个实体都应出现在 CRUD 矩阵中。
