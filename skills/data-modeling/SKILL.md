## 目的
创建实体-关系图（ERD），识别关键数据实体，定义其属性，并指定它们之间的关系。用于将自然语言需求和用例转化为正式的可视化模型，以揭示隐含的假设和遗漏的需求。

这是概念数据模型，而非物理数据库模式。它捕获系统必须管理的数据以及数据之间的关系，与存储技术无关。

## 核心概念

### ERD 表示法风格

**Chen 表示法（概念级，适合与利益相关者沟通）：**

| 符号 | 含义 |
|--------|---------|
| 矩形 | 实体（Entity） |
| 椭圆 | 属性（Attribute） |
| 菱形 | 关系（Relationship） |
| 线条 | 实体与关系之间的连接 |
| 双线矩形 | 弱实体（依赖另一个实体来标识） |
| 下划线属性 | 主键（Primary Key） |

**鸦爪表示法（Crow's Foot Notation，紧凑，开发人员偏好）：**

| 符号 | 含义 |
|--------|---------|
| 矩形 | 实体（属性列在内部） |
| 带鸦爪（三叉）的线条 | 关系的"多"端 |
| 带单竖线的线条 | 关系的"一"端 |
| 线条上的圆圈 | 可选参与（零） |
| 线条上的竖线 | 强制参与（一） |

### 基数与参与性

基数（Cardinality）定义一个实体有多少实例与另一个实体相关：

| 基数 | 含义 | 示例 |
|-------------|---------|---------|
| 1:1 | 一对一 | 每个实验室有且仅有一名主任 |
| 1:N | 一对多 | 一个实验室包含多种化学品 |
| M:N | 多对多 | 多种化学品可以用于多个实验 |

参与性（Participation）定义关系是强制的还是可选的：
- **全参与（强制）：** 每个实例都必须参与（化学品必须属于某个实验室）
- **部分参与（可选）：** 实例可以参与也可以不参与（化学品可能与实验关联，也可能不关联）

### 从需求中识别实体

实体是系统必须跟踪的持久"事物"。识别方法：
1. **需求中的名词** -- 化学品、实验室、用户、报告、警报
2. **用例中的主语和宾语** -- "技术人员添加一种*化学品*"（化学品是实体）
3. **具有自身标识的数据** -- 如果它有唯一标识符，则很可能是实体
4. **具有自身属性的数据** -- 如果可以描述其属性，则很可能是实体

**不是实体的：**
- 实体的属性（chemical_name 是属性，不是实体）
- 动作或流程（搜索、生成、审批）
- 实际上是 User 实体属性的角色

### 为什么有效

ERD 迫使你回答自然语言需求中含糊不清的问题：
- "化学品可以不属于任何存储位置吗？"（参与约束）
- "一条警报可以针对多种化学品吗？"（基数）
- "已处置的化学品是否仍与实验室保持关系？"（生命周期影响）

ERD 上的每个关系都暗含功能需求：如果 Chemical 与 StorageLocation 有关系，则必须有创建、读取、更新和解除该关系的需求。

### 反模式

- **上帝实体（God Entity）** -- 一个实体（如"Record"）拥有 50 个属性，实际应分解为多个实体
- **缺少关系约束** -- 在实体间画了线但未指定基数或参与性
- **过早的物理设计** -- 在概念阶段就引入关联表、外键或索引
- **孤立实体（Orphan Entity）** -- 一个与其他实体没有任何关系的实体（它为什么在这个系统中？）

## 应用方法

使用 `template.md` 获取填写结构。

### 步骤 1：盘点候选实体

扫描需求文档、用例和用户故事。列出代表系统管理的持久数据对象的每个名词：
- 用户创建或操作的对象
- 系统生成的对象（报告、警报、日志）
- 参考数据（类别、位置、单位）
- 系统必须跟踪的外部实体

ChemTrack 示例：Chemical、StorageLocation、Lab、User、ExpirationAlert、ComplianceReport、HazardClass、Experiment。

### 步骤 2：为每个实体定义属性

对每个实体，列出其拥有的属性。标记主键（唯一标识符）：
- 使用数据字典（`skills/data-dictionary/SKILL.md`）获取详细的属性定义
- 在此阶段，列出属性名称并标记键；详细格式属于数据字典

### 步骤 3：识别关系

对每对实体，询问："实体 A 的实例是否与实体 B 的实例相关？"
- 用动词短语命名关系：Chemical *存储于* StorageLocation
- 确定基数：一种化学品存储在一个位置（1:1）还是一个位置存放多种化学品（1:N）？
- 确定参与性：每种化学品都必须有存储位置（全参与）还是有些可以未分配（部分参与）？

### 步骤 4：解析多对多关系

M:N 关系通常隐藏了一个具有自身属性的关联实体：
- Chemical M:N Experiment 变为 Chemical 1:N ExperimentChemical N:1 Experiment
- ExperimentChemical 拥有自身属性：quantity_used、date_added_to_experiment

### 步骤 5：识别弱实体

弱实体（Weak Entity）依赖另一个实体来获取其标识：
- ExpirationAlert 依赖于 Chemical（没有化学品就没有警报）
- 如果父实体被删除，弱实体也必须被删除或重新分配

### 步骤 6：绘制 ERD

使用 Chen 或鸦爪表示法：
1. 将实体放置为矩形
2. 在它们之间绘制关系
3. 在每条线上标注基数和参与性
4. 标记主键和外键（鸦爪表示法）或下划线标记键（Chen 表示法）

### 步骤 7：对照用例验证

逐一检查每个用例并验证：
- [ ] 用例中引用的每个数据对象都有对应的实体
- [ ] 用例步骤中隐含的每个关系都在 ERD 中捕获
- [ ] 基数与业务规则一致（如"每种化学品必须在一个确定的位置"）
- [ ] 参与约束与需求一致（如"化学品可以选择性地关联 SDS"）
- [ ] 没有孤立实体（每个实体至少参与一个关系）
- [ ] ERD 与数据字典（`skills/data-dictionary/SKILL.md`）一致

## 示例

参见 `examples/sample.md` 获取 ChemTrack 的完整 ERD 规格说明。

简短示例（鸦爪表示法文本表示）：

```
Lab ||--o{ Chemical : "存储"
Chemical ||--|| StorageLocation : "存储于"
Chemical }o--o{ Experiment : "使用于"
Chemical ||--o{ ExpirationAlert : "触发"
User ||--o{ Chemical : "管理"
```

解读：一个 Lab 存储零个或多个 Chemical。一个 Chemical 存储在恰好一个 StorageLocation 中。一个 Chemical 可以用于零个或多个 Experiment，一个 Experiment 可以使用零个或多个 Chemical。一个 Chemical 触发零个或多个 ExpirationAlert。

## 常见陷阱

### 陷阱 1：跳过基数分析
**症状：** ERD 显示实体之间用线连接，但没有基数或参与性标记。

**后果：** 开发人员只能猜测关系约束。一个开发人员假设是 1:1，另一个假设是 1:N。数据库设计不一致。

**修复：** 每条关系线都必须在两端指定基数（1:1、1:N、M:N）和参与性（强制/可选）。

---

### 陷阱 2：上帝实体
**症状：** 一个实体拥有 30 个以上的属性，涵盖多个概念（化学品信息、存储信息、警报信息、审计信息全部在一个实体中）。

**后果：** 高耦合、维护困难、归属不清。

**修复：** 分解为独立实体。如果一组属性可以有自己的标识和生命周期，它就是一个独立实体。

---

### 陷阱 3：忽略 M:N 解析
**症状：** ERD 显示两个实体之间直接存在 M:N 关系，没有关联实体。

**后果：** 属于关系本身的属性（quantity_used、date_assigned）无处存放。

**修复：** 通过关联实体将 M:N 解析为两个 1:N 关系。将关系特有的属性添加到关联实体中。

---

### 陷阱 4：ERD 与数据字典脱节
**症状：** ERD 显示的实体和属性与数据字典定义的元素不同或有额外元素。

**后果：** 两个相互矛盾的事实来源。

**修复：** ERD 的实体和属性必须与数据字典条目一一对应。两者应一起审查。参见 `skills/data-dictionary/SKILL.md`。
