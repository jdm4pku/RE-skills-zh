## 目的
指导需求工程师建立正式的需求基线（Baseline）——在特定时间点上经过商定的、有版本控制的需求快照。基线是衡量所有未来变更的参考点，是所有可追溯性链接的锚点，也是所有开发承诺的基础。

没有基线，就无法回答这个问题："我们到底同意构建什么？"由于没有"之前"可以对比，变更无法被评估。可追溯性链接指向的是移动目标。审计人员也没有可审计的内容。

## 核心概念

### 什么构成基线

需求基线是：
- 在特定时间点上所有需求（及其属性）的**快照**
- 经过授权干系人的**批准**
- **不可变的**——一旦建立基线，内容不再更改。变更将创建新版本。
- 使用唯一的版本标识符进行**标注**
- 在配置管理下进行**存储**

基线不等同于"最新版本"。它是经过正式评审和批准的特定冻结版本。

### 版本标注规范

Wiegers 推荐一种结构化的标注方案：

| 标签格式 | 含义 | 示例 |
|---------|------|------|
| Version X.Y draft Z | 正在进行中的草稿，尚未批准 | Version 1.0 draft 3 |
| Version X.Y approved | 经过正式评审和批准 | Version 1.0 approved |
| Version X.Y | 已批准版本的简写 | Version 1.0 |

版本编号规则：
- **主版本号（X）**——在范围发生重大变更时递增（新发布、重大返工）
- **次版本号（Y）**——在发布范围内的已批准变更时递增
- **草稿号（Z）**——在尚未批准的工作草稿时递增

ChemTrack SRS 版本演进示例：
```
Version 1.0 draft 1  -- 需求获取后的初始草稿
Version 1.0 draft 2  -- 第一次评审后更新
Version 1.0 draft 3  -- 第二次评审后更新
Version 1.0 approved  -- 为 Release 1 开发建立基线
Version 1.1 draft 1  -- 纳入 CR-003 和 CR-005
Version 1.1 approved  -- 变更批准后更新基线
Version 2.0 draft 1  -- Release 2 范围扩展开始
```

### 基线化的准入标准

需求文档在满足最低质量标准之前不应建立基线：

- [ ] 所有需求已通过正式评审（参见 `skills/specification-review-checklist/SKILL.md`）
- [ ] 所有评审行动项已解决
- [ ] 所有 TBD 项已解决或明确推迟并附有理由
- [ ] 需求使用稳定的唯一 ID 进行标识
- [ ] 所有需求已分配优先级
- [ ] 所有需求可测试
- [ ] 可追溯性链接已建立（至少需求到业务目标）
- [ ] 所有具有签署权限的干系人已批准
- [ ] 无未关闭的高严重性缺陷

### 需求的配置管理

配置管理（CM）确保：
- 每份需求文档的每个版本都已存储且可检索
- 变更记录了作者、日期和理由
- 当前基线始终可识别
- 可以检索之前的基线进行对比
- 并发变更得到管理，不会丢失

需求配置管理工具：
- 版本控制系统（Git、SVN）用于基于文档的需求
- 需求管理工具（DOORS、Jama、Azure DevOps）用于数据库存储的需求
- 文档管理系统（SharePoint、Confluence）具有版本历史功能

### 基线评审和审批流程

1. **作者**准备基线候选并验证准入标准
2. **同行评审人**验证内容质量（通过 `skills/specification-review-checklist/SKILL.md`）
3. **技术负责人**验证可行性和一致性
4. **产品负责人/业务干系人**验证完整性和正确性
5. **项目经理**授权基线
6. **配置管理员**应用版本标签并锁定基线

### 为什么这种方法有效
- **建立责任制**——每个人都对承诺的内容达成共识
- **支持变更控制**——变更基于已知的参考点进行衡量
- **支持审计**——监管机构和审计人员可以准确看到任何时间点的需求规格
- **防止"需求漂移"**——没有基线，需求会悄无声息地变化，直到项目偏离轨道才有人注意到

### 反模式
- **过早建立基线**——在需求足够稳定之前就建立基线。这会导致立即产生变更请求，削弱基线的意义。
- **从不建立基线**——需求总是"进行中"，永远不会被正式冻结。变更控制没有参考点。
- **未经批准的基线**——版本被标记为"已建立基线"，但从未经过干系人的正式评审或批准。

## 应用

使用 `template.md` 获取完整的基线记录结构。

### 步骤 1：验证准入标准

在提议建立基线之前，逐项检查准入标准清单。以 ChemTrack Release 1 为例：

```
准入标准评估：
[x] 正式评审已完成（评审 #3，2025-03-20）
[x] 所有评审行动项已解决（12/12 已关闭）
[x] TBD 项已解决（3 项推迟到 Release 2 并附有理由）
[x] 所有需求具有唯一 ID（FR-01 至 FR-42，NFR-01 至 NFR-15）
[x] 优先级已分配（MoSCoW 分类已完成）
[x] 所有需求可测试（在评审中已验证）
[x] 可追溯性已建立（需求 -> 业务目标）
[x] 干系人签署已获得（4/4 审批人已签署）
[x] 无未关闭的高严重性缺陷（0 个未关闭）

结果：可以建立基线
```

### 步骤 2：准备基线记录

创建基线记录文档，记录以下内容：
- 基线标识符和版本标签
- 建立基线的日期
- 基线中包含的文档列表
- 审批人列表及其签署日期
- 自上一个基线以来的变更摘要（如适用）
- 已知问题或推迟项

### 步骤 3：获取正式审批

将基线提交审批。最少审批人：
- 产品负责人或业务发起人（内容正确性）
- 技术负责人（可行性）
- 项目经理（进度和范围承诺）
- 质量保证负责人（可测试性）

对于受监管的环境，增加：
- 合规官
- 安全官（如适用）

### 步骤 4：应用版本标签并锁定

一旦获得批准：
1. 应用版本标签（例如，"Version 1.0 approved"）
2. 锁定文档/仓库以防止未受控的变更
3. 将基线存储在配置管理系统中
4. 向所有干系人分发基线通知

在基于 Git 的配置管理中：
```bash
git tag -a "SRS-v1.0-approved" -m "ChemTrack SRS Version 1.0 baseline"
git push origin "SRS-v1.0-approved"
```

在需求管理工具中，标记基线并锁定需求集。

### 步骤 5：沟通基线

通知所有干系人：
- 什么被建立了基线（文档名称、版本）
- 在哪里可以找到它（仓库 URL、工具位置）
- 这意味着什么（开发可以开始/变更需要走 CR 流程）
- 如何请求变更（指向变更控制流程）

### 步骤 6：管理基线后的变更

建立基线后，所有变更必须通过变更控制流程（`skills/change-impact-analysis/SKILL.md`）：
1. 提交变更请求
2. 执行影响分析
3. CCB 批准/推迟/驳回
4. 如果批准，更新需求并创建新的基线版本

## 常见陷阱

### 陷阱 1：过早建立基线
**症状：** 在需求仍然不稳定时就建立基线。第一周内就收到多个变更请求。

**后果：** 基线立刻过时。变更控制的开销浪费在本应在评审中发现的变更上。

**修正：** 严格验证准入标准。如果超过 10% 的需求存在未解决的问题，文档尚不具备建立基线的条件。

---

### 陷阱 2：过晚建立基线（或从不建立）
**症状：** 需求尚未建立基线就开始开发。需求继续以非正式的方式演变。

**后果：** 变更控制没有参考点。开发人员基于移动目标进行构建。"但我以为我们已经达成一致了……"这样的对话不断出现。

**修正：** 在项目计划中设置基线化里程碑。一组需求在建立基线之前不应开始开发。

---

### 陷阱 3：没有配置管理的基线
**症状：** 基线是"Sarah 笔记本电脑上的那个文档"或"上周五我们邮件发送的那个版本"。

**后果：** 基线无法被可靠地检索。多个版本同时流通。没有人知道哪个版本是权威的。

**修正：** 将基线存储在版本控制仓库或需求管理工具中。基线必须在任何时候都能被任何授权干系人检索到。

---

### 陷阱 4：非正式审批
**症状：** 基线基于会议上的口头协议被"批准"，没有书面签署记录。

**后果：** 六个月后，某个干系人声称他们从未批准过某个需求。没有相反的证据。

**修正：** 要求有书面签署记录（数字签名、邮件确认或基于工具的审批工作流）。记录审批人、日期和任何条件。

---

### 陷阱 5：没有基线变更历史
**症状：** 基线被更新了，但没有记录版本之间发生了什么变更。

**后果：** 无法确定 Version 1.0 和 Version 1.1 之间的差异。未来变更的影响分析缺乏上下文。

**修正：** 每个新的基线版本都包含变更摘要：纳入了哪些变更请求，添加/修改/删除了哪些需求。
