## 目的
指导需求工程师完成变更控制流程——评估变更请求、执行影响分析并管理审批决策。当需求已基线化且变更需要结构化评估时使用此技能。

这不是要阻止所有变更。而是让变更变得*可见、经过评估且有意为之*，而非不可见、未经评估且意外发生。

## 关键概念

### 变更控制基础

**基线（Baseline）：** 经过评审和达成一致的一组需求，作为开发的基础。对基线的变更受到控制。

**范围蔓延（Scope Creep）：** 通过渐进的、未经评估的增量添加导致项目范围不受控制地增长。每个单独的变更看起来都很小；但累积效应会使项目偏离轨道。

**变更控制委员会（CCB，Change Control Board）：** 被授权批准或拒绝基线变更的团队。组成因项目而异：
- 小型项目：产品负责人 + 首席开发人员 + 业务分析师
- 大型项目：发起人、业务分析师、架构师、项目经理、测试负责人

### 变更请求属性

每个变更请求应包含以下内容：

| 属性 | 描述 |
|-----------|-------------|
| CR ID | 唯一标识符 |
| 标题 | 变更的简要描述 |
| 请求人 | 谁提出的变更 |
| 提交日期 | 请求提出的时间 |
| 受影响的需求 | 哪些需求 ID 受到影响 |
| 原因/理由 | 为什么需要此变更 |
| 业务价值 | 该变更带来什么价值 |
| 影响评估 | 进度、成本、质量和范围影响 |
| 优先级 | 此变更的紧急程度 |
| 状态 | 已提交 / 审核中 / 已批准 / 已拒绝 / 已实施 / 已验证 |
| 决定 | 批准 / 拒绝 / 延期 / 需要更多信息 |
| 决定日期 | CCB 做出决定的时间 |
| 决定理由 | 原因（尤其是拒绝的情况） |

### 需求在变更控制中的状态
一个需求会经历以下状态：
- **已提议（Proposed）** -- 已识别但尚未分析
- **进行中（In Progress）** -- 正在细化/编写
- **已起草（Drafted）** -- 已编写但未评审
- **已批准（Approved）** -- 已评审并纳入基线
- **已实施（Implemented）** -- 已编码并通过单元测试
- **已验证（Verified）** -- 已通过验收测试
- **已延期（Deferred）** -- 概念上已批准但推迟到未来版本
- **已删除（Deleted）** -- 从基线中移除（附有记录的理由）
- **已拒绝（Rejected）** -- 已评估并被否决

### 反模式
- **无流程** -- 变更直接从利益相关方流向开发人员，没有任何评估
- **流程过重** -- 每一个微小的澄清都需要正式的变更请求（拖慢一切进度）
- **全部批准** -- CCB 批准每一个请求，因为说"不"让人不舒服
- **推卸责任** -- 变更控制被惩罚性地使用（"你应该早点想到这一点"）

## 应用

### 交互式变更评估流程

**问题 1：这是什么类型的变更？**

1. **范围变更** -- 添加原始基线中没有的新需求
2. **修改** -- 更改现有需求的行为
3. **删除** -- 移除一个已基线化的需求
4. **澄清** -- 为模糊的需求添加细节（无行为变更）
5. **缺陷纠正** -- 修复需求文档中的错误

---

**问题 2：影响有多大？**

1. **孤立的** -- 仅影响 1-2 个需求，没有连锁效应
2. **中等的** -- 影响 3-10 个需求，需要一些下游变更
3. **重大的** -- 影响 10 个以上需求或需要架构变更
4. **未知** -- 影响需要在评估之前进行分析

---

**问题 3：此变更的紧急程度如何？**

1. **关键** -- 阻塞当前开发或导致缺陷
2. **高** -- 当前版本需要此变更才能达成目标
3. **中** -- 有价值但可以等到下个版本
4. **低** -- 锦上添花，没有时间压力

---

### 影响分析流程

对每个变更请求执行以下分析：

**步骤 1：追踪受影响的需求**
使用 `skills/requirements-traceability/SKILL.md`：
- 哪些需求被直接变更？
- 哪些需求依赖于被变更的需求？
- 哪些测试用例需要更新？
- 哪些设计/代码组件受到影响？

**步骤 2：评估进度影响**
- 此变更增加了多少人时的开发工作量？
- 是否影响关键路径？
- 能否与现有工作并行进行？

**步骤 3：评估成本影响**
- 额外的开发成本
- 额外的测试成本
- 需要更新的文档
- 培训影响

**步骤 4：评估质量影响**
- 此变更是否引入新风险？
- 是否影响质量属性（性能、安全性）？
- 是否需要回归测试？

**步骤 5：评估范围影响**
- 此变更是扩大了范围还是用其他内容进行了置换？
- 如果增加了范围，可以延期什么来补偿？
- 这是否是范围蔓延模式的开始？

**步骤 6：准备建议**
向 CCB 提交：
- 变更摘要
- 影响分析结果
- 选项：批准 / 附带置换条件批准 / 延期到下个版本 / 拒绝
- 带有理由的建议

---

### 范围蔓延检测

跟踪以下警告信号：
- 变更请求量随时间增加
- 变更无法追溯到业务目标
- "小"变更实际上是功能添加
- 利益相关方绕过变更流程
- 尽管没有重大变更，进度仍在延误

**应对措施：** 如果检测到范围蔓延：
1. 向 CCB 提交累积变更数据
2. 展示原始基线与当前范围之间的差异
3. 建议进行范围重置：重新对包括变更在内的所有需求进行优先级排序
4. 考虑在项目剩余阶段建立更严格的变更阈值

## 常见陷阱

### 陷阱 1：没有基线 = 没有控制
**症状：** 需求从未被正式基线化，因此没有可以控制变更的基准。

**后果：** 每个变更都是不可见的。没人知道范围何时增长了或增长了多少。

**修复：** 在需求评审后建立基线。它不必完美——但必须达成一致。

---

### 陷阱 2：对澄清事项流程过重
**症状：** 对需求的一个单词澄清就需要正式的变更请求、CCB 会议和三个批准。

**后果：** 人们绕过流程，因为它太慢了。结果：完全没有流程。

**修复：** 定义阈值：澄清（无行为变更）可以由业务分析师单独批准。范围增加需要 CCB 评审。让流程与变更的规模相匹配。

---

### 陷阱 3：未经影响分析就批准
**症状：** 变更请求仅根据业务理由批准，没有分析进度、成本或质量影响。

**后果：** 项目积累了无法交付的承诺。进度延误，质量下降。

**修复：** 任何变更请求都不应在没有影响分析的情况下被批准。即使是粗略的估计（"额外 2-3 天的工作量，影响 4 个需求"）也比什么都没有强。
