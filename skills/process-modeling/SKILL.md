## 目的
创建可视化流程模型，捕获工作如何在涉及多个参与者、决策和并行活动的系统中流转。流程模型以文字描述无法做到的方式揭示工作流的结构——它们使交接点、决策点、瓶颈和并行路径一目了然。

这不是关于建模对象状态（参见 `skills/state-modeling/SKILL.md`）或数据结构（参见 `skills/data-modeling/SKILL.md`）。流程模型关注的是跨参与者和活动的*工作流转*。

## 关键概念

### 活动图元素

| 元素 | 符号 | 描述 | 示例 |
|------|------|------|------|
| **动作（Action）** | 圆角矩形 | 单个步骤或任务 | "录入化学品数据" |
| **决策（Decision）** | 菱形 | 带条件的分支点 | "CAS 编号是否有效？" |
| **分支（Fork）** | 粗横线 | 将流程拆分为并行路径 | 验证和通知同时进行 |
| **汇合（Join）** | 粗横线 | 将并行路径合并回来 | 验证和通知都必须完成 |
| **起始节点（Start）** | 实心圆 | 流程的起点 | 流程开始 |
| **终止节点（End）** | 带圆环的实心圆 | 流程的终点 | 流程结束 |
| **泳道（Swimlane）** | 垂直或水平条带 | 按参与者/角色划分动作 | 实验室技术员泳道、安全官员泳道 |
| **流程箭头（Flow arrow）** | 有向线 | 显示动作的顺序 | 从"录入数据"到"验证 CAS" |

### 活动图与泳道图的对比

| 方面 | 基本活动图 | 泳道图 |
|------|-----------|--------|
| 是否显示参与者 | 否——关注流程流转 | 是——每条泳道是一个参与者或角色 |
| 最适用于 | 单参与者流程、算法流程 | 具有交接的跨职能流程 |
| 复杂度 | 较低 | 较高（增加了职责维度） |
| 揭示 | 决策逻辑、并行路径 | 交接点、职责、瓶颈 |

**经验法则：** 如果流程涉及 2 个以上的参与者，使用泳道图。如果是单个参与者执行一个序列，基本活动图就足够了。

### 为什么有效
- **视觉对齐** ——对文字描述存在分歧的干系人，在看到同一张图时往往能达成一致
- **交接检测** ——每条跨越泳道边界的箭头都是一个交接点。交接点是通知、审批和数据传输需求所在之处。
- **差距识别** ——遗漏的决策分支、死胡同路径和未处理的异常在图中一目了然
- **需求推导** ——图中的每个动作、决策和交接都是一个或多个需求的候选来源

### 反模式
- **流程图小说** ——一张包含 40 个以上动作的图。过于复杂，无法审查或验证。应分解为子流程。
- **仅有正常路径** ——图仅显示正常流程，没有决策分支或错误处理。
- **实现层面的图** ——建模系统内部（数据库查询、API 调用），而非业务流程步骤。
- **静态图** ——创建一次图后再也不更新。流程模型应随着理解的深入而演进。

## 应用

使用 `template.md` 作为流程模型规格说明的结构。

### 步骤 1：确定要建模的流程

选择一个满足以下条件的流程：
1. 跨越多个参与者或角色（适合使用泳道图）
2. 已在访谈或观察中被描述过（有数据可供建模）
3. 尚未被充分理解或干系人之间存在争议

**ChemTrack 示例：**
- 化学品货物接收（技术员、安全官员、实验室经理）
- 化学品处置（技术员、安全官员、环境合规部门）
- 月度合规报告（技术员、实验室经理、安全官员）

### 步骤 2：识别参与者和泳道

列出参与流程的每个角色。每个角色成为一条泳道。

```
ChemTrack 化学品接收流程：
泳道 1：实验室技术员
泳道 2：ChemTrack 系统
泳道 3：安全官员
泳道 4：实验室经理
```

**当系统执行自动化操作（验证、通知、计算）时，将"系统"作为一条泳道**。

### 步骤 3：映射动作和顺序

列出流程中的每个动作，将每个动作分配到泳道，并定义顺序：

```
1. [实验室技术员] 接收货物并检查包装
2. [实验室技术员] 将化学品数据录入 ChemTrack
3. [ChemTrack 系统] 通过 PubChem 验证 CAS 编号
4. [ChemTrack 系统] 检查库存中是否有重复的化学品
   --> 决策：发现重复？
       是 --> [ChemTrack 系统] 显示重复警告
               [实验室技术员] 选择更新现有记录或创建新记录
       否 --> 继续
5. [ChemTrack 系统] 分配库存 ID 并保存记录
6. [ChemTrack 系统] 通知安全官员有新的危险化学品
7. [安全官员] 审查危险等级分类
   --> 决策：危险等级是否正确？
       是 --> [安全官员] 批准录入
       否 --> [安全官员] 更正分类并批准
8. [ChemTrack 系统] 将库存状态更新为"活跃"
9. [实验室经理] 接收每周新化学品汇总
```

### 步骤 4：添加决策、分支和汇合

对每个动作，询问：
- **这里是否有决策？** 添加一个带标签分支的菱形（是/否，或条件标签）
- **是否有可以并行发生的事情？** 添加分支条将流程拆分，添加汇合条将流程合并
- **失败时会发生什么？** 添加异常分支

**并行示例：**
```
化学品数据录入后：
  分支 -->
    路径 A：[系统] 验证 CAS 编号
    路径 B：[系统] 检查存储位置容量
  汇合 -->（两者都必须完成后才能继续）
```

### 步骤 5：绘制图表

使用基于文本的表示法或绘图工具：

**基于文本的表示法（用于文档）：**
```
[开始]
  |
  v
[实验室技术员] 接收货物
  |
  v
[实验室技术员] 录入化学品数据
  |

  |
  v
<CAS 有效？> --否--> [系统] 显示错误
  |                      |
  是                     v
  |               [实验室技术员] 更正 CAS
  |                      |
  v                      v
[系统] 检查重复 <----+
  |
  v
<重复？> --是--> [系统] 显示重复警告
  |                      |
  否                     v
  |               [实验室技术员] 更新或创建新记录
  v                      |
[系统] 保存记录 <---+
  |
  v
<危险品？> --是--> [系统] 通知安全官员
  |                      |
```

**泳道表示法（文本格式）：**
```
| 实验室技术员        | ChemTrack 系统          | 安全官员            |
|--------------------|-----------------------|-------------------|
| 接收货物            |                       |                   |
| 录入化学品数据       |                       |                   |
|                    | 验证 CAS 编号          |                   |
|                    | <CAS 有效？>           |                   |
| 更正 CAS（否）      |                       |                   |
|                    | 检查重复               |                   |
|                    | 保存记录               |                   |
|                    | 通知（如为危险品）       |                   |

|                    | 设置状态为"活跃"        |                   |
```

### 步骤 6：从模型推导需求

图中的每个元素都会生成候选需求：

| 图表元素 | 需求类型 | 示例 |
|---------|---------|------|
| **动作（系统）** | 功能需求 | "ChemTrack 应通过 PubChem 验证 CAS 编号" |
| **决策** | 业务规则 + 功能需求 | "如果 CAS 编号无效，ChemTrack 应显示错误消息" |
| **分支/汇合** | 性能或并发需求 | "ChemTrack 应同时验证 CAS 编号和检查存储容量" |
| **交接（跨泳道箭头）** | 通知或工作流需求 | "当添加危险化学品时，ChemTrack 应通过电子邮件通知安全官员" |
| **泳道** | 授权需求 | "只有具有安全官员角色的用户才能批准危险等级分类" |

### 步骤 7：与干系人验证

向干系人展示流程模型并询问：
1. "这是否准确地反映了当前流程？"（针对现状模型）
2. "这是否是您希望新流程的工作方式？"（针对目标模型）
3. "是否有遗漏的路径或决策？"
4. "每个动作由谁负责——泳道分配是否正确？"
5. "当 [特定异常] 发生时会怎样？"

记录更正意见并迭代更新模型。

## 常见陷阱

### 陷阱 1：建模实现而非业务流程
**症状：** 图中显示的是"系统查询数据库"和"API 返回 JSON"，而不是业务活动。

**后果：** 模型成了系统设计文档，而非流程模型。干系人无法验证。

**修正：** 建模业务活动："记录化学品"、"批准处置"、"生成报告"。将实现细节留给设计阶段。

---

### 陷阱 2：单张图中动作过多
**症状：** 一张包含 30 个以上动作的活动图，覆盖了整个业务领域。

**后果：** 不可读、无法验证。干系人在第一页就失去了兴趣。

**修正：** 将每张图限制在 7-15 个动作。将大型流程分解为子流程，每个子流程有自己的图。使用一张概要级别的图来引用子流程图。

---

### 陷阱 3：缺少异常路径
**症状：** 每个决策菱形都有"是"路径，但没有"否"路径（或反之）。

**后果：** 流程模型仅覆盖了正常路径。异常处理需求未被推导出来。

**修正：** 对每个决策，询问"另一个分支会发生什么？"两条路径都必须有去处（另一个动作、错误处理程序或结束节点）。

---

### 陷阱 4：泳道没有明确的职责
**症状：** 动作被随意放置在泳道中。"验证 CAS 编号"出现在实验室技术员泳道中，但实际上这是一个系统功能。

**后果：** 基于角色的需求和授权规则是错误的。

**修正：** 每个动作属于*执行*它的参与者。如果系统自动执行验证，它属于系统泳道。如果技术员手动检查，它属于技术员泳道。

---

### 陷阱 5：从不更新模型
**症状：** 流程图在第 1 周创建，尽管需求发生了重大变更，却从未修订。

**后果：** 模型与现实脱节。新团队成员使用的是过时的流程理解。

**修正：** 将流程模型视为活文档。当需求变更时进行更新。将其与需求一起进行版本控制。
