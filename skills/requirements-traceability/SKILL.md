## 目的
创建一个追踪矩阵，在业务目标、需求、设计元素和测试用例之间建立双向链接。使用它来回答追踪性所服务的四个问题：

1. **从源头正向追踪：** 哪些需求实现了这个业务目标？
2. **向源头反向追踪：** 这个需求服务于哪个业务目标？
3. **向实现正向追踪：** 哪些设计/代码/测试覆盖了这个需求？
4. **影响分析：** 如果 X 发生变更，还有什么会受到影响？

## 关键概念

### 追踪链（Traceability Chain）
```
业务目标（愿景与范围）
    |
    v
用户需求（用例 / 用户故事）
    |
    v
功能需求（SRS）
    |
    v
设计元素（架构 / 组件）
    |
    v
测试用例（测试计划）
```

每个链接都是双向的。你应该能够正向追踪（目标 -> 需求 -> 测试）和反向追踪（测试 -> 需求 -> 目标）。

### 追踪链接类型

| 链接类型 | 从 | 到 | 目的 |
|-----------|------|-----|---------|
| **来源追踪** | 业务目标 | 用户需求 | 确保每个业务需要都被覆盖 |
| **需求追踪** | 用户需求 | 功能需求 | 确保用户需要分解为系统行为 |
| **设计追踪** | 功能需求 | 设计元素 | 确保每个需求都有设计 |
| **测试追踪** | 功能需求 | 测试用例 | 确保每个需求都被测试 |
| **依赖追踪** | 需求 | 需求 | 跟踪需求间的依赖关系 |

### 追踪矩阵格式

**简单两列追踪：**
| 需求 | 测试用例 |
|-------------|-------------|
| FR-001 | TC-001, TC-002 |

**完整链矩阵：**
| 业务目标 | 用户需求 | 功能需求 | 测试用例 | 状态 |
|-------------|----------|---------------|-----------|--------|
| BO-1 | UC-3 | CT.CATALOG.SEARCH.1 | TC-101 | 已验证 |

**N 对 M 矩阵（覆盖视图）：**
| | BO-1 | BO-2 | BO-3 |
|---|------|------|------|
| FR-001 | X | | |
| FR-002 | X | X | |
| FR-003 | | | X |

### 追踪性红旗信号
- **没有来源的需求** -- 这个需求从何而来？可能是镀金（gold-plating）。
- **没有需求的业务目标** -- 一个已声明的目标却没有实现路径。
- **没有测试的需求** -- 不可测试或未被测试的需求。
- **孤立的测试用例** -- 不追踪到任何需求的测试（测的是什么？）。

### 反模式
- **追踪一切到一切** -- 链接过于宽泛以至于毫无意义。每个需求都追踪到"提升用户体验"。
- **追踪一次，从不更新** -- 追踪矩阵在开始时创建，随着需求变更从未维护。
- **有工具无流程** -- 有需求工具但没有维护追踪链接的流程。

## 应用

### 步骤 1：建立追踪结构

确定要追踪哪些制品：
- **最小：** 业务目标 <-> 功能需求 <-> 测试用例
- **标准：** 业务目标 <-> 用户需求 <-> 功能需求 <-> 测试用例
- **完整：** 在链中增加设计元素和代码组件

### 步骤 2：创建矩阵

对每个功能需求：
1. 反向链接到其来源（用户需求、业务目标）
2. 正向链接到其测试用例
3. 记录当前状态

使用 `template.md` 作为结构模板。

### 步骤 3：分析覆盖率

执行以下检查：

**正向覆盖（无缺口）：**
- 每个业务目标应至少有一个需求
- 每个需求应至少有一个测试用例

**反向覆盖（无镀金）：**
- 每个需求应追溯到至少一个业务目标
- 每个测试用例应追溯到至少一个需求

**完整性指标：**
- 覆盖率 = (有追踪的需求数 / 总需求数) * 100%
- 目标：正向和反向追踪均达到 100%

### 步骤 4：执行影响分析

当需求发生变更时：
1. 在矩阵中找到该需求
2. 正向追踪：哪些测试用例需要更新？
3. 反向追踪：该变更是否符合业务目标？
4. 横向追踪：哪些其他需求依赖于此需求？
5. 在变更请求中记录影响范围

### 步骤 5：持续维护

- 当需求被添加、变更或删除时更新追踪
- 在每个里程碑或迭代评审时审查矩阵
- 跟踪追踪性指标：覆盖百分比、断裂链接
- 指定负责人：必须有人负责维护追踪

## 示例

参见 `examples/sample.md` 获取完整的追踪矩阵。

简要示例：

```markdown
| 业务目标 | 用户需求 | 功能需求 | 测试用例 | 状态 |
|-------------|----------|---------------|-----------|--------|
| BO-1: 缩短报告时间 | UC-8: 生成报告 | CT.REPORT.GEN.1: 30秒内生成 EPA 报告 | TC-201: EPA 报告生成负载测试 | 已验证 |
| BO-2: 消除过期化学品 | UC-5: 过期预警 | CT.ALERT.EXPIRY.1: 发送 30 天预警 | TC-150: 30 天预警邮件验证 | 已验证 |
| BO-2 | UC-5 | CT.ALERT.EXPIRY.2: 发送 7 天紧急预警 | TC-151: 7 天紧急预警验证 | 已实现 |
| -- | -- | CT.CATALOG.ADD.3: 允许从 CSV 批量导入 | -- | 已提议 |
```

**对这个简要示例的分析：**
- CT.CATALOG.ADD.3 没有反向追踪到业务目标（可能是镀金）
- CT.CATALOG.ADD.3 还没有测试用例（需要测试规划）
- BO-1 和 BO-2 通过需求和测试实现了正向覆盖

## 常见陷阱

### 陷阱 1：没有来源的需求
**症状：** 多个需求没有反向追踪到业务目标或用户需要。

**后果：** 这些可能是镀金——没有人要求的功能却消耗了开发资源。

**修复：** 对每个未追踪的需求，问："这个需求服务于哪个业务目标？"如果没有，要么找到遗漏的目标，要么移除该需求。

---

### 陷阱 2：矩阵未维护
**症状：** 追踪矩阵在项目开始时创建，之后从未更新。新需求没有追踪。

**后果：** 矩阵对影响分析毫无用处。变更评估无法理解完整的链路。

**修复：** 将追踪更新作为变更控制流程的必要步骤。在追踪更新完成之前，需求变更不算完成。

---

### 陷阱 3：没有到测试的正向追踪
**症状：** 需求存在但没有对应的测试用例。

**后果：** 这些需求从未被验证。这些领域的缺陷由用户在生产环境中发现。

**修复：** 每个需求在标记为"已验证"之前应至少有一个测试用例。使用矩阵识别未测试的需求并分配测试用例的创建。
