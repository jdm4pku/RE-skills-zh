## 目的
系统地识别软件项目的所有干系人（Stakeholder）和用户类别（User Class），按类型和影响力进行分类，并制定适当的参与策略。使用此技能可以避免在项目后期才发现关键干系人的代价高昂的错误，通过理解各群体的优先级来解决相互冲突的需求，并确保在正确的时间让正确的人参与。

这不是一份简单的联系人名单——它是一个分析框架，决定了你与谁交流、谁的需求优先、以及如何解决冲突。

## 关键概念

### 干系人类别
并非所有干系人都是平等的。按照与系统的关系对他们进行分类：

- **用户（Users）** -- 直接与系统交互的人
- **客户（Customers）** -- 购买或委托系统的人（可能不是用户）
- **发起人（Sponsors）** -- 资助和授权项目的人
- **领域专家（Domain experts）** -- 了解业务规则的主题专家
- **监管方（Regulators）** -- 施加合规约束的外部方
- **维护人员（Maintainers）** -- 系统上线后负责运营和维护的人

### 用户类别分类法
用户不是一个统一的群体。根据以下维度将其分为不同类别：

- **优先用户类别（Favored）** -- 在设计冲突中优先满足其需求的用户
- **非优先用户类别（Disfavored）** -- 有系统访问权但非主要设计对象（例如，使用管理面板的审计人员）
- **忽略用户类别（Ignored）** -- 明确不为这些用户设计（记录原因）

每个用户类别在以下维度上有所不同：
- 使用频率（每天 vs. 每季度）
- 技术熟练度（专家 vs. 新手）
- 使用的功能子集
- 访问权限级别
- 任务关键性

### 产品代言人模型
为每个用户类别确定一名**产品代言人（Product Champion）**：
- 代表该类别的真实用户
- 有权为该类别做需求决策
- 可持续参与需求细化和验证
- 不是*代替*用户发言的管理者——而是一名实际的从业者

### 干系人权力/利益矩阵

|               | 低利益 | 高利益 |
|---------------|--------|--------|
| **高权力** | 保持满意 | 密切管理 |
| **低权力** | 监控 | 保持知情 |

此矩阵决定参与强度："密切管理"的干系人需要频繁评审；"监控"的干系人只需定期更新。

### 反模式
- **遗漏的干系人** -- 在需求基线化之后才发现监管机构或运维团队
- **用户类别合并** -- 将所有用户视为一个同质群体
- **代理问题** -- 管理者声称代表用户发言，但已多年未亲自从事实际工作

## 应用

使用 `template.md` 获取完整的填写结构。

### 步骤 1：识别所有干系人

从头脑风暴开始。使用以下提示：
- 谁将直接使用系统？
- 谁为系统付费或委托开发？
- 谁将维护或运营系统？
- 谁提供业务规则或领域知识？
- 谁施加法规或合规要求？
- 如果系统故障，谁会受到影响？
- 谁向系统提供数据或从系统获取数据？
- 谁必须批准需求或签署产品验收？

列出每个人的姓名、角色和组织。广撒网——后续可以缩小范围。

### 步骤 2：分类用户类别

对于每组直接用户，确定：

```
用户类别：[名称]
描述：[他们是谁，做什么]
使用频率：[每天 / 每周 / 每月 / 每季度]
技术水平：[专家 / 中级 / 新手]
功能子集：[他们主要使用的功能]
优先级：[优先 / 非优先 / 忽略]
产品代言人：[具体人名，或待定]
```

**优先级决策规则：**
- 如果两个用户类别发生冲突，**优先**类别胜出
- 优先状态应反映业务价值，而非政治权力
- 记录优先级分配的理由

### 步骤 3：将干系人映射到权力/利益矩阵

对于每个非用户干系人：
1. 评估其**权力**（影响项目决策的能力）：高 / 低
2. 评估其**利益**（对项目的关心程度）：高 / 低
3. 将其放入矩阵中
4. 分配参与策略

### 步骤 4：制定参与计划

对于每个干系人或用户类别，记录：
- **参与类型：** 评审、访谈、工作坊、签署
- **频率：** 每个迭代、每月、基于里程碑
- **沟通渠道：** 邮件、会议、Slack、演示会
- **升级路径：** 谁来解决涉及该干系人的争议

### 步骤 5：验证和更新

- 与项目发起人一起审查干系人列表
- 提问："还有谁是我们应该交流的？"
- 每季度或在每个阶段关口重新审视——干系人会变化

```markdown
## 用户类别

### 优先：实验室技术员
- 使用频率：每天（8小时以上）
- 技术水平：中级

- 理由：主要价值驱动者；系统必须能支持日常实验台操作

### 非优先：实验室主任
- 使用频率：每周（用于报告和审批）
- 技术水平：软件新手
- 功能子集：仪表板、审批工作流、合规报告
- 产品代言人：Dr. James Lee

### 忽略：外部审计人员
- 理由：通过导出获取只读合规报告；
  初始版本不设计审计专用 UI
```

## 常见陷阱

### 陷阱 1：将所有用户视为一个群体
**症状：** 需求文档中始终使用"用户"一词，没有类别区分。

**后果：** 设计对谁都不够优化。高级用户觉得太慢；新手觉得太复杂。

**修复：** 至少识别 2-3 个不同的用户类别。即使只是"管理员"与"终端用户"的区分也是一个好的开始。

---

### 陷阱 2：没有产品代言人
**症状：** 需求决策由管理者、架构师或业务分析师做出，没有直接用户输入。

**后果：** 需求反映的是管理层*认为*用户需要什么，而不是用户实际需要什么。

**修复：** 从每个优先用户类别中指定一名真正的从业者作为产品代言人。如果无法接触到真实用户，请升级处理——这是一项项目风险。

---

### 陷阱 3：完全忽视非优先用户
**症状：** 非优先或忽略的用户类别被真正忽略了——没有记录该决策。

**后果：** 项目后期有人问"审计人员怎么办？"时出现突发需求。

**修复：** 明确记录被忽略的用户类别及其理由。这是一个有意识的决策，而非疏忽。

---

### 陷阱 4：静态的干系人列表
**症状：** 干系人分析在项目启动时做一次，之后再也不重新审视。

**后果：** 新的干系人出现（法规变化、组织重组）却未被纳入。

**修复：** 在每个里程碑审查干系人。在迭代回顾中增加一个固定议程项："有新的干系人吗？"
