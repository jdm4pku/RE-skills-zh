## 目的
在需求基线化之前，通过结构化评审、审查、原型验证和概念测试来验证需求。这是"需求已编写"与"开发启动"之间的质量关卡。

需求缺陷的修复成本会随着从需求阶段到设计、编码、测试再到生产阶段的推进而增加 10-100 倍。验证能在成本最低的时刻捕获缺陷。

## 关键概念

### V 模型
需求验证位于 V 模型的左侧：

```
业务需求（Business Requirements）  <----  验收测试（Acceptance Testing）
       |                                         ^
用户需求（User Requirements）      <----  系统测试（System Testing）
       |                                         ^
功能需求（Functional Requirements） <---- 集成测试（Integration Testing）
       |                                         ^
     设计（Design）                <----  单元测试（Unit Testing）
       |                                         ^
       +-----> 实现（Implementation） --------+
```

每个层级的需求对应相应层级的测试。验证确保每个层级在下一层级开始之前是正确的。

### 确认（Validation）与验证（Verification）
- **确认（Validation）：** "我们是否在构建正确的东西？"（需求是否匹配利益相关者的需要）
- **验证（Verification）：** "我们是否正确地构建了它？"（代码是否匹配需求）

本技能专注于确认——在构建之前确认需求的正确性。

### 四种验证技术

| 技术 | 能发现的问题 | 适用场景 |
|------|-------------|---------|
| **正式审查（Formal Inspection）** | 歧义、不完整、不一致 | 关键或受监管系统 |
| **原型验证（Prototyping）** | 可用性问题、被误解的工作流 | UI 密集型功能 |
| **概念测试（Conceptual Testing）** | 遗漏场景、不可测试的需求 | 所有需求 |
| **验收标准评审（Acceptance Criteria Review）** | 模糊的成功标准、遗漏的边界情况 | 每个需求 |

## 应用

### 阶段 1：验证前准备（1-2 小时）

**1.1 就绪检查**
在验证需求之前，确认：
- [ ] 所有 TBD（待定事项）已解决（或标记为已知的未知项）
- [ ] 需求使用"shall"语句或用户故事格式编写
- [ ] 每条需求有唯一标识符
- [ ] 业务规则单独记录（未嵌入需求中）
- [ ] 引用的数据元素的数据字典至少部分完成
- [ ] 可追踪性矩阵将需求链接到业务目标

**1.2 选择验证方法**
使用 `skills/requirements-review-advisor/SKILL.md` 选择评审正式程度级别。

**1.3 准备材料**
- 将需求分发给评审人员（会议前 3 个以上工作日）
- 提供缺陷检查清单
- 提供上下文文档（愿景与范围、利益相关者分析）
- 分配评审角色（主持人、朗读者、审查员）

---

### 阶段 2：正式评审/审查（2-4 小时）

运行在阶段 1 中选定的评审流程：

**2.1 个人准备**（每位评审人员 2-3 小时，在会议之前）
每位评审人员独立完成：
- 使用缺陷检查清单阅读需求
- 记录潜在缺陷，包含类别、严重性和位置
- 记录疑问和歧义之处

**2.2 评审会议**（1-3 小时，取决于数量）
- 朗读者逐条朗读需求
- 审查员提出在准备过程中发现的缺陷
- 小组讨论通过交互发现的新缺陷
- 主持人记录所有缺陷（不在会议中解决——仅识别缺陷）
- 对每个缺陷分类：关键（Critical）/ 重要（Major）/ 次要（Minor）

**2.3 缺陷分类**
对每个缺陷记录：
- 需求 ID
- 缺陷类型（歧义、不完整、不一致、不可行等）
- 严重性（关键 / 重要 / 次要）
- 描述
- 建议的解决方案（可选）

---

### 阶段 3：原型验证（1-3 小时，如适用）

适用于 UI 密集型或工作流密集型功能：

**3.1 构建原型**
- 纸面原型用于早期验证
- 低保真线框图用于工作流验证
- 交互式原型用于详细的 UI 验证

**3.2 进行用户走查**
1. 给用户一个任务："将一种新化学品添加到库存中。"
2. 观察他们与原型的交互
3. 记录：困惑点、错误假设、缺失功能、意外的工作流
4. 在每个界面询问："这是您期望的吗？"

**3.3 记录发现**
- 原型发现对应到需求修改
- UI 期望转化为可用性需求
- 工作流困惑转化为需求澄清

---

### 阶段 4：概念测试（1-2 小时）

在编写代码之前用场景测试需求：

**4.1 创建测试场景**
对每个主要需求或用例，编写 3-5 个测试场景：
- 正常路径（Happy path）场景
- 错误场景（无效输入、系统不可用）
- 边界情况场景（边界值、异常组合）
- 性能场景（负载条件下）

**4.2 逐一走查每个场景**
提问："根据这些需求，系统在此场景下会如何表现？"
- 如果答案清晰 -> 需求可测试且无歧义
- 如果答案不清晰 -> 需求存在歧义或缺口
- 如果答案是"我不知道" -> 需求不完整

**4.3 验证验收标准**
使用 `skills/acceptance-criteria/SKILL.md`：
- 每条需求是否都有验收标准？
- 每个标准是否可以通过特定测试来验证？
- 是否覆盖了边界条件？
- 是否覆盖了否定条件？

---

### 阶段 5：返工与跟进（1-2 小时）

**5.1 处理所有缺陷**
对阶段 2-4 中的每个缺陷：
1. 作者修订需求
2. 主持人验证修复
3. 如果超过 30% 的需求有关键缺陷，安排重新审查

**5.2 更新可追踪性**
- 验证所有修订的需求仍然追溯到业务目标
- 如果验收标准发生变化，更新测试用例映射

**5.3 基线化决策**
在所有缺陷解决之后：
- [ ] 所有关键缺陷已解决
- [ ] 所有重要缺陷已解决或已接受并记录理由
- [ ] 次要缺陷已解决或已推迟并跟踪
- [ ] 可追踪性矩阵已更新
- [ ] 利益相关者签署需求基线

## 常见陷阱

### 陷阱 1：未做准备就评审
**症状：** 评审人员在会议上第一次看到需求。

**后果：** 会议时间花在阅读上而非评审上。缺陷检出率下降 50%。

**修复：** 要求个人预先准备。大多数缺陷应在会议*之前*发现，而非在会议期间。

---

### 陷阱 2：没有概念测试
**症状：** 需求经过了清晰性评审但从未用场景进行测试。

**后果：** 需求在孤立审查时看似正确，但在面对真实场景测试时失败。

**修复：** 对每个主要功能编写 3-5 个测试场景，并走查需求，询问"系统会如何表现？"

---

### 陷阱 3：在会议中修复缺陷
**症状：** 评审会议变成了设计讨论会，缺陷在现场被争论和修复。

**后果：** 会议超时。并非所有需求都得到评审。修复过于仓促。

**修复：** 在会议中只识别和记录缺陷。解决方案由作者在会后离线完成。主持人事后验证修复。

---

### 陷阱 4：评审后未进行基线化
**症状：** 需求经过评审但从未正式基线化。变更在没有控制的情况下继续发生。

**后果：** 评审工作白费，因为需求在没有评估的情况下持续变更。

**修复：** 验证完成后，正式基线化需求。所有后续变更通过 `skills/change-control-advisor/SKILL.md` 进行管理。
