## 目的
创建上下文图，将系统显示为一个单一过程，展示所有外部实体和数据流。使用此技能建立清晰的系统边界，识别所有外部接口，并为利益相关者对齐提供可视化范围定义。

这是数据流图的最高层级（DFD Level 0）。系统是一个气泡。其他一切都是外部的。每个箭头都是一个需要需求的数据流。

## 关键概念

### 上下文图元素

| 元素 | 符号 | 代表 |
|------|------|------|
| 系统 | 单个圆形/气泡 | 正在构建的系统（只有一个） |
| 外部实体（终结者） | 矩形 | 用户、外部系统、设备、组织 |
| 数据流 | 带标签的箭头 | 在系统和外部实体之间移动的数据 |

### 规则
1. 系统始终是一个气泡——不要在上下文图中对其进行分解
2. 外部实体在系统边界之外——你不构建它们
3. 每个数据流都有一个描述移动数据内容的名称（而非方式）
4. 数据流是有方向的——箭头指向数据移动的方向
5. 外部实体之间没有数据流（如果两个外部实体在不经过你的系统的情况下交换数据，则不在范围内）

### 从上下文图到需求
每个元素都会产生需求：
- **每个外部实体** -> 需要用户类别或接口规格说明
- **每个输入数据流** -> 输入验证、数据格式和处理需求
- **每个输出数据流** -> 输出内容、格式、时间和目标需求
- **系统边界** -> 范围定义（哪些在内，哪些在外）

### 超越上下文图：DFD 层级体系
- **生态系统图** -- 展示所有系统及其交互，不仅仅是你的系统。在聚焦到你的系统边界之前，用于了解企业上下文。
- **Level 0 DFD** -- 将单一系统气泡分解为主要过程和内部数据存储。每个主要功能成为自己的气泡，它们之间有数据流。这是上下文图验证后的下一步。
- **Level 1+ DFD** -- 进一步将各个 Level 0 过程分解为子过程。继续分解直到每个过程足够简单，可以直接作为需求来规格说明。

**层级之间的连接：** 进出上下文图的每个数据流必须作为进出 Level 0 DFD 的数据流出现。这称为"平衡"——外部接口必须在各层级之间保持一致。

### 上下文图的启发式问题
构建上下文图时，向利益相关者提问：
- "谁将直接使用这个系统？"（识别用户实体）
- "这个系统与哪些其他系统交互？"（识别系统实体）
- "哪些数据从外部输入？"（识别输入流）
- "哪些数据输出到外部？"（识别输出流）
- "这个系统是否连接任何硬件设备？"（识别设备实体）
- "哪些监管机构或外部组织需要从这个系统获取信息？"（识别组织实体）
- "系统外部是否有任何触发系统内部活动的事物？"（识别事件驱动流）

### 反模式
- **多个系统气泡** -- 上下文图只有一个系统。如果你画了多个系统，你画的是生态系统图。
- **过程分解** -- 在上下文图中显示内部过程。将分解保留给 Level 0 DFD。
- **模糊的数据流** -- 箭头标注为"数据"或"信息"。命名实际的数据："prescription_details"、"compliance_report"。

## 应用

### 步骤 1：放置系统

在中心绘制一个圆圈，并标注系统名称。

### 步骤 2：识别外部实体

从你的利益相关者分析中，列出与系统交互的所有人和事物：
- **用户** -- 来自利益相关者分析的所有用户类别
- **外部系统** -- 系统集成的 API、数据库、服务
- **硬件设备** -- 打印机、扫描仪、传感器
- **组织** -- 监管机构、合作公司、支付处理商

将每个实体作为矩形放置在系统气泡周围。

### 步骤 3：绘制数据流

对于每个外部实体，提问：
- "这个实体向系统发送什么数据？"（输入箭头）
- "系统向这个实体发送什么数据？"（输出箭头）

用数据名称标注每个箭头。使用名词短语："chemical_record"、"expiration_alert"、"compliance_report"。

### 步骤 4：验证

- [ ] 只存在一个系统气泡
- [ ] 每个外部实体至少有一个数据流
- [ ] 每个数据流都有描述性标签（不是"数据"或"信息"）
- [ ] 外部实体之间不存在数据流（那些不在范围内）
- [ ] 利益相关者分析中的所有用户类别都已表示
- [ ] 所有外部系统集成都已表示
- [ ] 与利益相关者一起走查："是否遗漏了什么？"

### 步骤 5：导出需求

对于每个数据流，系统性地创建需求：

**输入流**（外部实体 -> 系统）：
- 包含哪些数据元素？（参考 `skills/data-dictionary/SKILL.md`）
- 适用哪些格式和验证规则？
- 什么触发数据流？（用户操作、计划事件、外部信号？）
- 如果数据无效或不可用，需要什么错误处理？

**输出流**（系统 -> 外部实体）：
- 输出包含什么内容？
- 接收方期望什么格式？
- 什么触发输出？（用户请求、系统事件、计划？）
- 有什么时效性要求？（实时、批处理、按需？）

**从 ChemTrack 上下文图导出的示例：**

| 数据流 | 方向 | 导出的需求 |
|--------|------|-----------|
| chemical_record | 技术员 -> 系统 | REQ-101：系统应接受包含名称、CAS 编号、数量、位置和有效期的化学品记录 |
| expiration_alert | 系统 -> 技术员 | REQ-102：系统应在化学品过期前 30 天通过电子邮件通知实验室技术员 |
| compliance_report | 系统 -> EHS 官员 | REQ-103：系统应按照 EPA 指南每月生成 PDF 格式的合规报告 |
| CAS_lookup_request | 系统 -> PubChem API | REQ-104：系统应在化学品注册期间根据 PubChem 数据库验证 CAS 编号 |

### 步骤 6：连接到 Level 0 DFD（可选的下一步）

在上下文图验证后，分解系统气泡：
1. 识别系统内部的 5-9 个主要过程
2. 识别内部数据存储（数据库、文件）
3. 展示过程之间以及过程与数据存储之间的数据流
4. 验证**平衡性**：上下文图中的每个外部数据流必须出现在 Level 0 边界上

## 常见陷阱

### 陷阱 1：遗漏外部实体
**症状：** 上下文图显示了用户，但没有显示软件集成的外部系统。

**后果：** API、数据库和硬件的接口需求被延迟发现。

**修复：** 系统性地检查：用户、外部系统、硬件设备、监管机构、合作组织。提问："系统是否还与其他任何事物交换数据？"

---

### 陷阱 2：没有名称的数据流
**症状：** 实体和系统之间的箭头没有标签。

**后果：** 没人知道交换了什么数据。无法从图中导出需求。

**修复：** 每个箭头必须有描述性的名词短语标签。如果你无法命名它，说明你对这个交互的理解还不够充分。

---

### 陷阱 3：分解系统
**症状：** 上下文图显示了内部子系统、数据库和处理步骤。

**后果：** 图过于详细，无法作为范围沟通工具。利益相关者看不到边界。

**修复：** 保持系统为一个气泡。在 Level 0 DFD 中分解，而不是在上下文图中。

---

### 陷阱 4：忘记双向流
**症状：** 外部实体只有单方向的箭头（例如，用户发送数据但从未接收任何回馈）。

**后果：** 该实体的输出需求缺失——没有确认、报告或警报。

**修复：** 对于每个实体，明确地问两个问题："它发送什么？"和"它接收什么？"大多数实体都有双向数据流。

---

### 陷阱 5：启发后不更新
**症状：** 上下文图在项目启动时绘制一次，之后从未修订。

**后果：** 在启发过程中发现的新外部实体和数据流未被捕获，导致范围缺口。

**修复：** 将上下文图视为活的制品。每当发现新的外部接口时更新它。在主要启发轮次后与利益相关者重新验证。
