## 目的
创建详细的用例规约（Use Case Specification），捕获用户如何与系统交互以实现特定目标。每个用例记录参与者（Actor）、前置条件、触发条件、正常流程、备选流程、异常和后置条件。当用户故事不足以捕获复杂的交互序列、分支逻辑或异常处理时使用。

这不是用户故事（User Story）——它是一种更详细的行为规约，描述用户与系统之间的完整对话，包括出错时会发生什么。

## 关键概念

### 用例（Use Case）与用户故事（User Story）
两者都捕获用户需求，但详细程度不同：

| 维度 | 用户故事（User Story） | 用例（Use Case） |
|-----------|-----------|----------|
| 详细程度 | 简短（1-3 句话） | 详细（完整流程） |
| 异常处理 | 最少 | 全面 |
| 格式 | 作为…/我想要…/以便… | 带有步骤的结构化模板 |
| 最适用于 | 敏捷待办列表、对话起点 | 复杂流程、受监管系统 |
| 何时使用 | 大多数功能 | 复杂交互、安全关键路径 |

**经验法则：** 从用户故事开始。当交互有 3 个以上备选流程或领域需要详细的异常处理时，升级为用例。

### 用例结构
一个用例包含以下要素：

- **用例 ID（Use Case ID）** -- 唯一标识符（UC-1、UC-2 等）
- **用例名称（Use Case Name）** -- 描述目标的动词短语（如"处理处方"）
- **主要参与者（Primary Actor）** -- 谁发起交互
- **前置条件（Preconditions）** -- 用例开始前必须为真的条件
- **触发条件（Trigger）** -- 什么事件启动用例
- **正常流程（Normal Flow）** -- "正常路径"的逐步序列
- **备选流程（Alternative Flows）** -- 正常流程的有效变体
- **异常（Exceptions）** -- 错误条件及系统如何处理
- **后置条件（Postconditions）** -- 成功完成后为真的条件
- **业务规则（Business Rules）** -- 管理用例内行为的规则（参考 `skills/business-rule/SKILL.md`）
- **优先级（Priority）** -- 高 / 中 / 低
- **频率（Frequency）** -- 此用例发生的频率

### 用例的层级
- **概要级（Summary Level / Kite）** -- 跨越多个会话的高级业务流程（如"管理化学品库存"）
- **用户目标级（User Goal Level / Sea Level）** -- 单个会话中的单个用户目标（如"添加化学品到库存"）-- **最常见**
- **子功能级（Subfunction Level / Fish）** -- 跨用例共享的可复用步骤（如"用户认证"）

### 反模式
- **巨型用例（The Mega Use Case）** -- 一个用例包含 30 个步骤，覆盖所有内容。应在用户目标级别拆分为多个用例。
- **伪装的实现（Implementation in Disguise）** -- 步骤描述 UI 控件（"点击右上角的蓝色按钮"）。应保持步骤技术中立。
- **缺失的异常（Missing Exceptions）** -- 仅有正常流程，没有备选或异常处理。这是大多数缺陷隐藏的地方。

## 应用

使用 `template.md` 获取完整的填写结构。

### 步骤 1：识别用例

从利益相关者分析和用户类别开始：
1. 对每个用户类别，列出他们与系统交互时的目标
2. 每个"用户目标级"的目标成为一个候选用例
3. 用动词短语命名每个用例："下单"、"生成报告"、"登记新化学品"

**识别技术：**
- 从用户故事推导（一个复杂的用户故事可能展开为一个用例）
- 从事件列表推导（每个业务/信号/时间事件暗示一个用例）
- 从上下文图推导（每个数据流暗示交互）
- 询问用户："您来这个系统是为了完成什么？"

### 步骤 2：编写正常流程

将正常路径写成编号步骤：
1. 每个步骤是一次参与者-系统交换
2. 参与者做某事，系统响应（或反之）
3. 保持步骤在一致的抽象层次
4. 使用主动语态："系统显示……"而不是"列表被显示"

**步骤格式：**
```
1. 药剂师扫描处方条形码。
2. 系统检索处方详情并显示患者姓名、药物、剂量和处方医生。
3. 药剂师验证患者身份。
4. 系统根据患者的用药历史检查药物相互作用。
5. 系统显示"未发现相互作用"。
6. 药剂师确认配药。
7. 系统记录配药、更新库存并打印标签。
```

### 步骤 3：识别备选流程

对正常流程中的每个步骤，询问：
- "这里还可能发生什么？"
- "如果用户做出不同的选择呢？"
- "如果数据不同呢？"

命名每个备选流程并引用其分支的步骤：
```
备选流程 3a：无法验证患者身份
  在步骤 3，如果患者无法提供有效证件：
  3a.1 药剂师选择"暂挂处方"
  3a.2 系统将处方标记为"待验证"
  3a.3 用例结束
```

### 步骤 4：识别异常

对每个步骤，询问：
- "什么可能出错？"
- "如果系统不可用呢？"
- "如果数据无效或缺失呢？"

```
异常 4a：检测到药物相互作用
  在步骤 4，如果系统检测到药物相互作用：
  4a.1 系统显示带有严重级别的相互作用警告
  4a.2 药剂师查看相互作用详情
  4a.3 药剂师联系处方医生获取授权
  4a.4 如果获得授权，药剂师输入覆盖代码，
       用例从步骤 6 继续
  4a.5 如果未获得授权，药剂师拒绝该处方，
       用例结束
```

### 步骤 5：定义前置条件和后置条件

**前置条件：** 用例开始*之前*必须为真的条件。这些条件不由用例测试——它们是假设成立的。
```
前置条件：
- 药剂师已使用有效凭证登录
- 处方已存在于系统中（由接待人员录入）
```

**后置条件：** 成功完成*之后*保证为真的条件。
```
后置条件：
- 处方状态为"已配药"
- 该药物的库存数量已递减
- 配药记录已记录，包含药剂师 ID 和时间戳
- 标签已打印
```

### 步骤 6：审查用例

质量检查：
- [ ] 每个步骤都有明确的参与者（用户或系统）
- [ ] 正常流程实现了声明的目标
- [ ] 所有备选流程都已探索（在每个步骤问"还有什么？"）
- [ ] 所有异常流程都有定义的系统行为（错误处理没有"待定"）
- [ ] 前置条件是用例*假设*的事项，而非用例*测试*的事项
- [ ] 后置条件是可验证的结果
- [ ] 步骤是技术中立的（没有特定于 UI 的语言）
- [ ] 用例处于用户目标级别（不会太高，也不会太低）

## 示例

参见 `examples/sample.md` 获取完整的用例示例。

简要示例摘录：

```markdown
**UC-3: 添加化学品到库存**
- **参与者：** 实验室技术员
- **触发条件：** 技术员收到新的化学品货物
- **正常流程：**
  1. 技术员选择"添加化学品"
  2. 系统显示化学品录入表单
  3. 技术员输入化学品名称、CAS 编号、数量、位置、有效期
  4. 系统根据化学品数据库验证 CAS 编号
  5. 系统确认录入并分配库存 ID
- **备选流程 3a：** 化学品已存在于库存中
  - 系统提示更新数量而非创建新条目
- **异常 4a：** 无效的 CAS 编号
  - 系统显示错误，技术员更正或手动输入
```

## 常见陷阱

### 陷阱 1：未记录异常
**症状：** 每个用例都是晴天场景，没有错误处理。

**后果：** 开发人员在编码时自行发明错误处理，且不一致。测试人员没有负面测试用例的基础。

**修复：** 对正常流程中的每个步骤，问"什么可能出错？"每个用例至少记录 2-3 个异常。

---

### 陷阱 2：步骤中包含实现细节
**症状：** "用户点击模态对话框右上角的提交按钮。"

**后果：** 用例与特定的 UI 设计耦合。任何 UI 变更都会使需求失效。

**修复：** 保持步骤技术中立："用户提交表单。"让 UI 设计师决定具体机制。

---

### 陷阱 3：步骤过多
**症状：** 单个用例的正常流程有 25 个以上的步骤。

**后果：** 用例过于复杂，难以审查、测试或作为一个单元实现。

**修复：** 如果正常流程超过 10-12 个步骤，寻找自然断点并拆分为单独的用例。使用"包含（include）"关系处理共享的子功能。

---

### 陷阱 4：参与者是系统，而非人
**症状：** "API 调用服务"——参与者应该是有目标的人类或外部系统。

**后果：** 用例变成系统设计文档而非需求文档。

**修复：** 参与者应该是人（角色）或有目标的外部系统。内部系统组件不是参与者。
