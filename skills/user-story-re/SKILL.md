## 目的
创建满足需求工程标准的用户故事——可追溯、可测试、有优先级的用户需求表达。每个故事遵循"作为/我希望/以便"格式，配有结构化的验收标准，并根据 INVEST 准则进行评估。适用于敏捷或混合环境中以用户故事作为需求制品的场景。

这不是要用便利贴替代正式需求文档。而是要以足够的严谨性编写用户故事，使其能够作为可追溯、可验证的需求，同时保持敏捷以用户为中心、注重对话的精神。

## 关键概念

### 用户故事格式
```
作为 [用户类别或角色]，
我希望 [动作或能力]，
以便 [业务价值或成果]。
```

每个词都必须有其存在的意义：
- **作为** -- 强制识别特定的用户类别（不能写"作为一个用户"）
- **我希望** -- 从用户视角描述能力
- **以便** -- 说明业务价值（不是对动作的重复描述）

### INVEST 准则
在将故事纳入 Sprint 之前，使用此准则作为质量关卡：

| 准则 | 问题 | 警示信号 |
|-----------|----------|----------|
| **Independent（独立性）** | 该故事能否独立于其他故事进行开发和交付？ | "我们必须先完成故事 X 才能做这个" |
| **Negotiable（可协商性）** | 实现方式是否有讨论空间？ | 过于具体的实现细节描述 |
| **Valuable（有价值）** | 是否为用户或客户交付价值？ | "作为开发人员，我想要重构..." |
| **Estimable（可估算）** | 团队能否估算工作量？ | "我们完全不知道这有多复杂" |
| **Small（小粒度）** | 能否在一个 Sprint 内完成？ | Epic 伪装成故事 |
| **Testable（可测试）** | 能否编写测试来验证？ | "系统应该对用户友好" |

### 验收标准格式

**Given/When/Then（Gherkin 格式）：**
```
Given [前置条件]，
When [动作]，
Then [预期结果]。
```

**检查清单格式：**
```
- [ ] [可验证条件 1]
- [ ] [可验证条件 2]
- [ ] [可验证条件 3]
```

**基于规则的格式：**
```
Rule: [必须满足的业务规则]
Example: [该规则实际应用的具体示例]
```

### 用户故事在需求层次中的位置
```
业务需求（愿景和范围）
  -> Epic（大型用户需求）
    -> 用户故事（Sprint 级别的能力）
      -> 验收标准（可测试的条件）
        -> 任务（实现工作）
```

### 反模式
- **技术故事** -- "作为开发人员，我想要升级数据库"（非用户价值）
- **伪装的 Epic** -- 一个故事涵盖 5 个以上的能力
- **模糊的价值** -- "以便我可以使用系统"（陈述显而易见的事情）
- **无验收标准** -- 没有任何方式可以验证完成的故事

## 应用

使用 `template.md` 作为填写结构。

### 步骤 1：识别用户类别
参考你的干系人分析（`skills/stakeholder-analysis/SKILL.md`）。使用具体的用户类别名称，而不是"用户"。

正确："作为实验室技术员"
错误："作为一个用户"

### 步骤 2：编写故事陈述
关注*做什么*（能力）和*为什么*（价值），而不是*怎么做*（实现方式）。

正确："我希望在化学品即将过期时收到警报，以便我能在它成为安全隐患之前进行处置或更换。"
错误："我希望系统发送一封主题为 ALERT 且带有红色图标的邮件，以便我看到警报。"

### 步骤 3：编写验收标准

每个故事编写 3-7 条验收标准。每条标准必须：
- **具体** -- 具体的条件，不能模糊
- **可测试** -- 测试人员可以验证通过/失败
- **独立** -- 每条标准独立成立

```markdown
#### 验收标准：
- [ ] 在化学品过期前 30 天通过邮件发送警报
- [ ] 警报包含化学品名称、CAS 编号、存放位置和过期日期
- [ ] 警报发送给分配到该化学品存储位置的实验室技术员
- [ ] 如果技术员没有登记邮箱，则警报发送给实验室主管
- [ ] 已标记为"已处置"的化学品不发送警报
```

### 步骤 4：添加需求属性

在需求工程场景中，为每个故事补充以下属性：
- **故事 ID** -- 唯一的持久标识符（US-001、US-002）
- **优先级** -- 高/中/低（或 MoSCoW）
- **来源** -- 谁提出了这个需求（干系人、用户类别、法规）
- **业务规则** -- 管控该故事的 BR-ID
- **追溯到** -- 愿景和范围中的业务目标或特性
- **状态** -- 已提议/已批准/已实现/已验证

### 步骤 5：根据 INVEST 准则验证

在接受故事之前，检查每项 INVEST 准则。如有不满足项，进行修改：

- 不独立？识别依赖关系，要么消除依赖，要么对故事进行排序。
- 没有价值？重新编写以表达用户价值，或重新归类为技术任务。
- 不够小？使用拆分技巧：工作流步骤、业务规则、数据变体、CRUD 操作或正常/异常路径。
- 不可测试？添加具体的、可度量的验收标准。

## 示例

参见 `examples/sample.md` 获取完整示例。

简要示例：

```markdown
### US-015：实验室技术员的过期警报
**作为** 实验室技术员，
**我希望** 在化学品过期前 30 天收到邮件警报，
**以便** 我能在它成为安全隐患之前安排处置或更换。

**验收标准：**
- [ ] 在过期日期前 30 天发送邮件
- [ ] 邮件包含：化学品名称、CAS 编号、存放位置、过期日期
- [ ] 邮件发送给分配到该存储位置的技术员
- [ ] 已标记为"已处置"的化学品不发送警报
- [ ] 警报记录在系统审计日志中

**优先级：** 高
**来源：** 实验室技术员用户类别（Maria Santos）
**业务规则：** BR-011
**追溯到：** BO-2（消除过期化学品）
```

## 常见陷阱

### 陷阱 1：没有验收标准的故事
**症状：** "作为用户，我想要搜索化学品。"没有关于什么构成成功搜索的标准。

**后果：** 开发人员实现最简搜索功能。测试人员没有测试依据。争论随之而来。

**解决方法：** 每个故事在进入 Sprint 之前必须至少有 3 条验收标准。

---

### 陷阱 2："以便"重复了"我希望"
**症状：** "我希望登录系统，以便我可以访问系统。"

**后果：** 无法洞察其重要性。无助于确定优先级。

**解决方法：** 深入挖掘真正的价值："以便我可以在不去实验室的情况下查看实验结果。"

---

### 陷阱 3：太大（伪装的 Epic）
**症状：** 一个故事有 15 条验收标准，涵盖多个能力。

**后果：** 无法在一个 Sprint 内完成。复杂度太高，无法估算。

**解决方法：** 按工作流步骤、业务规则、数据变体或正常/异常路径进行拆分。拆分后的每个故事应有 3-7 条验收标准。

---

### 陷阱 4：缺乏可追溯性
**症状：** 待办列表中有 200 个用户故事，但没有与业务目标的关联。

**后果：** 无法回答"我们为什么要构建这个？"无法证明业务需求的覆盖范围。

**解决方法：** 添加"追溯到"属性，将每个故事链接到愿景和范围文档中的业务目标或特性。
