# 用户故事示例（需求工程场景）

## 示例 1：优秀的用户故事

```markdown
### US-015：化学品过期警报

**作为** 实验室技术员，
**我希望** 在我负责的存储区域中的化学品过期前 30 天收到邮件警报，
**以便** 我能在化学品成为安全隐患或违反法规合规要求之前安排处置或更换。

#### 验收标准：
- [ ] 在过期日期前恰好 30 天发送邮件
- [ ] 邮件包含：化学品名称、CAS 编号、数量、存放位置和过期日期
- [ ] 邮件发送给分配到该化学品存储位置的技术员
- [ ] 如果没有分配技术员，则邮件发送给实验室主管
- [ ] 状态为"已处置"或"已转移"的化学品不发送警报
- [ ] 警报记录在系统审计日志中，包含时间戳和接收人

#### 需求属性：
- **优先级：** 高
- **来源：** 实验室技术员用户类别（Maria Santos，产品代言人）
- **业务规则：** BR-011（过期通知时间线）
- **追溯到：** BO-2（消除过期化学品）、FE-2（过期警报）
- **状态：** 已批准

#### INVEST 检查：
- [x] Independent（独立性） -- 不依赖其他故事
- [x] Negotiable（可协商性） -- 可以是邮件、应用内通知或短信（待讨论）
- [x] Valuable（有价值） -- 防止安全隐患和合规违规
- [x] Estimable（可估算） -- 团队估算为 5 个故事点
- [x] Small（小粒度） -- 可在单个 Sprint 内交付
- [x] Testable（可测试） -- 所有验收标准均可验证
```

**为什么这个故事写得好：**
- 具体的用户类别（"实验室技术员"），而不是泛化的"用户"
- 明确的能力描述，有具体的触发条件（过期前 30 天）
- 真实的业务价值（安全 + 合规，而不仅仅是"让我知道"）
- 6 条验收标准，全部可测试
- 完整的可追溯性，关联到业务目标和特性
- 所有 INVEST 准则均通过

## 示例 2：薄弱的用户故事（改进前）

```markdown
### US-099：搜索

**作为** 用户，
**我希望** 搜索东西，
**以便** 我能找到我需要的。

#### 验收标准：
- [ ] 搜索可用
```

**问题：**
- "用户"太泛化——具体是哪个用户类别？
- "搜索东西"——搜索什么？按什么条件搜索？
- "找到我需要的"只是对动作的重复描述
- 只有一条验收标准，且不可测试（"可用"）
- 没有可追溯性、没有优先级、没有来源

**改进后：**

```markdown
### US-023：通过 CAS 编号搜索化学品

**作为** 实验室技术员，
**我希望** 通过 CAS 编号搜索化学品，并查看包含存放位置和过期信息的匹配结果，
**以便** 我能快速找到实验所需的特定化学品，而无需在整个实验室中来回查找。

#### 验收标准：
- [ ] 搜索接受完整或部分 CAS 编号输入
- [ ] 对于最多 50,000 条记录，结果在 2 秒内显示
- [ ] 每条结果显示：化学品名称、CAS 编号、数量、存放位置、过期日期
- [ ] 当用户所在实验室已知时，结果按位置排序（最近的优先）
- [ ] 搜索无匹配时显示"未找到结果"消息
- [ ] 搜索功能可通过每个页面上的固定搜索栏访问

#### 需求属性：
- **优先级：** 高
- **来源：** 实验室技术员用户类别（Maria Santos）
- **业务规则：** 无
- **追溯到：** BO-1（减少报告时间）、FE-1（化学品目录）
- **状态：** 已批准
```
