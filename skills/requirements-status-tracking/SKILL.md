## 目的
指导需求工程师建立需求状态跟踪系统，提供每个需求生命周期状态的可见性。这使得能够以数据驱动的方式回答以下问题："我们进展到哪了？""瓶颈在哪里？""我们能按时发布吗？"

这不是项目管理的替代品。它是以需求为中心的进度视图，通过展示哪些需求已经被规范化、批准、实现和验证——以及哪些处于停滞、延期或风险状态——来补充进度跟踪。

## 关键概念

### 传统状态生命周期

标准需求状态生命周期包含六个主要状态和三个终态：

```
已提议 --> 进行中 --> 已草拟 --> 已批准 --> 已实现 --> 已验证
                        |            |            |
                        v            v            v
                      已延期       已拒绝       已删除
```

| 状态 | 定义 | 进入条件 |
|--------|-----------|----------------|
| **已提议（Proposed）** | 需求已被识别但尚未展开分析 | 利益相关方提交或分析师识别 |
| **进行中（In Progress）** | 需求正在被分析和编写 | 分析师开始展开分析 |
| **已草拟（Drafted）** | 需求已编写完成，等待评审 | 初始规格说明完成 |
| **已批准（Approved）** | 需求已通过评审并纳入基线 | 正式评审通过；获得利益相关方签字 |
| **已实现（Implemented）** | 需求已在系统中实现 | 开发人员确认实现完成 |
| **已验证（Verified）** | 需求已测试并确认正确 | 测试用例通过；验收标准满足 |
| **已延期（Deferred）** | 需求有效但推迟到未来版本 | CCB（变更控制委员会）决定延期 |
| **已删除（Deleted）** | 需求从项目中移除 | CCB 决定；已被替代或不再需要 |
| **已拒绝（Rejected）** | 需求经评审后被认定无效或超出范围 | 评审或 CCB 决定 |

### 敏捷状态变体

适用于使用待办列表（Backlog）和迭代（Sprint）的敏捷团队：

```
待办列表 --> 已定义 --> 进行中 --> 已完成 --> 已接受
                          |                     |
                          v                     v
                        已阻塞               已阻塞
```

| 状态 | 定义 | 进入条件 |
|--------|-----------|----------------|
| **待办列表（In Backlog）** | 用户故事在产品待办列表中，尚未精化 | PO（产品负责人）添加到待办列表 |
| **已定义（Defined）** | 故事已精化，包含验收标准和估算 | 精化会议完成 |
| **进行中（In Progress）** | 故事正在当前迭代中实现 | 迭代规划拉取故事 |
| **已完成（Completed）** | 故事满足完成定义（Definition of Done） | 开发人员标记完成 |
| **已接受（Accepted）** | 产品负责人已接受该故事 | PO 演示和验收 |
| **已阻塞（Blocked）** | 故事因障碍无法继续推进 | 团队识别出阻塞项 |

### 状态转换规则

并非所有转换都是有效的。定义允许的转换：

| 起始状态 | 允许的转换 |
|------|-------------------|
| 已提议 | 进行中、已延期、已拒绝 |
| 进行中 | 已草拟、已延期 |
| 已草拟 | 已批准、进行中（返工）、已拒绝 |
| 已批准 | 已实现、已延期、已删除 |
| 已实现 | 已验证、已批准（验证失败） |
| 已验证 | （终态） |
| 已延期 | 已提议（重新考虑时） |

无效的转换（例如直接从"已提议"到"已验证"）表明流程存在问题。

### 状态分布可视化

状态分布快照展示所有需求当前所处的位置：

```
状态分布（ChemTrack Release 1 -- 第 12 周）

已提议:     |||                           3  (5%)
进行中:     |||||                         5  (9%)
已草拟:     ||||||||                      8  (14%)
已批准:     ||||||||||||                 12  (21%)
已实现:     |||||||||||||||              15  (26%)
已验证:     ||||||||||||                 12  (21%)
已延期:     ||                            2  (4%)
已拒绝:     |                             1  (2%)
-------------------------------------------
总计:                                    58
```

### 进度报告指标

| 指标 | 公式 | 用途 |
|--------|---------|---------|
| **规格完成度** | (已批准 + 已实现 + 已验证) / 总数 | 有多少已准备好进入开发 |
| **实现进度** | (已实现 + 已验证) / 已批准 | 有多少已被构建 |
| **验证进度** | 已验证 / 已实现 | 有多少已被测试 |
| **变更率** | 已变更需求 / 已基线化总数 | 需求有多不稳定 |
| **阻塞率** | 已阻塞 / 进行中 | 有多少条目被卡住 |

### 为什么有效
- **数据驱动的可见性** -- 将"我觉得我们在正轨上"替换为"73% 的已批准需求已实现"
- **瓶颈检测** -- "已草拟"状态的堆积意味着评审流程是瓶颈
- **早期预警** -- 高变更率在影响进度之前就预示范围不稳定
- **利益相关方信心** -- 定期状态报告建立项目处于可控状态的信任

### 反模式
- **状态表演** -- 为了报告而更新状态，但不验证实际进展。"已实现"意味着开发人员说完成了，但没人检查过。
- **缺少终态** -- 不跟踪已延期、已删除或已拒绝的需求。这些需求从视野中消失，导致总数不一致。
- **无转换规则** -- 任何状态都可以变为任何其他状态。需求从"已提议"直接跳到"已验证"，破坏了生命周期。

## 应用

使用 `template.md` 获取完整的仪表盘结构。

### 步骤 1：定义状态生命周期

选择传统或敏捷生命周期（或混合模式）。以 ChemTrack 为例，使用传统生命周期：

1. 记录状态定义（参见上方表格）
2. 记录允许的转换
3. 定义每个状态的进入条件
4. 获得团队对定义的共识

### 步骤 2：初始化状态登记表

为每个已基线化的需求设置初始状态：
- 已评审和批准的需求从"已批准"开始
- 仍在展开分析的需求从"进行中"或"已草拟"开始
- 来自变更请求的新需求从"已提议"开始

```
初始状态登记表（ChemTrack，基线 v1.0）：
- 42 个功能需求：42 个已批准
- 15 个非功能需求：15 个已批准
- 3 个待处理变更请求：3 个已提议
```

### 步骤 3：建立更新节奏

定义何时以及如何更新状态：
- **每日站会** -- 开发人员报告实现完成情况
- **迭代评审** -- QA 和 PO 确认已验证状态
- **每周** -- BA（业务分析师）更新已提议/进行中/已草拟状态
- **CCB 会议** -- 已延期/已拒绝/已删除状态变更

### 步骤 4：生成状态分布

在每个报告间隔生成快照：

```
ChemTrack Release 1 -- Sprint 6 状态报告

功能需求（共 42 个）：
  已批准:      8  (19%)  -- 准备进入开发
  已实现:     22  (52%)  -- 已构建，等待测试
  已验证:     10  (24%)  -- 已测试并接受
  已延期:      2  (5%)   -- 移至 Release 2

非功能需求（共 15 个）：
  已批准:      5  (33%)
  已实现:      6  (40%)
  已验证:      4  (27%)

变更请求（共 3 个）：
  已提议:      1  (33%)  -- 等待 CCB 评审
  已批准:      1  (33%)  -- 准备进入开发
  已实现:      1  (33%)  -- 已构建，等待测试
```

### 步骤 5：计算进度指标

```
规格完成度:    (42 + 15) / (42 + 15 + 3) = 95%
实现进度:      (22 + 10) / 42 = 76%（功能需求）
验证进度:      10 / 32 = 31%（功能需求，占已实现的比例）
变更率:        3 / 57 = 5.3%（3 个变更请求对应 57 个已基线化需求）
```

### 步骤 6：识别并报告瓶颈

查找异常分布：
- **"已草拟"堆积** -- 评审流程是瓶颈。增加评审人员或提高评审频率。
- **"已实现"堆积** -- 测试是瓶颈。需要更多 QA 资源。
- **项目后期"已提议"数量高** -- 范围仍在被发现。风险标记。
- **需求在同一状态停留多个迭代** -- 逐个调查。

### 步骤 7：向利益相关方报告

在每个里程碑产出简洁的状态报告：
- 状态分布图
- 关键指标（规格完成度、实现进度、验证进度）
- 瓶颈分析及建议措施
- 趋势对比（本次迭代与上次迭代）

## 常见陷阱

### 陷阱 1：没有进入条件的状态
**症状：** 任何人可以在任何时候将需求状态更改为任何值。

**后果：** "已实现"对每个人的含义不同。有人在编码开始时就标记为已实现；有人在测试通过后才标记。

**修复：** 为每个状态转换定义进入条件。"已实现"意味着代码已提交、单元测试通过且代码评审已批准。记录并强制执行。

---

### 陷阱 2：不跟踪终态
**症状：** 已延期和已删除的需求从跟踪系统中消失。

**后果：** 需求总数莫名其妙地变化。利益相关方好奇之前讨论过的功能去了哪里。

**修复：** 将已延期、已删除和已拒绝的需求保留在登记表中并标记终态。它们应该在报告中可见，即使从活动视图中被过滤。

---

### 陷阱 3：过时的状态数据
**症状：** 状态更新仅在每月或管理层评审前才进行。

**后果：** 状态报告总是落后现实 2-4 周。瓶颈被发现时已来不及解决。

**修复：** 在转换发生时就更新状态，而不是批量更新。将状态跟踪集成到每日站会和迭代仪式中。

---

### 陷阱 4：没有上下文的指标
**症状：** 报告显示"76% 已实现"但不解释这对进度意味着什么。

**后果：** 利益相关方无法判断在项目当前阶段 76% 是好、坏还是符合计划。

**修复：** 始终为指标配上上下文：计划值与实际值、趋势方向，以及简短评估（"正常"、"有风险"、"落后"）。

---

### 陷阱 5：过度跟踪
**症状：** 需求经历 12 个状态，伴随复杂的工作流和审批关卡。

**后果：** 状态跟踪变成了负担。团队成员花更多时间更新状态而不是做实际工作。

**修复：** 使用能提供有用可见性的最少状态数。六到八个状态对大多数项目来说已经足够。
