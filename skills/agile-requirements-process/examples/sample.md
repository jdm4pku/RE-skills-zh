# 敏捷需求过程示例：ChemTrack 基于 Sprint 的需求工程

## 背景
ChemTrack 化学品库存管理系统正在使用 Scrum 进行开发，采用 2 周的 Sprint。大学实验室管理办公室是发起人。团队成员：1 名 Product Owner（陈博士，实验室主任）、1 名 BA/Scrum Master、3 名开发人员、1 名 QA。

---

## 阶段 1：初始愿景（Sprint 0，第 1 周）

### 轻量级愿景声明

**对于** 大学实验室管理人员和技术人员
**他们** 需要追踪危险化学品库存、确保法规合规，并减少过期化学品浪费，
**ChemTrack** 系统
**是一个** 基于 Web 的库存管理应用
**它** 提供实时库存可见性、自动过期提醒和一键合规报告，
**不同于** 当前基于电子表格的追踪流程，
**我们的产品** 消除手工数据录入错误，并在无需专职合规人员的情况下确保持续的 EPA/OSHA 合规。

### 初始用户画像草案

| 用户画像 | 目标 | 痛点 |
|---------|-------|------------|
| 实验室技术人员（主要用户） | 快速登记化学品，获取过期提醒 | 当前的电子表格速度慢且容易出错 |
| EHS 官员（关键干系人） | 按需生成合规报告 | 手动组装报告需要 2 天以上 |
| 实验室主任（发起人） | 将过期化学品浪费减少 50% | 无法查看跨实验室的库存情况 |

### 范围边界（轻量级）

**Release 1 范围内：** 化学品 CRUD、过期提醒、基本合规报告、SSO 登录
**Release 1 范围外：** 条码扫描、采购集成、多校区支持
**决策依据：** Release 1 聚焦于替代电子表格并满足即将到来的 EPA 审计（3 个月后）所需的最小功能集。

---

## 阶段 2：Backlog 种子创建（Sprint 0，第 2 周）

### Epic 识别

| Epic | 业务目标 | T 恤尺码 |
|------|-------------------|-------------|
| E-1: 化学品登记 | 替代电子表格的化学品添加/编辑功能 | L |
| E-2: 过期管理 | 自动提醒以减少过期浪费 | M |
| E-3: 合规报告 | 一键生成 EPA/OSHA 报告 | M |
| E-4: 用户认证 | 与大学身份系统的 SSO 集成 | S |

### 初始用户故事（来自 E-1: 化学品登记）

```markdown
### US-101: 登记新化学品
- **作为** 实验室技术人员
- **我想要** 通过输入化学品名称、CAS 编号、数量和存储位置来登记新化学品
- **以便** 库存准确，并且可以追踪化学品以满足合规要求

#### 验收标准：
- 假设我已登录并在登记页面上
- 当我提交一个包含有效 CAS 编号、名称、数量和位置的化学品时
- 那么该化学品在 1 秒内出现在我实验室的库存中

### US-102: 验证 CAS 编号
- **作为** 实验室技术人员
- **我想要** 在登记时根据 PubChem 验证我的 CAS 编号
- **以便** 我不会意外登记带有错误标识符的化学品

### US-103: 编辑化学品记录
- **作为** 实验室技术人员
- **我想要** 更新现有化学品的数量或位置
- **以便** 在我移动或使用化学品后，库存反映当前实际情况

### US-104: 查看实验室库存
- **作为** 实验室技术人员
- **我想要** 按位置排序查看我实验室的所有化学品
- **以便** 我可以快速找到所需物品并发现缺口
```

### INVEST 检查（US-101）

| 标准 | 评估 | 通过？ |
|-----------|-----------|-------|
| Independent（独立的） | 可以不依赖 US-102 进行开发（验证可以后续添加） | 是 |
| Negotiable（可协商的） | CAS 编号在第一次迭代中可以是可选的 | 是 |
| Valuable（有价值的） | 直接替代电子表格录入——核心价值 | 是 |
| Estimable（可估算的） | 团队估算为 5 个故事点 | 是 |
| Small（小的） | 单个登记表单——一个 Sprint 内可完成 | 是 |
| Testable（可测试的） | AC 是具体的：提交 → 出现在库存中 | 是 |

## 阶段 3：Sprint 1 规划

### Sprint 1 故事选择

**Sprint 目标：** 实验室技术人员可以登记和查看化学品（核心 CRUD）。

| 故事 | 点数 | 优先级 | 依据 |
|-------|--------|----------|-----------|
| US-101: 登记新化学品 | 5 | 必须 | 核心价值主张 |
| US-103: 编辑化学品记录 | 3 | 必须 | 准确性所需 |
| US-104: 查看实验室库存 | 5 | 必须 | 用户需要看到他们输入的内容 |
| US-401: SSO 登录 | 3 | 必须 | 所有访问的前提 |
| **合计** | **16** | | **速率估算：18 点** |

### 即时细化（US-101）

Sprint 规划期间编写的详细验收标准：

```markdown
### US-101: 登记新化学品（已细化）

#### 验收标准：
1. 假设我已登录，当我导航到"添加化学品"时，那么我看到以下字段：化学品名称、CAS 编号、数量、单位、存储位置、过期日期、危险类别
2. 假设我输入有效的 CAS 编号，当我提交时，那么化学品被保存并出现在我的实验室库存中
3. 假设我将化学品名称留空，当我提交时，那么我看到错误提示"化学品名称为必填项"
4. 假设我输入数量 ≤ 0，当我提交时，那么我看到错误提示"数量必须为正数"
5. 假设我提交成功，那么系统记录我的用户名和时间戳作为创建者

#### 业务规则：
- BR-101: 每种化学品必须有 CAS 编号或明确的"无 CAS"标记
- BR-102: 存储位置必须引用大学房间数据库中的有效实验室房间

#### 数据需求：
- 化学品实体：name, CAS_number, quantity, unit, storage_location_id, expiration_date, hazard_class, created_by, created_at
```

## 阶段 4：即时细化（Sprint 2 准备）

### 即将进行：过期管理（E-2）

在 Sprint 1 期间，BA 在开发人员构建 Sprint 1 内容的同时细化 Sprint 2 的故事：

```markdown
### US-201: 设置过期提醒阈值
- **作为** 实验室主任
- **我想要** 配置过期前多少天发送提醒（默认：30 天）
- **以便** 实验室有足够的时间使用或处置即将过期的化学品

### US-202: 接收过期提醒
- **作为** 实验室技术人员
- **我想要** 在我实验室的化学品即将过期时收到邮件提醒
- **以便** 我可以在过期前使用、处置或申请替换

### US-203: 查看即将过期化学品仪表板
- **作为** EHS 官员
- **我想要** 查看所有实验室中 30/60/90 天内即将过期的所有化学品仪表板
- **以便** 我可以优先安排处置行动并确保合规
```

### 分析模型（刚好够用）

对于过期提醒逻辑，需要一个状态转换图：

```
[活跃] --到达过期阈值--> [已发送提醒]
[已发送提醒] --化学品已使用--> [已消耗]
[已发送提醒] --过期日期已过--> [已过期]
[已过期] --已处置--> [已处置]
[活跃] --已处置--> [已处置]
```

该模型使用 `skills/state-modeling/SKILL.md` 创建——它揭示了原始故事中未包含的"已过期"状态和"已处置"转换。新增：

```markdown
### US-204: 标记化学品为已处置
- **作为** 实验室技术人员
- **我想要** 将过期或未使用的化学品标记为已处置，并记录处置方法和日期
- **以便** EHS 官员有合规报告的审计追踪记录
```

## 阶段 5：持续验证

### Sprint 1 评审（验证）

**参会者：** 陈博士（PO）、EHS 官员、2 名实验室技术人员、开发团队

**演示结果：**
- US-101（登记）：已接受。陈博士要求添加危险品象形图显示——作为 US-105 添加到 Backlog。
- US-103（编辑）：已接受。轻微 UI 反馈——技术人员建议数量变更应显示之前的值。添加 US-106。
- US-104（查看）：有变更地接受——按过期日期排序，而不是按位置排序。故事已更新。
- US-401（SSO 登录）：已接受。

**评审中发现的新需求：**
- US-105: 在化学品记录上显示 GHS 危险品象形图（可以有——Sprint 4 及以后）
- US-106: 在编辑时显示数量变更历史（应该有——Sprint 3）

**实际速率：** 16 点（与估算一致——良好的校准）

### Sprint 1 回顾（过程改进）

| 做得好的 | 需要改进的 |
|-------------|----------------|
| 即时细化使故事保持新鲜 | 需要更早发现业务规则——BR-102（房间数据库）在开发期间才被发现 |
| PO 可用于日常问题解答 | E-2 的状态建模应在 Sprint 规划前完成，而非期间 |
| 验收标准防止了歧义 | 需要一个轻量级数据字典来统一共享术语（CAS 编号、危险类别） |

**行动：** 在每个 Sprint 的最后 2 天增加一次"发现会议"，根据需要使用建模来细化下一个 Sprint 的故事。参考 `skills/analysis-advisor/SKILL.md` 选择合适的模型。

---

## 关键要点

**与传统需求工程相比，什么保持不变：**
- 仍然需要愿景和范围（只是更轻量）
- 干系人识别仍然重要
- 业务规则仍然需要捕获
- 质量属性仍然需要规约（Sprint 3 中添加了响应时间的非功能需求）
- 可追溯性仍然维护（故事 → 验收标准 → 测试用例）

**什么改变了：**
- 没有预先的 SRS——需求即时细化
- 用户故事替代了大多数功能的完整用例
- 状态建模选择性使用（仅用于复杂行为，如过期生命周期）
- 验证在每个 Sprint 评审中进行，而非在正式关卡
- 变更控制通过 Backlog 梳理进行，而非 CCB 流程
