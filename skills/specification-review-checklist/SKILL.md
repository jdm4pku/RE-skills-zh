## 目的
提供结构化检查清单，系统地审查单个需求和完整的SRS文档。在审查（Inspection）、同行评审（Peer Review）或自我审查中使用，在需求基线化并移交开发之前检测缺陷。

这不是运行审查会议的流程——而是一组质量检查清单。有关审查流程本身，请参阅 `skills/requirements-review-advisor/SKILL.md`。

## 关键概念

### 编写良好的单个需求的特征

每个单独的需求应具备以下10个属性：

| # | 属性 | 定义 | 测试问题 |
|---|------|------|----------|
| 1 | 完整性（Complete） | 包含所有必要信息 | 开发人员能否在不提问的情况下实现此需求？ |
| 2 | 正确性（Correct） | 准确反映利益相关者的需要 | 利益相关者是否确认这正是他们所需要的？ |
| 3 | 可行性（Feasible） | 可在已知约束条件下实现 | 开发团队是否确认这是可实现的？ |
| 4 | 必要性（Necessary） | 可追溯到业务需求或利益相关者请求 | 如果移除此需求会发生什么？ |
| 5 | 已确定优先级（Prioritized） | 已分配相对于其他需求的重要性 | 此需求是否与竞争需求进行了排序？ |
| 6 | 无歧义性（Unambiguous） | 只有一种解释方式 | 两个读者是否可能有不同的解读？ |
| 7 | 可验证性（Verifiable） | 可以被测试或演示 | 我能否为此编写测试用例？（参见 `skills/requirements-testing/SKILL.md`） |
| 8 | 一致性（Consistent） | 不与其他需求矛盾 | 此需求是否与其他需求冲突？ |
| 9 | 可修改性（Modifiable） | 可以修改而不产生连锁影响 | 此需求是否只表述一次并通过交叉引用使用？ |
| 10 | 可追溯性（Traceable） | 具有唯一ID，可追溯到来源和测试 | 我能否从利益相关者需求追溯到测试用例？ |

### 编写良好的SRS的特征

SRS文档整体应具备以下8个属性：

| # | 属性 | 定义 | 测试问题 |
|---|------|------|----------|
| 1 | 完整性（Complete） | 所有需求都已包含；不存在待定（TBD）项 | 是否存在空白、占位符或未定义的章节？ |
| 2 | 一致性（Consistent） | 需求之间没有矛盾 | 是否有两个需求指定了冲突的行为？ |
| 3 | 可修改性（Modifiable） | 组织结构便于修改且不产生副作用 | 每个需求是否只陈述一次并通过交叉引用使用？ |
| 4 | 可追溯性（Traceable） | 每个需求都有前向和后向链接 | 每个需求是否都能追溯到来源和测试？ |
| 5 | 正确性（Correct） | 每个需求都准确陈述了真实需要 | 内容是否已与利益相关者确认？ |
| 6 | 已排序（Ranked） | 需求按重要性排序 | 是否分配了指导实施顺序的优先级？ |
| 7 | 无歧义性（Unambiguous） | 没有需求存在多种解释 | 文档是否经过多位读者审查？ |
| 8 | 可验证性（Verifiable） | 每个需求都可以被客观验证 | 是否可以为每个需求编写验收测试？ |

### 缺陷分类法

在审查过程中对每个发现进行分类：

| 缺陷类型 | 定义 | 示例 |
|----------|------|------|
| 歧义性（Ambiguity） | 需求可以有多种解释 | "系统应快速处理交易" |
| 不完整性（Incompleteness） | 需求缺少实现所需的信息 | "系统应验证输入"（哪个输入？什么验证？） |
| 不正确性（Incorrectness） | 需求未准确反映利益相关者的需要 | 需求说30天告警，但利益相关者需要60天 |
| 不一致性（Inconsistency） | 需求与SRS中的另一个需求矛盾 | 需求5.1说3秒响应；需求7.2说5秒响应 |
| 不可验证性（Unverifiability） | 没有客观方法判断需求是否被满足 | "系统应直观易用" |
| 不可行性（Infeasibility） | 需求无法在约束条件内实现 | "系统对所有查询的响应时间应在1毫秒内" |
| 冗余性（Redundancy） | 相同需求在多处陈述且略有差异 | 化学品名称验证在三个不同章节中指定 |
| 镀金（Gold-plating） | 需求添加了没有利益相关者请求的功能 | 开发人员添加了不在任何用户故事中的"自动建议"功能 |

### 为什么有效

结构化检查清单能捕获非正式阅读遗漏的缺陷。研究表明，结构化审查比随意审查每小时发现的缺陷数多2-3倍。检查清单确保审查人员明确检查每个质量属性，而不是将需求当作散文来阅读。

### 反模式
- **无检查清单审查** -- 像阅读小说一样阅读需求，而不是系统地检查质量属性
- **作者审查自己的工作** -- 编写需求的人是唯一的审查者（盲点对作者来说是不可见的）
- **审查过晚** -- 在编写数月后才审查完整的SRS，而不是增量审查
- **审查中修复** -- 在审查会议期间试图修复缺陷，而不是记录并在之后修复

## 应用

使用 `template.md` 作为综合审查检查清单。

### 步骤1：选择审查范围

确定要审查的内容：
- **单个需求审查：** 对每个需求应用10属性检查清单
- **SRS级别审查：** 对整个文档应用8属性检查清单
- **聚焦审查：** 针对特定缺陷类型进行审查（如歧义性通过、完整性通过）

### 步骤2：单个需求审查

对每个需求，依据10个属性进行评估：

```
需求ID：[ID]
文本："[需求文本]"

[ ] 完整性 -- 实现所需的所有信息都存在？
[ ] 正确性 -- 已与利益相关者确认？
[ ] 可行性 -- 已由开发团队确认？
[ ] 必要性 -- 可追溯到业务需求？
[ ] 已确定优先级 -- 已分配优先级？
[ ] 无歧义性 -- 只有一种可能的解释？
[ ] 可验证性 -- 可编写测试用例？
[ ] 一致性 -- 与其他需求没有冲突？
[ ] 可修改性 -- 只陈述一次，其他地方交叉引用？
[ ] 可追溯性 -- 有唯一ID、来源链接、测试链接？
```

### 步骤3：检查常见歧义指标

标记包含以下词语的需求以进行更仔细的检查：

| 歧义术语 | 问题 | 修复方式 |
|----------|------|----------|
| "适当的"（appropriate） | 谁来决定什么是适当的？ | 指定具体标准 |
| "用户友好"（user-friendly） | 主观的，不可测试 | 定义可用性指标 |
| "快速"（fast/quickly） | 没有可衡量的阈值 | 以秒为单位指定响应时间 |
| "灵活"（flexible） | 对不同人意味着不同的事情 | 指定什么必须是可配置的 |
| "健壮"（robust） | 模糊的质量声明 | 指定错误处理和恢复行为 |
| "无缝"（seamless） | 未定义的集成期望 | 明确指定集成行为 |
| "等等"（etc./and so on） | 不完整的枚举 | 明确列出所有项目 |
| "如果可能"（if possible） | 不清楚的承诺级别 | 将其设为明确需求或删除 |
| "应该"vs"必须"（should vs shall） | 歧义的义务级别 | 强制性使用"必须"（shall），可选的则删除 |
| "支持"（support） | 未指定系统具体做什么 | 指定确切的功能 |

### 步骤4：SRS级别审查

审查文档整体：

```
[ ] 完整性 -- 没有TBD章节遗留？
[ ] 完整性 -- 所有用例都有对应的功能需求？
[ ] 完整性 -- ERD中的所有数据实体都有对应的数据字典条目？
[ ] 一致性 -- 各章节之间没有冲突的需求？
[ ] 一致性 -- 全文术语使用一致？
[ ] 可修改性 -- 需求只陈述一次并通过交叉引用使用？
[ ] 可追溯性 -- 每个需求都有唯一ID？
[ ] 可追溯性 -- 可追溯性矩阵将需求链接到来源和测试？
[ ] 正确性 -- 内容已与利益相关者确认？
[ ] 已排序 -- 所有需求都已分配优先级？
[ ] 无歧义性 -- 术语表定义了所有领域术语？
[ ] 可验证性 -- 所有质量属性需求都有适配标准？
```

### 步骤5：记录缺陷

对每个发现，记录：
- 需求ID（或SRS级别发现的章节号）
- 缺陷类型（来自分类法）
- 严重程度（严重 / 主要 / 次要）
- 缺陷描述
- 建议的解决方案

### 步骤6：计算审查指标

跟踪审查效果：
- 每页或每个需求发现的缺陷数
- 按类型的缺陷分布（哪些类型占主导？）
- 按章节的缺陷分布（哪些章节问题最多？）

## 示例

参见 `examples/sample.md`，了解使用此检查清单对ChemTrack需求进行的完整审查。

简要示例：

```markdown
## 需求 CT-FR-05
"系统应以用户友好的方式显示搜索结果。"

### 审查发现：
| 属性 | 通过？ | 发现 |
|------|--------|------|
| 完整性 | 否 | 未指定显示哪些字段或结果如何排序 |
| 无歧义性 | 否 | "用户友好"没有客观定义 |
| 可验证性 | 否 | 无法为"用户友好的方式"编写测试 |
| 一致性 | -- | 未检测到冲突 |

### 记录的缺陷：
1. [歧义性] "用户友好" -- 替换为具体的布局和可用性标准
2. [不完整性] 缺少显示字段、排序顺序和分页的规格说明
3. [不可验证性] 没有可用性的适配标准 -- 添加可衡量的目标

### 建议改写：
"系统必须以表格形式显示化学品搜索结果，包含化学品名称、
CAS编号、存放位置和数量，按化学品名称升序排列。系统必须
每页最多显示50条结果并提供分页控件。"
```

## 常见陷阱

### 陷阱1：检查清单疲劳
**症状：** 审查人员匆忙浏览检查清单，勾选复选框而未进行真正的评估。

**后果：** 缺陷通过审查未被发现。检查清单变成一种形式。

**修复：** 轮换审查人员，将审查会议限制在1-2小时，采用聚焦通过方式（一次检查一个属性）而不是在一次通过中检查每个需求的所有10个属性。

---

### 陷阱2：无缺陷分类
**症状：** 审查发现以自由文本评论形式记录，没有分类。

**后果：** 无法识别模式（例如，"我们80%的缺陷是歧义性问题"）。无法衡量随时间的改进。

**修复：** 使用缺陷分类法。按类型和严重程度分类每个发现。跨审查跟踪统计数据。

---

### 陷阱3：一次审查过多
**症状：** 在一次马拉松式会议中审查200页的SRS。

**后果：** 第一个小时后审查质量下降。后面的章节受到的审查更少。

**修复：** 每次审查15-20页或30-50个需求。安排多次会议。

---

### 陷阱4：跳过SRS级别审查
**症状：** 单个需求通过审查，但SRS整体存在空白：缺失的用例、不一致的术语、各章节间冲突的需求。

**后果：** 树木看起来没问题，但森林是有问题的。

**修复：** 同时进行单个需求审查和SRS级别审查。它们捕获不同类型的缺陷。

---

### 陷阱5：无后续跟进
**症状：** 审查期间记录了缺陷，但从未跟踪到解决。

**后果：** 审查工作白费。相同的缺陷持续到开发阶段。

**修复：** 将每个缺陷分配给责任人并设定解决截止日期。在下一轮中重新审查已修正的需求。
