# 需求分析过程示例

## 示例：ChemTrack 分析会议输出

```markdown
# 需求分析：化学品目录功能

**日期：** 2025-03-28
**分析师：** Sarah Chen
**输入：** 发现研讨会笔记（2025-03-25）、Tom Rivera访谈
（2025-03-26）、Maria Santos观察会议（2025-03-27）

---

## 第一阶段：需求获取输出分类

### 功能需求（草案）
- 按名称、CAS编号、位置、日期搜索化学品
- 添加新的化学品记录
- 更新化学品数量
- 带日志记录的化学品处置
- 生成过期警报
- 生成合规报告

### 已识别的业务规则
- BR-008：CAS编号必须经过验证（格式检查）
- BR-011：在过期前30天发出警报
- BR-012：过期化学品不能用于实验

### 数据需求
- 化学品记录字段：名称、CAS编号、数量、单位、位置、
  过期日期、危险等级、安全数据表（SDS）链接
- 警报记录：化学品引用、类型、日期、接收人、状态
- 报告记录：类型、期间、格式、内容

### 待解决问题
- Q1：化学品能否在实验室之间转移？（需要与Dr. Lee确认）
- Q2：处置后警报历史怎么处理？（需要EHS意见）
- Q3：每个位置是否有化学品数量上限？（物理约束？）

---

## 第二阶段：已创建的可视化模型

### 状态模型：化学品记录
[参见 skills/state-modeling/examples/sample.md 获取完整模型]
状态：活跃、即将过期、已过期、已处置、已转移
事件：添加、三十天标记、过期、处置、转移、续期

从状态表中发现的关键问题：需要定义当有人试图对已过期化学品
进行"续期"时会发生什么（答案：必须先处置，不能续期——
创建了业务规则BR-013）。

### 决策表：处置授权
[参见 skills/decision-table/examples/sample.md 获取完整表格]
3个条件（是否危险品？>5kg？是否过期？）-> 8条规则

关键发现：发现需要BR-019（危险品处置审批）和BR-020
（危险物品文档要求）——在任何需求获取会议中均未提及。

---

## 第三阶段：分解后的需求

来自利益相关者陈述"我需要知道化学品什么时候过期"：

| 编号 | 需求 | 来源 | 业务规则 |
|------|------|------|----------|
| CT.ALERT.EXPIRY.1 | 应在过期前30天发送电子邮件 | Maria Santos | BR-011 |
| CT.ALERT.EXPIRY.2 | 应在过期前7天发送紧急电子邮件 | Maria Santos | BR-011 |
| CT.ALERT.EXPIRY.3 | 在已过期状态下，应显示红色"已过期"横幅 | Tom Rivera | BR-012 |
| CT.ALERT.EXPIRY.4 | 如果已过期，应阻止分配到实验中 | Tom Rivera | BR-012 |
| CT.ALERT.EXPIRY.5 | 应将所有警报记录到审计追踪中 | Tom Rivera | BR-025 |

---

## 第四阶段：数据分析

### CRUD矩阵发现

| 缺失的操作 | 实体 | 发现 |
|------------|------|------|
| 警报无只读操作 | expiration_alert | 需要一个"警报历史"视图 |
| 报告无更新操作 | compliance_report | 报告不可变（正确，法规要求） |
| 用户无删除操作 | user_account | 大学SSO管理账户。正确。 |

发现的新需求：CT.ALERT.HISTORY.1 -- 系统应提供警报历史视图，
显示所有已发送的警报，包括日期、接收人和确认状态。

---

## 第五阶段：已解决的冲突

| 冲突 | 利益相关者A | 利益相关者B | 解决方案 |
|------|------------|------------|----------|
| 警报时间 | Tom（30天） | Maria（14天就够了） | 采用30天（EHS采购周期要求）。Maria在看到处置时间线后表示同意。 |
| 过期化学品处理 | Dr. Lee（允许覆盖使用） | Tom（不允许例外） | Tom胜出（法规要求）。根据EPA规定，过期化学品不允许覆盖使用。 |

---

## 第六阶段：完整性检查

- [x] 上下文图所有数据流都有对应需求
- [x] 状态表完全填充（5个状态 x 8个事件 = 40个单元格）
- [x] CRUD矩阵完成——发现了1个新需求
- [x] 决策表完成（处置的8/8条规则）
- [x] 所有3个用户类别都有用例
- [x] 所有正常流程步骤都指定了错误处理
- [ ] 质量属性待定（计划在下周）
- [x] 待解决问题：3个中已解决2个，Q3推迟到第2版

### 通过分析发现的新需求总数：7
（任何需求获取会议中都未提及——通过建模发现）
```

**为什么这样做有效：**
- 系统化分类将混乱的笔记转化为有组织的类别
- 可视化模型（状态表、决策表）发现了7个利益相关者未提及的需求
- 冲突记录有清晰的解决方案和理由
- CRUD矩阵发现了一个缺失的功能（警报历史视图）
- 完整性检查提供了具体的质量关卡
