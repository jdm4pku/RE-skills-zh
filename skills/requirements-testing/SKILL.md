## 目的
在编写代码之前直接从需求中推导测试用例。使用此技能验证每个需求是否可测试，暴露过于模糊而无法测试的需求，并生成与利益相关者期望一致的早期验收测试计划。

这不是软件测试方法论——而是一种需求质量技术。从需求编写测试的过程本身就能揭示需求中的缺陷：模糊性、不完整性和不可测试的陈述。

## 关键概念

### 可测试性作为质量属性

一个需求是可测试的，当且仅当存在一个有限的、成本可控的过程来确定已实现的系统是否满足该需求。

**可测试的：**
```
系统应在3秒内显示搜索结果，
适用于返回最多1000条化学品记录的查询。
```

**不可测试的：**
```
系统应快速显示搜索结果。
```

两者的区别在于**适合性标准（fit criterion）**——一个量化的、可衡量的阈值，定义了"快速"的含义。

### 适合性标准（Fit Criteria）

每个需求都需要一个适合性标准，使其可以被客观验证：

| 需求类型 | 适合性标准示例 |
|---------|-------------|
| 性能 | 95%的查询响应时间 <= 3秒 |
| 可用性 | 新用户在5分钟内无需帮助即可完成核心任务 |
| 可靠性 | 系统月度正常运行时间 >= 99.5% |
| 容量 | 支持500个并发用户且无性能下降 |
| 功能 | 添加到库存的化学品在1分钟内出现在搜索结果中 |

### 测试用例推导来源

| 来源 | 推导方法 |
|------|---------|
| 用例 | 主流程一个测试 + 每个备选/异常流程一个测试 |
| 功能需求 | 每个"应"（shall）语句一个或多个测试 |
| 业务规则 | 每个规则结果一个测试 + 边界测试 |
| 状态模型 | 每个有效转换一个测试 + 每个无效转换一个测试 |
| 数据字典 | 每个受约束字段的边界值测试 |
| 质量属性 | 针对适合性标准的可衡量测试 |

### 在编码之前编写测试

概念性测试（在编码之前从需求编写测试）有以下几个目的：
1. **验证可测试性** ——如果你无法编写测试，则需求存在缺陷
2. **暴露模糊性** ——编写具体的测试步骤迫使你解决模糊的术语
3. **发现缺失的需求** ——测试场景揭示需求未涉及的条件
4. **创建验收标准** ——测试成为每个需求的"完成"定义

### 为什么这种方法有效

编写测试用例要求的精确程度超过了单纯编写需求本身。当你尝试写"给定[前置条件]，当[操作]时，则[预期结果]"时，你会发现需求没有指定前置条件，操作是模糊的，或者预期结果是未定义的。

### 反模式
- **不可测试的需求** ——需求中包含"适当的"、"用户友好的"、"快速"、"直观的"等词汇，且没有适合性标准
- **编码后才测试** ——仅在实现之后编写测试，这验证的是实现而非需求
- **仅覆盖正常路径** ——仅从用例的主流程推导测试，忽略异常和错误情况
- **缺少边界测试** ——仅测试典型值，不测试边界值和无效值

## 应用

使用 `template.md` 作为填写结构。

### 步骤1：盘点需要测试的需求

收集所有可测试的来源：
- 功能需求（"应"语句）
- 用例（主流程、备选流程和异常流程）
- 业务规则
- 质量属性需求
- 数据字典中的数据约束（`skills/data-dictionary/SKILL.md`）

### 步骤2：为模糊需求分配适合性标准

对于每个包含不可衡量术语的需求，定义适合性标准：

| 原始需求 | 问题 | 适合性标准 |
|---------|------|-----------|
| "系统应快速响应" | "快速"是主观的 | "搜索结果在3秒内显示，适用于最多1000条记录" |
| "系统应易于使用" | "易于"是主观的 | "新用户在5分钟内无需培训即可完成'添加化学品'任务" |
| "系统应处理大量数据" | "大量"未定义 | "系统支持10,000条化学品记录且无性能下降" |

### 步骤3：从用例推导测试

对于每个用例，生成测试：

**主流程测试：** 按照描述执行用例步骤。验证所有后置条件。

**备选流程测试：** 每个备选流程一个测试。验证备选后置条件。

**异常流程测试：** 每个异常流程一个测试。验证错误处理和恢复。

**边界测试：** 对于用例中的每个输入，测试边界值。

### 步骤4：从功能需求推导测试

对于每个"应"语句：
```
给定：[前置条件——测试前的系统状态]
当：  [操作——用户或系统执行的动作]
则：  [预期结果——可观察的结果]
```

至少生成：
- 一个正向测试（需求被满足）
- 一个反向测试（条件不满足时会发生什么）
- 针对任何数值、日期或字符串约束的边界测试

### 步骤5：从业务规则推导测试

对于每条业务规则（`skills/business-rule/SKILL.md`）：
- 测试规则的每个结果
- 测试所有阈值的边界条件
- 如果多个条件存在交互，测试组合情况（使用 `skills/decision-table/SKILL.md` 中的决策表）

### 步骤6：编制验收测试计划

将推导出的测试组织成验收测试计划：
1. 按功能或用例分组测试
2. 分配优先级（关键路径测试优先）
3. 确定测试数据需求
4. 确定环境需求
5. 定义整体系统的通过/失败标准

### 步骤7：通过测试验证需求

审查测试套件以发现需求问题：
- [ ] 每个需求至少有一个测试用例
- [ ] 每个测试用例有具体的预期结果（不能出现"系统表现适当"）
- [ ] 所有受约束输入的边界值都已测试
- [ ] 异常流程有对应的测试用例
- [ ] 质量属性有可衡量的适合性标准及对应测试
- [ ] 无法测试的需求已标记为需要重写

## 示例

请参阅 `examples/sample.md` 获取 ChemTrack 的完整测试用例推导。

简短示例：

```markdown
## 需求：CT-FR-12
"系统应阻止用户将化学品分配给实验，
如果该化学品的到期日期早于实验的开始日期。"

### 测试用例：

**TC-12.1：过期化学品被阻止（正向测试）**
- 给定：化学品"丙酮"于2026-01-15到期；实验于2026-02-01开始
- 当：用户将丙酮分配给该实验
- 则：系统拒绝并显示消息"化学品在实验开始日期之前到期"

**TC-12.2：有效化学品被接受（规则的反向测试）**
- 给定：化学品"丙酮"于2026-06-15到期；实验于2026-02-01开始
- 当：用户将丙酮分配给该实验
- 则：系统接受分配

**TC-12.3：同一天边界情况**
- 给定：化学品"丙酮"于2026-02-01到期；实验于2026-02-01开始
- 当：用户将丙酮分配给该实验
- 则：[需求缺口：'早于'是否包括同一天？]
```

请注意 TC-12.3 暴露了一个缺失的需求——原始需求没有指定"早于"是否包括同一天。

## 常见陷阱

### 陷阱1：接受不可测试的需求
**症状：** 像"系统应具有用户友好性"这样的需求在没有适合性标准的情况下被批准。

**后果：** 无法验证需求。验收测试变成主观判断。关于需求是否满足的争议不断。

**修复：** 每个需求必须有一个适合性标准。如果利益相关者无法用可衡量的术语定义"用户友好"，则协助他们讨论以建立具体的、可测试的标准。

---

### 陷阱2：仅测试正常路径
**症状：** 测试用例覆盖了每个用例的主流程，但忽略了备选流程和异常流程。

**后果：** 错误处理、边缘情况和恢复路径未经测试。大多数生产缺陷都发生在这些地方。

**修复：** 每个备选流程至少推导一个测试，每个异常流程至少推导一个测试。使用状态模型（`skills/state-modeling/SKILL.md`）来识别错误转换。

---

### 陷阱3：没有边界测试
**症状：** 测试仅使用典型的中间值（例如，数量=5），从不测试边界值（0、1、最大值、最大值+1）。

**后果：** 差一错误（off-by-one）、溢出条件和空集情况直到生产环境才被发现。

**修复：** 对于数据字典中的每个受约束字段，生成边界测试：最小值、最小值-1、最大值、最大值+1、零、空、null。

---

### 陷阱4：开发完成后才编写测试
**症状：** 测试用例在代码完成后编写，基于系统的实际行为而非应有行为。

**后果：** 测试验证的是实现而非需求。需求缺陷被编码到系统中，并被测试所"验证"。

**修复：** 在需求分析阶段、开发之前编写概念性测试用例。将编写测试作为需求验证技术来使用。
