## 目的
指导在组织或项目团队中系统地改进需求工程实践。当需求问题反复出现时使用此技能——遗漏的需求、模糊的规格说明、不受控的变更、不充分的评审——而临时性修复无法奏效。

这不是一次性评估。这是一个持续改进周期：评估、规划、试点、度量、重复。目标是从被动的救火模式转变为已定义的、可度量的、持续改进的RE过程。

## 关键概念

### 4阶段改进周期

```
阶段1：评估（ASSESS）      阶段2：规划（PLAN）
当前RE实践            --> 有优先级的改进
及其差距                  行动（含负责人）
       ^                          |
       |                          v
阶段4：评价（EVALUATE）    阶段3：创建/试点/推广（CREATE/PILOT/ROLL OUT）
度量结果并            <-- 新的过程资产，
调整方法                  在实际项目上试点
```

该周期不断重复。每次迭代针对少量改进（2-3项），进行试点，度量结果，并将发现反馈到下一个周期。

### 根因分析（石川图 / Ishikawa Diagram）

当需求问题发生时，追溯到根本原因而非表面症状：

```
                       需求缺陷
                          |
    +-----------+------+------+------+-----------+
    |           |      |      |      |           |
  获取        分析    规格    验证    管理      人员
    |           |      |      |      |           |
- 无观察    - 无     - 模糊  - 无   - 无     - 无RE
  会议        模型     语言    评审    基线      培训
- 遗漏关键  - 无     - 无    - 无   - 无     - 分析师
  SME         分解     模板    标准    变更      流动
- 技术选择  - 无     - 遗留  - 无   - 无     - 领域
  错误        CRUD     TBD     用户    追踪      知识
              矩阵             参与    矩阵      缺口
```

石川（鱼骨）图按类别组织原因。对于RE，主要类别映射到五个RE活动阶段加上一个"人员"类别。

### 目标-问题-度量（GQM）方法

在决定度量什么之前，先定义你想改进什么：

| 层级 | 描述 | 示例 |
|------|------|------|
| **目标（Goal）** | 你想要实现什么 | 将测试中发现的需求缺陷减少50% |
| **问题（Question）** | 你需要知道什么来评估目标 | 有多少缺陷源自需求？最常见的缺陷类型是什么？ |
| **度量指标（Metric）** | 什么数据能回答问题 | 每个发布版本的需求来源缺陷数量；缺陷分类（模糊性、不完整性、不一致性） |

GQM防止"为收集度量指标而收集度量指标"——每个度量指标都可追溯到一个问题，每个问题都可追溯到一个目标。

### 过程资产清单

RE过程资产分为两类：

**需求开发（RD）资产：**
- 获取指南和技术检查清单
- 分析模型模板（状态图、决策表、数据字典）
- SRS模板和编写指南
- 需求评审检查清单
- 需求模式（Requirement Pattern）目录

**需求管理（RM）资产：**
- 变更控制过程定义
- 追踪矩阵模板
- 需求状态跟踪规程
- 基线化规程
- 需求文档的版本控制约定

### 学习曲线（"绝望之谷"）

```
绩效
    ^
    |  *                                        * * * *
    | * *                                   * *
    |*   *                                * *
    |     *                             *
    |      *       绝望之谷          *
    |       *      (Valley of      *
    |        *      Despair)     *
    |         *    * * *     *
    |          *  *     * *
    |           **       *
    +-----------------------------------------> 时间
    旧方式                               新方式
```

引入新的RE实践时，团队绩效会在人们学习新方法期间暂时下降。这是正常的。危险在于在低谷期间放弃改进，回到旧的实践方式。

### 为什么有效
- **分阶段方法**防止"贪多求全"——一次改进2-3件事，而不是同时改变一切
- **根因分析**针对实际问题，而非症状
- **GQM**确保度量真正重要的东西，而非容易计数的东西
- **试点**在组织范围推广之前提供证据
- **学习曲线意识**让团队为暂时的绩效下降做好准备，使他们不会放弃

### 反模式
- **大爆炸式改进** ——同时引入15个新的RE实践。团队不堪重负，什么都无法落地，组织最终得出"过程改进不起作用"的结论。
- **只评估不行动** ——花数月时间评估当前实践，产出一份精美的报告，然后从不实施任何改进。
- **度量指标迷恋** ——收集30个度量指标却不将它们与改进目标关联。团队花在报告上的时间比改进还多。
- **归咎于人** ——将需求问题归因于个人能力不足而非过程缺口。根因通常是缺少过程资产，而非缺少人才。

## 应用

### 阶段1：评估当前RE实践（2-4小时）

**1.1 盘点当前过程资产**

审计当前已有的资产。对每个资产评定其状态：

| 资产 | 存在？ | 使用？ | 有效？ |
|------|--------|--------|--------|
| 获取指南 | Y/N | Y/N | Y/N |
| SRS模板 | Y/N | Y/N | Y/N |
| 评审检查清单 | Y/N | Y/N | Y/N |
| 追踪矩阵 | Y/N | Y/N | Y/N |
| 变更控制过程 | Y/N | Y/N | Y/N |
| 需求基线化 | Y/N | Y/N | Y/N |

存在但未使用的资产等同于不存在。使用但无效的资产需要修订。

**1.2 分析缺陷数据**

收集近期项目的数据：
- 有多少缺陷可追溯到需求来源？
- 类型是什么：模糊性、不完整性、不一致性、不可行性？
- 在哪个阶段发现的：评审、测试、生产？
- 修复成本是多少？

使用 `skills/requirements-risk-assessment/SKILL.md` 来识别哪些风险类别产生了最多的实际缺陷。

**1.3 构建石川图**

对于排名前3-5的反复出现的需求问题：
1. 将问题写成清晰的陈述（例如，"40%的测试缺陷可追溯到模糊的需求"）
2. 在每个RE类别下头脑风暴原因（获取、分析、规格说明、验证、管理、人员）
3. 对每个原因，连续追问"为什么？"2-3次以达到根因
4. 识别在各问题中出现频率最高的2-3个根因

**1.4 干系人反馈**

访谈项目参与者：
- 开发人员："需求在哪些方面导致你最多的返工？"
- 测试人员："有多大比例的缺陷可追溯到需求问题？"
- 产品负责人："需求在哪些方面与你的预期不符？"
- 项目经理："哪些RE活动对进度影响最大？"

---

### 阶段2：规划改进（1-2小时）

**2.1 对根因进行优先级排序**

从石川分析中，按以下维度对根因进行排序：
- 频率（这个原因多久导致一次问题？）
- 影响（后果有多严重？）
- 可行性（解决起来有多容易？）

选择排名前2-3的根因在本改进周期中解决。不要试图一次性修复所有问题。

**2.2 定义改进目标（GQM）**

对每个选定的根因，定义：

```
目标：[修复后会有什么不同？]
问题：[我们需要度量什么才能知道是否成功？]
度量指标：[要收集的具体数据，含基线和目标值]
```

示例：
```
目标：在2个发布版本内将模糊性缺陷减少50%
问题：每个发布版本有多少缺陷被分类为"需求模糊"？
度量指标：每个发布版本的模糊性来源缺陷数量
  基线：每个发布版本12个（最近3个发布版本的平均值）
  目标：每个发布版本6个或更少
```

**2.3 定义行动**

对每个目标，定义具体行动：

| 行动 | 负责人 | 截止日期 | 对应目标 |
|------|--------|----------|----------|
| 创建带编写检查清单的SRS模板 | BA主管 | Sprint 3 | 减少模糊性 |
| 试点需求评审检查清单 | QA主管 | Sprint 4 | 减少模糊性 |
| 培训团队使用状态建模 | BA主管 | Sprint 2 | 减少不完整性 |

每个行动必须有一个负责人（一个具体的人，而非一个委员会）和截止日期。

---

### 阶段3：创建、试点和推广（1-3个月）

**3.1 创建过程资产**

对每个计划的改进，创建或更新必要的过程资产。使用相关技能：
- SRS模板：`skills/srs-document/SKILL.md`
- 评审检查清单：`skills/specification-review-checklist/SKILL.md`
- 追踪矩阵：`skills/requirements-traceability/SKILL.md`
- 变更控制过程：`skills/change-control-advisor/SKILL.md`

**3.2 在实际项目上试点**

选择一个试点项目：
- 不是最关键的项目（风险太高）
- 不是最简单的项目（结果不够有说服力）
- 一个典型的、有代表性的项目，且团队愿意参与

试点期间：
- 培训试点团队使用新实践（投入2-4小时）
- 在初始使用期间提供教练支持
- 收集阶段2中定义的度量指标
- 记录哪些有效、哪些需要调整

**警告：预期会出现"绝望之谷"。** 试点团队最初会变慢。这是学习曲线。提前准备干系人的预期，使他们不会在低谷期间取消试点。

**3.3 根据试点结果调整**

试点结束后：
- 什么按设计运行？
- 什么需要修改？
- 什么因为不切实际而被放弃？
- 根据试点反馈更新过程资产

**3.4 推广**

成功试点后：
1. 根据试点经验更新过程资产
2. 向更广泛的组织传达结果（用数据，而非观点）
3. 培训其他团队（让试点团队成员担任教练）
4. 分阶段推广——不要在第一天就强制推行所有内容

---

### 阶段4：评价结果（1-2小时）

**4.1 收集度量指标**

从试点和早期推广中收集阶段2定义的度量指标：
- 缺陷数量是否在改善？
- 返工是否在减少？
- 实践者的反馈如何？

**4.2 根据目标进行评估**

对每个GQM目标：
- 是否达到了目标？
- 如果是，哪些因素促成了成功？
- 如果否，还有哪些障碍？当前的行动是否足够，还是需要不同的方法？

**4.3 反馈到下一个周期**

- 庆祝已记录的改进（即使是小的改进）
- 记录经验教训
- 识别下一批要解决的2-3个根因
- 返回阶段1开始下一个改进周期

## 常见陷阱

### 陷阱1：贪多求全
**症状：** 改进计划列出了15个要同时引入的新实践。

**后果：** 团队不堪重负。没有任何实践被正确采纳。六个月后，组织回到了旧的方式。

**修复：** 将每个改进周期限制为2-3个针对性变更。在扩展之前先展示成功。

---

### 陷阱2：跳过试点
**症状：** 新的RE实践在没有在实际项目上试点的情况下就在整个组织范围内强制推行。

**后果：** 不可预见的实际问题同时出现在每个项目上。引发广泛的挫败感。

**修复：** 始终先试点。一个有代表性的项目可以验证可行性并培养内部倡导者。

---

### 陷阱3：在低谷期放弃
**症状：** 新实践在2-3周后被放弃，因为团队"比以前更慢了"。

**后果：** 改进投资被浪费。团队对未来的改进努力产生了抵触情绪。

**修复：** 提前警告干系人学习曲线的存在。设定合理的预期："绩效将在4-6周内出现下降，然后才会改善。"

---

### 陷阱4：没有目标的度量指标
**症状：** 团队收集了20个度量指标，因为"数据是好的"，但无法解释他们想改进什么。

**后果：** 数据收集变成了开销。没有任何度量指标能推动行动，因为没有一个与改进目标关联。

**修复：** 严格使用GQM。每个度量指标必须追溯到一个问题，每个问题追溯到一个目标。如果一个度量指标不能驱动决策，就停止收集它。

---

### 陷阱5：没有反馈闭环
**症状：** 改进被推广但从未评价。团队假设它们在起作用，因为没有人抱怨。

**后果：** 无效的实践持续存在。有效的实践未被认可或强化。

**修复：** 阶段4（评价）不是可选的。将实际度量指标与目标进行比较。据此调整或庆祝。
