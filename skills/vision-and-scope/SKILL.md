## 目的
引导需求工程师构建愿景与范围文档，定义业务需求（目标、成功指标、风险）、项目范围（特性、限制、排除项）和业务上下文（干系人画像、优先级、部署）。使用此技能来防止范围蔓延（scope creep），使干系人就项目将交付和不交付的内容达成一致，并为所有下游需求工作提供稳定的基础。

这不是一份完整的SRS——而是在详细需求之前的战略框架文档。可以将其视为业务发起人和项目团队之间就*项目存在的原因*和*项目涵盖的内容*达成的契约。

## 关键概念

### 业务需求的三个层次
业务需求位于需求层次结构的顶端：

1. **业务需求（Business Requirements）** -- 项目存在的原因（目标、成功指标）
2. **用户需求（User Requirements）** -- 用户需要完成的事项（用例、用户故事）
3. **功能需求（Functional Requirements）** -- 系统必须执行的操作（详细行为）

愿景与范围文档捕获第1层，并界定第2层和第3层的边界。

### 业务目标模型
将目标构建为层次结构：

- **问题或机会** -- 业务驱动因素（例如，"客户入职流程需要3周，导致30%的流失"）
- **业务机遇** -- 对现有方案的竞品分析，阐明市场趋势和本产品的差异化优势
- **业务目标** -- 可量化的目标（例如，"将入职时间缩短至3天"）
- **成功指标** -- 如何衡量目标达成情况（例如，"入职完成率从70%提升至95%"）
- **愿景声明** -- 一句话概括产品方向

业务目标与成功指标的区别：业务目标说明"想要实现什么变化"，成功指标定义"用什么指标、什么基线、什么目标值来证明目标已达成"。两者不应混淆。

### 范围表示技术
用于界定范围的多种工具：

- **上下文图（Context Diagram）** -- 将系统显示为单个气泡，展示所有外部实体和数据流（参见 `skills/context-diagram/SKILL.md`）
- **特性树（Feature Tree）** -- 将特性按层级分解为子特性
- **事件列表（Event List）** -- 系统响应的业务事件、信号事件和时间事件的目录
- **范围内/外表（In/Out Table）** -- 明确的两列列表，列出范围内和范围外的内容
- **特性×版本矩阵（Feature-Release Matrix）** -- 将每个特性映射到计划的发布版本，展示各版本的实现程度和时间安排

### 反模式（这不是什么）
- **不是PRD** -- 愿景与范围文档更简短，聚焦于*原因*和*边界*，而非详细解决方案
- **不是愿望清单** -- 范围内的每个特性都必须可追溯到一个业务目标
- **不是不可变的** -- 当项目方向发生变化时更新它，但将变更视为受控决策

## 应用

使用 `template.md` 获取完整的填写结构。

### 步骤 1: 定义业务需求

**1.1 背景**
撰写1-2段文字说明项目存在的原因。从大众角度描述推动该计划的问题或机会，阐述产品产生的必要性。

**1.2 业务机遇**
分析当前市场中的现有产品或解决方案，突出本产品的优势和定位。具体要求：
- 列出2-3个现有方案（竞品、替代流程或传统做法）
- 对每个方案，说明其优点和无法解决的问题
- 描述当前的市场趋势、技术发展或政策环境，说明为什么现在是构建该产品的合适时机
- 总结本产品相比现有方案的核心差异化优势

**示例：**
```
| 现有方案 | 优点 | 存在的问题 |
|----------|------|-----------|
| Excel电子表格 | 零成本，灵活 | 无自动过期提醒，无法生成合规报告 |
| 通用LIMS系统 | 功能全面 | 价格昂贵，化学试剂管理非核心模块 |
| 纸质记录本 | 无技术门槛 | 无法检索，审计时需人工翻阅 |

市场趋势：高校实验室安全管理日趋规范化，EPA合规要求持续加强。

本产品优势：ChemTrack 专注化学试剂管理垂直场景，提供法规报告
自动生成和过期提醒，成本远低于通用LIMS系统。
```

**1.3 业务目标**
列出3-7个可量化的目标。每个目标应包含：
- 对将要发生什么变化的清晰陈述
- 量化的目标值（将X提升Y%，将Z从A降低到B）
- 衡量方法

注意：目标必须是可实现的。过高的目标（如"消除所有安全事故"）不现实，应设置合理的目标值。

**示例：**
```
BO-1: 将季度法规报告生成时间从3天缩短至4小时，
      通过分析仪表板中的首次价值实现中位时间进行衡量。
BO-2: 将试用转付费转化率从12%提升至25%，
      通过月度队列分析进行衡量。
```

**1.4 成功指标**
对每个业务目标定义验收标准。成功指标与业务目标的区别在于：业务目标说明"想要实现什么"，成功指标定义"如何证明已实现"。

对每个指标说明：
- **指标名称** -- 衡量什么
- **当前基线** -- 目前所处的位置
- **目标值** -- 需要达到的水平
- **衡量方法** -- 如何衡量
- **时间框架** -- 预计何时达到目标

**1.5 愿景声明**
用一句话表述产品的长期目的和意图，严格按照以下格式（Moore 模板）：

"**For** [目标客户]，**Who** [有某种需求或痛点]，**The** [产品名称] **Is** [产品品类]，**That** [关键优势/使用理由]。**Unlike** [当前替代方案或竞争对手]，**Our product** [核心差异化优势]。"

**1.6 业务风险**
列出项目面临的前3-5个风险。对每个风险说明：
- **风险描述** -- 可能出什么问题
- **概率** -- 用百分比范围或高(>60%)/中(30-60%)/低(<30%)量化
- **影响** -- 高 / 中 / 低（或1-10评分）
- **缓解措施** -- 具体的应对措施（不能只写"持续关注"）

**1.7 业务假设与依赖**
记录项目依据的前提条件和外部约束。区分两类：
- **假设**：项目团队相信为真但尚未验证的前提条件。对每个假设说明持有者和若不成立的后果。
- **依赖**：项目成功所依赖的外部因素（如第三方系统、外部组织配合）。对每个依赖说明依赖方和影响范围。

---

### 步骤 2: 定义范围和限制

**2.1 主要特性**
列出范围内的每个特性。对每个特性说明：
- **特性ID**（例如 FE-1、FE-2）
- **特性名称**
- **描述** -- 1-2句话概述
- **优先级** -- 高 / 中 / 低
- **支持的业务目标** -- 追溯到 BO-x

然后对每个特性进行子功能分解，列出2-5个组成该特性的具体子功能。如果无法列出子功能，说明特性定义过于抽象，需要进一步分析。

推荐使用特性树展示层次结构：产品 → 特性模块 → 子功能。

**2.2 初始发布范围**
使用特性×版本矩阵规划各版本的实现范围。对每个特性标注在各版本中的实现程度（完整/部分/不含），并说明每个版本的计划时间和范围目标。

```
| 特性ID | 特性名称 | v1.0 (时间) | v2.0 (时间) | v3.0 (时间) |
|--------|----------|-------------|-------------|-------------|
| FE-1   | 名称     | 完整        |             |             |
| FE-2   | 名称     | 部分        | 完整        |             |
```

**2.3 后续发布范围**
对每个后续版本说明计划时间、新增特性和推迟原因。

**2.4 限制与排除项**
明确列出*范围外*的内容及其原因：
```
OUT-1: 移动应用（第二阶段，初始发布优先桌面端）
OUT-2: 多语言支持（初始仅面向英语市场，暂不需要）
OUT-3: 与遗留ERP系统集成（将在单独项目中解决）
```

---

### 步骤 3: 记录业务上下文

**3.1 干系人画像**
对每个干系人群体说明：
- **名称/角色** -- 他们是谁
- **主要价值** -- 他们从产品中获得什么
- **态度** -- 拥护者 / 支持者 / 中立 / 批评者
- **主要关注点** -- 他们最关心什么
- **约束条件** -- 他们带来的限制

**3.2 项目优先级**
使用优先级矩阵锁定权衡决策：

| 维度    | 约束 | 驱动因素 | 自由度 |
|---------|------|----------|--------|
| 进度    |      |          |        |
| 特性    |      |          |        |
| 质量    |      |          |        |
| 人员    |      |          |        |
| 成本    |      |          |        |

规则：每列每行只能有一个勾选标记。每行只能有一个勾选标记。这迫使团队做出明确的权衡决策。

**3.3 部署考虑**
- **基础设施需求：** 硬件、软件、网络等部署所需的基础设施
- **开发与上线计划：** 开发里程碑、上线策略（一次性切换/分阶段/试点）、数据迁移
- **用户培训：** 培训方式、培训时间安排、上线后的技术支持计划

---

### 步骤 4: 评审与验证

- 与项目发起人一起审阅文档
- 验证每个特性至少可追溯到一个业务目标
- 与可能认为某些范围外项目已包含在内的干系人确认范围外列表
- 获得正式签批或将文档基线化

## 示例

参见 `examples/sample.md` 获取完整的愿景与范围文档。

简短示例摘录：

```markdown
## 业务需求

### 背景
ChemTrack 是一款用于管理大学实验室化学试剂库存的桌面应用程序。
实验室管理员目前通过电子表格跟踪化学试剂，
导致过期试剂未被发现，且每季度的法规报告需要2-3天才能完成。

### 业务机遇
| 现有方案 | 优点 | 存在的问题 |
|----------|------|-----------|
| Excel电子表格 | 零成本，灵活 | 无自动过期提醒，无法生成合规报告，数据孤立 |
| 通用LIMS系统 | 功能全面 | 价格昂贵（年费$5,000+/实验室），化学试剂管理非核心 |

本产品优势：ChemTrack 专注化学试剂管理垂直场景，成本远低于
通用LIMS系统，且针对法规合规和过期管理进行专项优化。

### 业务目标
- BO-1: 将季度法规报告生成时间从3天缩短至4小时
- BO-2: 消除库存中残留的过期化学试剂（目前任何时间点占库存的12%）
- BO-3: 在6个月内使目标实验室管理员的采用率达到90%

### 愿景声明
**For** 苦于手动化学试剂跟踪的大学实验室管理员，**Who** 需要满足日益严格的
法规合规要求，**The** ChemTrack **Is** 一款库存管理系统，**That** 能够自动化
合规报告和过期提醒。**Unlike** 电子表格跟踪或昂贵的通用LIMS系统，
**Our product** 以低成本提供实时可见性和一键式法规报告。
```

## 常见陷阱

### 陷阱 1: 没有指标的目标
**症状：** "改善用户体验"或"提高效率"，没有附加任何数字。

**后果：** 无法衡量成功。项目永远无法被宣布完成或进行评估。

**修复：** 每个目标都需要量化的目标值和衡量方法。如果无法衡量，就细化目标直到可以衡量为止。

---

### 陷阱 2: 通过遗漏定义范围
**症状：** 文档列出了范围内的内容，但从未说明范围外的内容。

**后果：** 干系人会假设他们偏好的特性已被包含在内。范围蔓延随之而来。

**修复：** 明确列出范围外的项目及其理由。这可能令人不适，但能防止后续更严重的冲突。

---

### 陷阱 3: 过多的业务目标
**症状：** 15-20个目标，涵盖了所有可以想象的内容。

**后果：** 没有重点。一切都是优先事项，所以什么都不是。

**修复：** 限制在3-7个目标。如果超过这个数量，说明项目范围过大——应该拆分。

---

### 陷阱 4: 愿景声明变成营销文案
**症状：** 愿景声明读起来像一篇充满流行语的新闻稿。

**后果：** 无法指导决策。团队无法用它来解决范围争议。

**修复：** 使用结构化格式：对于[谁]中[有某种需求]的人，[产品]是一个[品类]，它[优势]。不同于[替代方案]，我们的产品[差异化优势]。

---

### 陷阱 5: 没有干系人优先级矩阵
**症状：** 进度、特性、质量、人员和成本都是"最高优先级"。

**后果：** 当权衡出现时（总会出现），没有框架来做决策。

**修复：** 使用约束/驱动因素/自由度矩阵进行强制排序。每个维度只能获得一个指定。

---

### 陷阱 6: 没有竞品分析的业务机遇
**症状：** 业务机遇部分只描述了问题或技术趋势，没有列出现有产品/方案，也没有说明本产品的差异化优势。

**后果：** 读者无法理解为什么需要"这个"产品而不是使用现有方案。缺乏说服力。

**修复：** 列出2-3个现有方案，对每个方案分析优点和不足，然后明确阐述本产品如何解决这些不足。对比必须具体——"功能单一、体验不佳"这类笼统描述不算有效对比。

---

### 陷阱 7: 特性描述过于笼统
**症状：** 特性列表只有一行名称，如"库存管理"、"用户管理"、"报表功能"，没有子功能分解。

**后果：** 范围定义模糊，开发团队对特性的理解不一致。20分的评分项可能大幅失分。

**修复：** 每个特性必须包含1-2句描述和2-5个子功能。如果无法列出子功能，说明特性定义过于抽象，需要进一步分析。推荐使用特性树展示层次结构。

---

### 陷阱 8: 保留 AI 生成标记
**症状：** 文档中残留 `[placeholder]`、`**TODO**`、ChatGPT风格的格式痕迹、"需要我帮你..."等提示语，或模板占位符未替换。

**后果：** 暴露文档未经认真审阅，严重损害专业性和可信度。

**修复：** 提交前全文搜索方括号 `[]`、`TODO`、模板占位符，逐段确认所有内容都是项目的实际内容。
